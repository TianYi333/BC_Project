## 真机 OTA 收尾未烧录：根因定位（2026-09-02 续）
- 现象：TFTP 收满→写 PENDING→软复位后，App 上电打印 `ota: meta state=1 (PENDING)`，且 boot 全程无日志。说明 boot **没把 PENDING 处理成 DONE**——只要 boot 真跑了 do_update，无论成功(DONE=2)或失败(FAILED=4)都会 write_meta 落盘，App 不可能读到 1。
- 已排除：① FAL 分区偏移 vs boot 裸 OTA_*_OFFSET 逐字节一致；② App 链接 0x08100000 正确；③ boot 的 SPI1 初始化完整（spi.c 的 MX_SPI1_Init+HAL_SPI_MspInit 已编入 boot 且 HAL_SPI_Init 失败会死循环、而 App 能跑说明 SPI OK）；④ SFUD 默认标准读、全工程无 0xB9 深度掉电/Quad 使能，裸读不应失效。
- 最可能根因：**驻留 0x08000000 的 bootloader 是旧版（不含 do_update）或从未烧入**。用户反复 ST-Link 烧的是 App(0x08100000)，旧 boot 只校验向量表后跳 App、不读 ota_meta → PENDING 原封不动。新 App 能从 0x08100000 跑起来，反证 0x08000000 必有合法 boot（旧版）在跳 App。
- 修复（非代码动作）：单独编译 `boot` 目标 → 把 `build/Debug/boot.bin` 烧到内部 Flash **0x08000000** → 重跑 OTA；预期 state 走 1→2(DONE)→3(CONFIRMED)。
- 兜底（待用户确认再改代码）：若烧新 boot 仍 state=1，则是 boot 读 W25Q 返回垃圾（magic 不匹配）。可在 boot 里把读到的 magic 写到一个空闲 SPI 扇区、App 启动打印，无需 UART 即可观测 boot 实际读到了什么。
- 用户后续重编 App 版本升至 1.0.5 并再次 OTA 推送（len=371836/crc=9C829B7B 与早前一致，即推的是同一份 firmware.bin），复位后 App 仍打印 `state=1 (PENDING)`。继续指向根因：**驻留 0x08000000 的 boot 仍是旧版（不含 do_update），用户尚未单独编译 boot 并烧到 0x08000000**。App 端 OTA 接收链路（upgrade_start 接受→TFTP 收满→写 PENDING→软复位）已确认每次 100% 正常，唯一卡点在 boot 烧录。建议用"加明显启动打印的新 firmware.bin 走 OTA"来肉眼区分 boot 是否真烧录成功。

### backup 后卡死真因 = SCB_DisableDCache/ICache 触发 HardFault（2026-09-02 15:07 用户实测 + 定位）
- 用户烧 19544B 寄存器级版断电重启，串口实测：`[BOOT] START` → `try=0 magic=4C55424F state=1` → `final ...` → `do_update: crc_spi=F444F368 exp=F444F368` → `** DO NOT POWER OFF **` → `backup done` → `[BOOT] flash unlock ok` → **`[BOOT] HARDFAULT`**（不再静默）。
- **真因（决定性）**：`flash unlock ok` 之后、下一个本该打印 `mass-erase BANK2...` 之前只有三步 `SCB_DisableDCache()` → `SCB_DisableICache()` → `FLASH->CCR2=...`；而 FLASH 寄存器访问在 `flash_unlock` 已验证可用（读 CR2/写 KEYR2 未挂），故 **HardFault 100% 出在那两个 cache 关闭调用**。这同时解释了最早"backup done 之后卡死无输出"——旧版用默认 HardFault handler（静默 `while(1)`），把这个故障伪装成了"卡死/擦除慢"。**之前所有"HAL 50s 等待"假设都错，真凶是 cache 关闭调用本身。**
- 机理：boot 上电复位后 D-Cache/I-Cache **默认关闭且全程不开启**，Flash 读回直接走 AXIM，本无缓存一致性问题；在此处调用 `SCB_DisableDCache()/SCB_DisableICache()` 反而会触发 HardFault（具体为 Usage/Bus 类，待 HFSR/CFSR 确认）。
- **修复（/d/Desktop/boot/Core/Src/main_boot.c）**：① `erase_app_internal` 删除 `SCB_DisableDCache(); SCB_DisableICache();` 两行；② 把 `HardFault_Handler` 升级为打印 `HFSR/CFSR/MMFAR/BFAR/PC/LR/MSP`（`__get_MSP()` 取栈帧，按 `EXC_RETURN[4]` 区分有无 FPU 栈帧取 PC），便于万一仍崩时一锤定音故障类型。重新 `cmake --build` 产出 `boot.bin`=**19664B**（链接仍 `0x08000000`，Entry `0x080002D9`）。

### TFTP ERROR 1 根因：改 OTA 文件名后的"引导死锁"（2026-09-02 16:2x）
- **现象**：GUI 真机升级报 `TFTP ERROR 1: Unable to open requested file`（`ota_tftp_push.py` line 110 的 `tftp_put` 抛出）。这是 lwIP TFTP server 在 `tftp_open_cb` 返回 NULL 时回的标准错误，即**设备端主动拒绝打开请求**。
- **设备端 `tftp_open_cb`（ota.c:157）三个拒绝分支**：① `write==0`→"read not supported"；② `strcmp(fname, OTA_TFTP_FILENAME)!=0`→"reject file %s (expect %s)"；③ `g_ota_state!=OTA_RX_ACTIVE`→"no active upgrade session"。任一命中都回 ERROR 1。
- **根因**：文件名不匹配。GUI 已收到 `upgrade_start_ack`（说明 `g_ota_state==ACTIVE` 成立、WRQ 也非读请求），故命中分支②——设备当前运行的**老固件**里 `OTA_TFTP_FILENAME` 还是旧值 `firmware.bin`，而 GUI 现在发 `Oil_Pump_Control.bin`。证据：`build/Debug/Oil_Pump_Control.bin` mtime 15:38:05 晚于 `ota.h` 15:38:03（新构建已含 `Oil_Pump_Control.bin`），但设备上仍是此前两轮 OTA 确认的老固件（当时文件名还是 `firmware.bin`）。
- **处置（引导死锁）**：改 OTA 文件名后，老固件只认旧名 → 本次引导升级必须把 GUI 的"TFTP 文件名"框临时改成 `firmware.bin`（匹配当前运行老固件），推送新 `.bin`；升级重启进新固件后，才能用默认 `Oil_Pump_Control.bin`。或用 CubeProgrammer 直接烧 `0x08100000` 跳过文件名检查。
- **可复用经验**：**改 OTA 接收文件名是一次性的"鸡生蛋"问题**——新固件内部虽已用新名，但要把它推上去，推送时 TFTP 文件名必须先用旧名引导一次，否则老固件按旧名校验直接拒绝。
