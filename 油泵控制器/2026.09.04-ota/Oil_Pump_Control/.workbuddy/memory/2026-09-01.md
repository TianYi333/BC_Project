# 2026-09-01 OTA 第3步硬件验证完成

## 验证过程与结论
- 第3步（内部Flash双区 + Bootloader双target构建）已通过硬件验证。
- 烧录方式：CubeProgrammer 分别烧 `boot.elf`@0x08000000、`Oil_Pump_Control.elf`@0x08100000（两个文件均**不勾选** Run after programming）。
- 用 Device memory 读取两区向量表确认地址正确：
  - boot 区 0x08000000 首字=0x24008000(MSP→D1 SRAM)、Reset_Handler=0x080009F9（在 boot 区）✅
  - app 区 0x08100000 首字=0x24008000(MSP)、Reset_Handler=0x08125989（在 app 区）✅
- **最终验证**：断电/按复位键（脱离调试器，自然从 0x08000000 启动），板子正常进 App（OLED/业务跑起来）→ boot→app 跳转成功。
- 结论：App 链接脚本(0x08100000)+main.c 的 SCB->VTOR=0x08100000 + boot.ld(0x08000000/64K) + CMake boot target 均正确生效。

## 遇到的问题
- 烧录 `Oil_Pump_Control.elf` 时一度报 "Error: failed to erase memory"（擦除失败）。
- 根因：ST-Link 连接偶发问题（非配置/代码问题）。**断开烧录器重新连接后恢复正常**。
- 经验：H743 用 CubeProgrammer 烧录偶发擦除失败，先尝试重连 ST-Link、Reset 时机、检查 Option Bytes(DBANK/WRP) 再排查。

## 第4步实施（boot 端 OTA 烧录+回滚，已落地待构建验证）
- **方案修正**：原想直接把 Fal/SFUD 编入 boot，但发现 `sfud_port.c` 依赖 FreeRTOS(`vTaskDelay`/`#include "FreeRTOS.h"`) 与日志系统(`logInfo`)，`fal_def.h` 默认用 `rt_malloc/rt_kprintf`，`fal_rtt.c` 是 RT-Thread 设备模型——裸机 boot 编进去会链接爆炸。故改为 **boot 内置极简 W25Q64 SPI 裸驱动 + 自实现 CRC32**，物理偏移与 fal_cfg.h 分区表严格对齐。
- 新增文件：
  - `Core/Inc/ota_common.h`：ota_meta_t(32B)/状态枚举(NONE/PENDING/DONE/CONFIRMED/FAILED)/物理偏移(fw_a@192KB,bak@1216KB,meta@2240KB)/App地址，boot 与 App 端第5步 ota.c 共用。
  - `Core/Src/boot_crc.c`+`Core/Inc/boot_crc.h`：复制 fdb_utils.c 的 crc32_table + 同款循环，与 App 端 fdb_calc_crc32 字节级一致。
  - `Core/Src/boot_w25q.c`+`Core/Inc/boot_w25q.h`：W25Q64 极简驱动(read/page-program/64KB-block-erase/4KB-sector-erase)，用 SPI1(hspi1)+SPI1_NSS，与 sfud_port 共用硬件。
- 改写 `Core/Src/main_boot.c`：完整状态机——读 ota_meta；PENDING→校验fw_a CRC→备份App→擦内部Flash(bank2 mass erase)→烧fw_a→校验内部Flash CRC→置DONE/失败回滚bak置FAILED；DONE→回滚bak置NONE；CONFIRMED→清标记；NONE/FAIL→直接跳。H7 D-Cache/ICache 擦写前关闭；32-bit 字编程尾部补0xFF。
- 改 `CMakeLists.txt`：boot target 源加 `Core/Src/spi.c`+`boot_crc.c`+`boot_w25q.c`，include 加 `Core/Inc`。
- 待本地构建验证：boot target 是否链接成功（需 STM32_Drivers 含 HAL_SPI/HAL_FLASH 模块；若 undefined reference 需补源）、boot.bin<64KB、断电复位跳转正常。
- 仍待办（App 端，建议并入第5步）：App 启动成功后写 ota_meta=CONFIRMED（完整 A/B 防砖的最后一块；否则 DONE 状态下次启动会被判失败回滚）。第5步 ota.c 接收固件写 firmware_a + 写 ota_meta(PENDING,new_len,new_crc32) 也需实现。

## 本沙箱构建验证（2026-09-01 续）
- 沙箱无 ninja/make，改用 `arm-none-eabi-gcc`(/d/APP/GCC-ARM/bin) 直接复刻 boot target 的编译+链接（源列表/inc/宏/链接脚本取自 cmake/stm32cubemx 与 toolchain 文件），路径须用 Windows 风格(D:/...) 否则 gcc(Windows exe) 找不到文件。
- **构建中暴露并修复 6 处缺陷**（原以为只 4 处）：
  1. boot target 缺 `stm32h7xx_hal_msp.c` → SPI1 时钟/引脚未配置（HAL_SPI_MspInit 是弱空实现）。→ CMakeLists boot target 增加该源。
  2. boot 无 `SysTick_Handler` → HAL_Init 开 SysTick 后第一次 tick 跳 Default_Handler 死循环。→ main_boot.c 加 `void SysTick_Handler(void){HAL_IncTick();}`。
  3. `Error_Handler` 未定义（spi.c 失败分支调用，仅 main.c 有）→ 链接失败。→ main_boot.c 加死循环实现。
  4. CS 引脚 SPI1_NSS 未初始化（软件 CS，需 GPIO 输出）→ boot_gpio_init() 配 CS 输出空闲高，main() 中 HAL_Init 后、MX_SPI1_Init 前调用；不拖 gpio.c/it.c 进 boot。
  5. main_boot.c 用 memcpy/memset 但缺 `<string.h>` → 隐式声明。→ 加 `#include <string.h>`。
  6. **（关键架构错误）原 `burn_spi_to_internal` 用 `FLASH_TYPEPROGRAM_WORD` 4字节编程，但 STM32H7 HAL 的 HAL_FLASH_Program 只支持 `FLASH_TYPEPROGRAM_FLASHWORD`（256-bit/32字节 flash word），且无 WORD 类型**。→ 改为按 32 字节对齐 flash word 编程：RAM 中 32 字节对齐缓冲(buf[32] __aligned(32))，尾块按擦除值 0xFF 补齐，`HAL_FLASH_Program(FLASHWORD, addr, (uint32_t)buf)`，addr 步进 32。CRC 仍按 new_len 字节校验，与 fw_a 一致。
- **验证结果：BUILD_OK**。boot.bin = 12988 B(≈12.7KB) < 64KB(占 19.8%)；链接无 undefined reference、无警告(-Wall -Wextra 干净)；向量表@0x08000000；MSP=0x24080000(RAM_D1 顶)；Reset_Handler=0x08000e49(合法 Thumb)。boot.ld 生效（非 App 链接脚本）。
- 注意：`erase_app_internal` 擦写前关 D/I Cache 后未重新打开；boot 跳 App 后由 App 自行开 Cache，不阻塞。
- 结论：Step4 boot 端 OTA 烧录+A/B 回滚代码已正确可构建。下一步做第5步 ota.c(TFTP 收固件写 firmware_a+写 ota_meta PENDING) 与 App CONFIRMED 写入（防砖最后一块）。改动前仍需先给用户方案确认。
