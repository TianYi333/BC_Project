## H743_VS_GCC_IDE：tcp_client_task 卡死在 LOCK_TCPIP_CORE() 根因定位（对比 Oil_Pump_Control）

### 现象
- 打印到 `[NET:203] Flash loading network configuration succeeded, TCP started` 后，
  `tcp_client_task` 上电跑一小段就静默，断点卡在 `net_comm_task.c:1272` 的 `LOCK_TCPIP_CORE()`，
  连 `Start connect server IP:...` 都打不出来。

### 根因（已定位，待用户选方案修复）
1. `H743_VS_GCC_IDE/LWIP/Target/lwipopts.h:84` 人为加了
   `#define LWIP_TCPIP_CORE_LOCKING 1`（中文注释"开启TCPIP内核锁，多任务并发安全增强"，
   文件 mtime 9/2 17:32，位于 `USER CODE BEGIN 0` 区，非 CubeMX 默认）。
2. 该宏为 1 时 `LOCK_TCPIP_CORE()` = `sys_mutex_lock(&lock_tcpip_core)`
   → `osMutexAcquire(..., osWaitForever)`；而 `sys_arch.c:399` 用 `osMutexNew(NULL)`
   创建，**非递归、无超时**。宏为 0 时该宏展开为空。
3. 参考工程 `Oil_Pump_Control` **磁盘上没有 lwipopts.h**（全盘 find 只剩
   `build/Debug/.cache/clangd/index/lwipopts.h.*.idx` 索引残留，疑似被误删），
   故走 lwIP 默认值 `LWIP_TCPIP_CORE_LOCKING = 0`，LOCK/UNLOCK 全是空操作
   → 从来不会卡在锁上。这是两个工程行为分叉的根源。
4. H743 的 `net_comm_task.c` 从 Oil_Pump 移植时**漏了锁**：
   - `tcp_sender_task`（3352 `tcp_sndbuf` / 3383 `tcp_write`）**完全没有** LOCK_TCPIP_CORE，
     而 Oil_Pump 版 `tcp_sender_task` 有（Oil_Pump net_comm_task.c 2931/2940/2972/2984/2993）。
   - UDP 路径（`udp_discovery_pcb_create` 428/436/447、`udp_discovery_pcb_destroy` 411/412、
     `udp_send_device_online` 730/893）只有 `udp_pcb_mutex`，**无 core 锁**。
   - 已加锁的：`safe_tcp_close`（1115，core→tcp_send_mutex 顺序）、`tcp_client_task` 重连分支（1272）。
5. 死锁路径：tcpip_thread 持 core 锁处理一切 lwIP 事务，与裸调 raw API 的
   tcp_sender_task / udp_discover_task 并发改写同一批 pcb / pbuf / memp 链表
   → 链表损坏 → tcpip_thread 持锁卡死 → core 锁永不释放 → tcp_client_task 永久阻塞。
   并行路径：`safe_tcp_close` 持 core 锁等 `tcp_send_mutex`(osWaitForever)，
   持有者 tcp_sender_task 若卡在被破坏的 `tcp_write` 里，同样导致 core 锁永久被占。

### 候选修复方案（已提交用户选择）
- 方案 A（最小、先定性）：lwipopts.h:84 改回 `LWIP_TCPIP_CORE_LOCKING 0`，行为立即与 Oil_Pump 一致。
- 方案 B（长期正确）：保留 =1，给 `tcp_sender_task` 补 LOCK/UNLOCK（core→mutex，照抄 Oil_Pump 版），
  UDP 路径补 core 锁，`safe_tcp_close` 的 `osMutexAcquire(tcp_send_mutex, osWaitForever)` 改带超时。
- 建议：先用 A 验证坐实根因，再按 B 改正确版本。

### 排查中确认"不是原因"的项
- `udp_recv_callback` 用 `xQueueSend(..., 0)` 非阻塞，不会持锁阻塞。
- `tcp_parse_cmd` 内最长阻塞只有 `xQueueSend(..., pdMS_TO_TICKS(10))`，无永久阻塞。
- `tcpip_init(NULL, NULL)` 回调为空；输入走 `tcpip_input` mbox 投递；`TCPIP_MBOX_SIZE 6` 满时丢包不阻塞。
- `LWIP_DHCP 0`、`TCPIP_THREAD_PRIO 32`、`TCPIP_THREAD_STACKSIZE 4096`。
- `ota_app_confirm()`（freertos.c:391）已注释，与本问题无关。

### 待办
- freertos.c:391 的 `//ota_app_confirm();` 需恢复（根因与 OTA 无关）。

## H743_VS_GCC_IDE：OTA 升级报 WinError 10054（TFTP 阶段）根因定位

### 现象
GUI 工具日志：TCP 50010 连上 → 发 upgrade_start → 设备只回了 `register` 包（无 ack）
→ 立刻 TFTP 下发 → `ConnectionResetError: [WinError 10054] 远程主机强迫关闭了一个现有的连接`
（ota_tftp_push.py:95）。

### 根因（时序错配，已定位）
1. **PC 端 `recv_until_ack` 早退 bug**（ota_tftp_push.py:66-78）：
   `except socket.timeout: if buf: break`。收到设备的 `register` 后 buf 非空，
   下一次 1s 超时就 break，**实际只等约 1 秒且完全不检查是否收到 ack**。
   GUI 日志里那句 "设备回: {...register...}" 正是这个早退的产物。
2. **设备端先擦 Flash 再起 TFTP**（H743 `ota.c:239-246` `ota_handle_upgrade_start`）：
   `fal_partition_erase(g_fw_part, 0, OTA_FW_PART_SIZE)` 擦 1MB → **擦完才** `tftp_init()`。
   即命令到达到 UDP 69 真正监听之间存在数秒空窗。
3. **擦除耗时量级**：`OTA_FW_PART_SIZE = 0x100000`（1MB），firmware_a @192KB。
   SFUD `sfud_erase` 走 SFDP 选粒度：W25Q64 若用 64KB block erase → 16×150~300ms ≈ 2.5~5s；
   若 SFDP 不可用回退 4KB sector → 256×45~100ms ≈ 11~25s。均远超 PC 端的 ~1s 等待。
4. **10054 的真正含义**：Windows UDP socket 收到 ICMP port unreachable 后，
   下一次 `recvfrom`/`sendto` 抛 `WSAECONNRESET`。所以"远程主机强迫关闭"
   实际是 **UDP 69 当时没有监听**，不是 TCP 断链。
5. **附加隐患**：`tcp_parse_cmd` 由 `tcp_recv` 回调调用，运行在 **tcpip_thread 上下文**；
   `LWIP_TCPIP_CORE_LOCKING=1` 时该线程正持有 core 锁 → 擦除数秒期间
   整个 lwIP 停摆、其他任务 `LOCK_TCPIP_CORE()` 全阻塞。与上面 TCP 死锁同属一类问题。

### 已排除项
- `HMAC_KEY` 两端一致（project_config.h:68 `"0123456789abcdef0123456789abcdef"`）。
- 时间/seq 校验的 `goto` 已注释（H743 net_comm_task.c:2005/2010），设备 RTC 停在
  1735664019 也不会拒收命令。
- 签名源串两端逐字符一致：`{"device_id":..,"new_crc32":..,"new_len":..,"seq":..,"ts":..,"type":"upgrade_start"}`，
  device_id 用 register 里的 510400440035，`uint64_to_str` 无前导零。
- 参数合法：new_len=352972 < 1MB，new_crc32=0xFAC6948B 非 0。
- `tcp_send_upgrade_start_ack` 走 tcp_send_queue 队列，非直发；register 能发出说明队列通。

### 待确认（看串口日志三条）
- `TCP Recv JSON:` → 命令是否收到；
- `TCP received message successfully!` vs `sign check failed!` → 签名是否过；
- `ota: upgrade_start accepted, ... TFTP listening` → 就绪时刻（据此量出真实擦除耗时）。

### 候选修复方案
- A：只改 PC 端脚本（`recv_until_ack` 必须收到 ack 才返回、超时提到 30s；
  TFTP 前固定延时；`sock.setsockopt(SOL_SOCKET, SIO_UDP_CONNRESET, False)` 关掉
  Windows 的 ICMP→10054 行为，让超时重试逻辑真正生效；WRQ 重试次数加大）。不改固件，零风险。
- B：只改固件（擦除移出 upgrade_start 同步路径：先 tftp_init + 回 ack，
  再在独立任务擦除，或在 `ota_feed_chunk` 里按 4KB/64KB 边收边擦）。
- C：A + B 都做（推荐长期）。

## 已实施：修复 boot 备份/回滚长度越界（D:/Desktop/boot）

### 前提确认
- `.ioc` 中 `Mcu.CPN=STM32H743ZGT6` → 后缀 G = **1024KB Flash**，双 bank 各 512KB。
- `boot/boot.ld`: `FLASH ORIGIN=0x08000000, LENGTH=64K`（boot 在 BANK1 前 64K）。
- App `STM32H743XG_FLASH.ld`: `FLASH ORIGIN=0x08100000, LENGTH=512K` → BANK2 = 0x08100000~0x0817FFFF。
- 故 `OTA_FW_PART_SIZE`(0x100000, 1MB) 用于内部 Flash 必然越界 512K。

### 改动（boot/Core/Src/main_boot.c）
1. 新增常量（紧随 `APP_ADDRESS` 之后）：
   `#define APP_FLASH_SIZE (512UL * 1024UL)`，注释说明须与 SPI 分区大小
   `OTA_FW_PART_SIZE`(1MB) 区分：内部 Flash 相关长度一律用本常量。
2. `backup_app_to_bak()`：`remaining = OTA_FW_PART_SIZE` → `APP_FLASH_SIZE`；
   擦除循环 `for (b = 0; b < OTA_FW_PART_SIZE; ...)` → `b < APP_FLASH_SIZE`（1MB→512K，8 次 64K 擦）。
3. 三处回滚 `burn_spi_to_internal(OTA_FW_BAK_OFFSET, OTA_FW_PART_SIZE)`
   → `..., APP_FLASH_SIZE`（do_update 两处 + `case OTA_STATE_DONE` 一处）。
4. **新增容量保护**（防砖）：`burn_spi_to_internal()` 开头加
   `if (len == 0 || len > APP_FLASH_SIZE) return -1;`
   ——因 App 端 `ota_handle_upgrade_start` 仍按 `OTA_FW_PART_SIZE`(1MB) 校验 new_len，
   超过 512K 的固件 App 会接受、boot 会越界烧录，故在 boot 侧兜底。

`FLASH: 19728 B / 64 KB (30.10%)`，生成 boot.bin(19728B) / boot.hex / boot.elf。
`OTA_FW_PART_SIZE` 在 main_boot.c 中仅剩注释引用，不再参与任何内部 Flash 操作。

### 代码层复核（"continue" 时做的验证，未改文件）
- `tcp_sender_task`(net_comm_task.c:3277) 与 `udp_discover_task`(L465) 均为独立
  FreeRTOS 任务（osThreadNew 在 ETH_InitTask，L375/L369），**非 tcpip_thread**。
- 它们内的 raw API：`tcp_sndbuf`(L3352)/`tcp_write`(L3383)、`udp_new/bind/recv/sendto`
  只持有各自的 `tcp_send_mutex` / `udp_pcb_mutex`，**均无 `LOCK_TCPIP_CORE`**。
- 翻 lwIP 源码确认：`core/tcp.c` 的 `tcp_write` **不**自带 `LOCK_TCPIP_CORE`；
  lwIP 内该锁仅在 `api_msg.c`/`netifapi.c`/`sockets.c`（tcpip_thread 自身消息处理）使用。
  → 从非 tcpip 线程调 raw API 必须由应用自己加锁，否则与持锁 tcpip_thread 并发改 pcb。
- **结论**：`=1` 下原死锁根因（并发破坏 pcb 链表 → tcpip_thread 持锁卡死）在代码中
  **仍然存在**，重新编译本身不会改变这一点（源码 =1 与原死锁版本一致）。
  用户实测 OK 可能源于测试场景（连上/注册/少量控制报文）未触发竞争窗口；
  OTA 大量 TCP 数据搬运 + 网络侧 ACK/重传并发时可能复现。
- **行动**：尊重用户裁定，未改任何代码；仅如实告知残留风险。如需确认稳定性，
