## 网络重连 HardFault + pbuf 断言排查
- 现象：网络重连时触发 HardFault（HFSR=0x40000000 FORCED，CFSR=0x8200 BFARVALID+PRECISERR，BFAR≈0xFF001E），调用栈停在 `tcp_fasttmr`；同时串口打印两次 `pbuf.c:753` 断言 `pbuf_free: p->ref > 0`。
- 根因定位：
  1. `tcp_error_callback` / `tcp_recv_cb(p==NULL)` 只在断开时设置 `tcp_pending_close=1`，没有清空全局 `tcp_pcb`；lwIP 在 errf/recv-close 返回后会立即释放 pcb，导致后续 `safe_tcp_close()` 对**已释放 pcb** 调用 `tcp_abort`，造成 pcb 链表和 pbuf 队列双重释放/损坏。
  2. 业务任务（Tcp_client_task / tcp_sender_task / safe_tcp_close）直接调用 lwIP raw API，未在 `LWIP_TCPIP_CORE_LOCKING=1` 环境下获取 `LOCK_TCPIP_CORE()`，与 `tcpip_thread` 并发操作 pcb/pbuf 链表。
- 已修改 `UserCode/Drivers/ETH/net_comm_task.c`：
  - `tcp_error_callback`：设置 pending 同时 `tcp_pcb = NULL; g_tcp_connected = 0;`。
  - `tcp_recv_cb` 错误/关闭分支：同上清空指针。
  - `safe_tcp_close`：先 `LOCK_TCPIP_CORE()` 再拿 `tcp_send_mutex`，abort 后两把锁都释放；队列清理和 `vTaskDelay(20)` 移到核心锁外。
  - `tcp_sender_task`：把 tcp 状态检查/`tcp_sndbuf`/`tcp_write` 临界区用 `LOCK_TCPIP_CORE()` + `tcp_send_mutex` 保护，统一顺序 core→mutex。
  - `Tcp_client_task` 重连块：在核心锁保护下执行 `tcp_new`/`tcp_connect`/`tcp_abort` 并赋值 `tcp_pcb`。
- 已修改 `UserCode/Drivers/ETH/net_comm_task.h`：增加 `#include "lwip/tcpip.h"` 以使用 `LOCK_TCPIP_CORE` / `UNLOCK_TCPIP_CORE`。
- 未编译（本机无 arm-none-eabi），需在 STM32CubeIDE Clean+Rebuild 验证。
- 仍存在的同类风险（本次未改）：`net_config_init` / `udp_msg_process` 中的 `netif_set_*`、`autoip_*`、`sntp_*`、UDP raw API 也应在核心锁下执行；如重连问题复现，可继续加锁。

## 网络重连 HardFault 后续（新截图：malloc/free 路径崩溃）
- 现象：重连时 HardFault 转移到 `_malloc_r`（`tcp_new/tcp_alloc`）和 `_free_r`（`HAL_ETH_TxFreeCallback` ← `low_level_output`），说明 C 库堆/freelist 元数据已损坏，问题从 TCP 定时器内部转移到了内存分配器。
- 根因再定位：
  1. `lwipopts.h` 中 `MEM_LIBC_MALLOC=1` / `MEMP_MEM_MALLOC=1` 让 lwIP 使用 C 库 malloc/free；一旦 pbuf 被 double-free 或越界写，C 库堆元数据损坏后所有 malloc/free 都可能 HardFault。
  2. `low_level_output` 在启动 ETH DMA 前未做 D-Cache clean；STM32H7 的 DMA 与 D-Cache 不一致可能读到脏数据，甚至触发总线错误。
  3. `safe_tcp_close` 直接使用 `tcp_abort`；`tcp_abort` 会释放 unacked TCP 段里的 pbuf，而这些 pbuf 可能仍挂在 ETH DMA 发送描述符上，等 DMA 完成后 `HAL_ETH_TxFreeCallback` 再 `pbuf_free` 一次，形成 double free。
- 已修改：
  - `LWIP/Target/lwipopts.h`：注释掉 `MEM_LIBC_MALLOC` 和 `MEMP_MEM_MALLOC`，让 lwIP 使用自带的 `LWIP_RAM_HEAP_POINTER`（0x30000800）内部堆与固定 memp pools，隔离 C 库堆。【**已撤销**：用户要求恢复原配置，现恢复 `#define MEM_LIBC_MALLOC 1` / `#define MEMP_MEM_MALLOC 1`，lwIP 重新走 C 库 malloc/free。】
  - `LWIP/Target/ethernetif.c`：`low_level_output` 曾加 TX 前 D-Cache clean（`SCB_CleanDCache_by_Addr`）。【**已撤销**：当前 MPU Region 0 (0x24000000 D1 AXI SRAM) 为 Write-Through (NON_BUFFERABLE)，CPU 写直接穿到物理 RAM，DMA 读即最新数据，clean 非必需；且该 clean 与网络重连 HardFault 无因果关系，为保持简洁已删除。注意：若将来 Region 0 改为 Write-Back，则 TX 必须重新加 clean。】
  - `UserCode/Drivers/ETH/net_comm_task.c`：
    - `safe_tcp_close`：先取 pcb 引用，清空全局指针，再 `tcp_close()`；只有 `tcp_close()` 失败才 fallback 到 `tcp_abort()`，减少粗暴 abort 导致 pending pbuf double-free 的概率。
    - `tcp_connected_cb` 错误分支：删除 `tcp_abort(tpcb)`；lwIP 回调里 pcb 所有权已归 lwIP，用户只清全局引用，由 errf (`tcp_error_callback`) 释放。
- 未编译（本机无 arm-none-eabi），需在 STM32CubeIDE Clean+Rebuild 验证。若问题复现，新配置下 lwIP 更可能给出明确断言（如 `pbuf_free: p->ref > 0`），便于进一步定位。

## 新增：电机启停事件时间记录
- 需求：记录电机启动/停止的时间点。
- 设计：电机状态由状态机写入快照 `motor_status.state`（STOP=0/RUN=1/WAIT=2/FAULT=3）。在 `MainLogicTask` 主循环末尾跟踪上一拍电机状态 `last_motor_state`（static，初值 MOTOR_STATE_WAIT），检测"进入 RUN=启动 / 离开 RUN=停止"跳变打点。RUN<->WAIT 不记（WAIT 仅软件等待态，电机未实际停转）。
- 数据结构：`MotorEventRecord`（event/hour/min/sec/tick(uint64_t)），数组 `g_motor_event_records[MOTOR_EVENT_MAX_CNT=32]`，计数 `g_motor_event_cnt`，满则 memmove 前移覆盖（与报警记录同风格）。时间取用复用 `refresh_rtc_time()`+`RtcTime`（北京时间显示）+`RTC_To_UnixMs()`（UTC 精确时间戳），与报警记录一致。
- 落点：`main_logic.h`（结构体/枚举/extern 声明，紧跟 AlarmRecord 后）、`main_logic.c`（全局数组定义 + static 跟踪变量 + 循环末尾跳变检测与记录 + `LOG_logic`）。
- 注意：初始 `last_motor_state=WAIT`，上电后首次进入 RUN 会记一条 START（合理）；WAIT 是软件态不触发 STOP，故上电不会误记 STOP。
