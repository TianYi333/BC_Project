## 修改：sync_from_sysdb 增加全零有效性判断 + 触发重置
- 需求：从 FlashDB 读出的 sys_cfg 若全部参数为 0（未初始化/损坏），则调用 `flashdb_format_and_reset()` 恢复默认值。

- 边界：仅当所有字段同时为 0 才触发重置；只要任一字段非 0（如默认值 ref_pressure 等）即视为有效，不会误伤合法配置（如 min_motor_speed=0 这种单字段 0 不被误判）。

  - 原 `if(got == sizeof(SYS_CONFIG_T))` 改为 `if(got >= sizeof(SYS_CONFIG_T))`：兼容旧固件写入的更大 blob（本次删掉的 4 个校准字段在原结构体末尾，头部布局一致，取前 sizeof 字节即为有效配置），避免升级后用户已保存配置被整体清空。`fdb_kv_get_blob` 在存储 blob > buf_len 时只拷贝头 buf_len 字节、返回存储实际大小，故 got>sizeof 时 tmp 头部有效。

## 修改：sys_cfg 增加 magic + 版本号 + CRC32 校验（堵"部分损坏"漏洞）
- 需求：在前面全零判断基础上，进一步检测"部分位翻转/非全零但损坏"的记录，校验不过则 `flashdb_format_and_reset()` 恢复默认。
- 设计（`main_logic.h` 新增，紧邻 SYS_CONFIG_T）：
  - `#define SYS_CFG_MAGIC 0x4C554232U`("LUB2")、`#define SYS_CFG_VERSION 1U`。
  - `SYS_CFG_HDR_T { uint32_t magic; uint32_t version; uint32_t crc32; }`；`SYS_CFG_STORE_T { SYS_CFG_HDR_T hdr; SYS_CONFIG_T cfg; }`（写入 FlashDB 的完整记录 = 头+载荷）。
- 改动：
  - `sync_to_sysdb()`：改为写 `SYS_CFG_STORE_T`；`store.hdr.crc32 = fdb_calc_crc32(0, &store.cfg, sizeof(SYS_CONFIG_T))`（复用 FlashDB 自带 `fdb_calc_crc32`，flashdb.h:73 已声明，syncif.c 已 include）。
  - `sync_from_sysdb()`：读入 `SYS_CFG_STORE_T store`；
    - `got == sizeof(SYS_CFG_STORE_T)` → 校验 magic+version+CRC32（应用层校验，与 FlashDB 自身 KV CRC 互补）。任一失败 → format&reset；全零 → format&reset；否则 `SysConfig_WriteSnapshot(&store.cfg)`。
    - `else if(got >= sizeof(SYS_CONFIG_T)` → 兼容**旧固件**（无头、直接存 SYS_CONFIG_T）：`memcpy(&tmp, &store, sizeof(SYS_CONFIG_T))` 取头部有效载荷（自动丢弃已移除的 4 校准字段），下次 sync_to_sysdb 自动重写新格式；全零→reset。
    - `else`（got < sizeof） → format&reset。
  - syncif.c 加 `#include <string.h>`（memcpy/memset）。
- 关键正确性：
  - 新格式 blob 的 `got` 恒 == sizeof(STORE)；FlashDB 自身 KV CRC 校验存储长度与数据，位翻转不改 `got`。故新格式损坏(magic/crc 错)必走第一分支 → reset，**不会**误落入旧格式分支造成"假接受"。
  - 旧格式 blob 的 `got`(如 64) != sizeof(STORE)(60) → 正确走旧格式兼容分支。（验证：旧结构=13+4字段、新结构=13字段、STORE=新载荷+12头，二者尺寸不等，无碰撞。）
  - 仅 syncif.c 读写 "sys_cfg"（grep 确认），无其它旧格式写者导致新格式读失败。
- 效果：kill 之前"部分损坏仍被原样采用"的漏洞；新设备/损坏/全零/版本不符 → 全部走 reset 恢复默认；旧固件配置平滑迁移不丢失。
- 未编译，需 Clean+Rebuild 验证（重点：fdb_calc_crc32 原型、SYS_CFG_STORE_T 尺寸、memcpy/memset 来自 string.h）。

## 修复：TCP 接收 JSON 签名排序触发 MemManage（IACCVIOL）
- 现象：STM32CubeIDE 调试截图显示调用栈 `tcp_recv_cb → tcp_parse_cmd → cJSON_SortObjectRecursive → qsort → med3 → MemManage_Handler`，故障寄存器 `IACCVIOL` 置位。
- 根因：`cJSON_SortObjectRecursive` 里把 `qsort` 的比较函数 `key_cmp` 定义为**嵌套函数（nested function）**。GCC 会为嵌套函数在**栈上生成 trampoline 可执行代码段**，而 Cortex-M7 MPU 把栈区配置为 **XN（Execute Never）**。当 `qsort` 通过函数指针调用该 trampoline 时，CPU 尝试从栈地址取指执行，触发 **IACCVIOL**（指令访问违规）→ MemManage Fault。
- 修复（`UserCode/Drivers/ETH/net_comm_task.c`）：
  - 把嵌套函数提到文件顶部，改为 `static int cJSON_KeyCompare(const void *a, const void *b)`。
  - 删除 `cJSON_SortObjectRecursive` 内部的嵌套定义，`qsort(..., cJSON_KeyCompare)` 调用文件级函数。
  - 比较函数内增加 NULL key 防御（NULL 排最前，避免 strcmp 传 NULL 触发另一次 fault）。
- 验证：grep 确认全工程仅 `net_comm_task.c:1781` 一处 `qsort(`，无其它嵌套比较函数残留。
- 未编译，需 Clean+Rebuild 验证（重点：确认 `cJSON_KeyCompare` 不再生成栈 trampoline，可用反汇编或断点确认）。

## 修复：配网改 IP 后仍走满 5 秒重连节流（重连门被 safe_tcp_close 冲掉回拨）
- 现象复核：之前以为配网 `reconnect_tick = HAL_GetTick() - 5000` 能让重连立即触发，但实际无效——因为 `tcp_pending_close` 分支在 `safe_tcp_close()` 后会执行 `reconnect_tick = HAL_GetTick()`（Tcp_client_task 内，原 1184 行）把回拨覆盖掉，重连门看到的仍是"刚断开时刻"，照样等满 5 秒。
- 修复（`UserCode/Drivers/ETH/net_comm_task.c`，3 处）：
  1. 全局区新增 `static volatile uint8_t g_fast_reconnect = 0;`（reconnect_tick 旁）。
  2. 配网回调（config_set，约 1010-1017）：在 `reconnect_tick = HAL_GetTick() - 5000;` 后再置 `g_fast_reconnect = 1;`（保留原回拨作双保险）。
  3. 重连门（约 1249-1257）：将节流条件由 `(now - reconnect_tick < reconnect_interval)` 改为 `((now - reconnect_tick < reconnect_interval) && (g_fast_reconnect == 0))`，并在通过节流后 `g_fast_reconnect = 0;` 消费清零。
- 语义：标记在"发起连接前"消费，故快速重连后若握手失败，标记已清零，下一轮仍走 5 秒节流，不会形成重试风暴。IP 变更 → 立即重连一次；之后任何失败 → 5 秒节流兜底。stable_delay(2s) 等待网络稳定仍保留。
- 未编译，需 Clean+Rebuild 验证（重点：FLASH 占用 +32B，标记与分支是否生效）。
