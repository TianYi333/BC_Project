## 安全顺序修复：task_order 验签前入队漏洞
- 问题：原 `tcp_parse_cmd` 的 `task_order` 分支在 HMAC 签名校验(2385-2403)之前就把任务 `xQueueSend` 入队 / `sched_add_split_task` 进调度表(2148-2195)，伪造/错签帧会在验签失败 `goto exit` 前已排进注油动作。
- 修复（手术刀式，仅 net_comm_task.c）：
  1. 从 `task_order` 分支移除入队/调度动作，仅保留解析填 buf + 构造签名原文。
  2. 在签名校验通过后的 post-verify 段（函数末尾、`exit:` 标签之前）插入带 `type=="task_order"` 守卫的入队/调度动作。
- 验证：build/verify 增量整编 EXIT 0（FLASH 359564B）。
- 顺带确认：`stop_task` 分支虽在验签前写了 `g_stop_target_task_id`，但真正急停 `g_force_stop_task=1` 在验签后段(2431-2443)，非漏洞，未动。`state_request/task_empty/heartbeat_ack/upgrade/device_reboot` 分支仅构造签名原文+解析局部变量，无验签前全局副作用。

## 解析规则澄清 & period_seq / total_x10 语义落地
- 用户给出 task_order 字段契约 + 解析规则：分次字段(sub_index/sub_total/adj_period_sec/total_x10)仅当 sub_total>0 出现；exec_at 仅当 >0 出现；task_type 1/2 不带分次字段（旧固件兼容）。
- 经确认三项决策：
  1. **分流依据维持 `task_type==3`**（不改判 `sub_total>0`，接受 task_type=3 但 sub_total=0 的静默丢任务边角）。
  2. 示例 JSON 中 task_type=1 带全部分次字段只是 schema 说明，真实 1/2 不会带。
  3. **period_seq 是 execute_result 上行字段，下行 task_info 不含它**（之前误判为"遗漏"，实际无矛盾）。
- period_seq 落地改动（net_comm_task.c/.h）：
  - 删掉下行解析 `cJSON_GetObjectItem(item,"period_seq")` 及其存储（它不是下行字段）。
  - 上行 execute_result 仍回报 period_seq（保留 `cJSON_AddNumberToObject` 与 inline_report_result 的赋值）。
  - 上报值取 **sub_index**（用户确认：取 sub_index，非分次/离线填 0）；调度器 online 置 `g_slot3_ctx.period_seq = s->sub_index`，offline 置 0。
- total_x10 语义最终确认 = **注油次数(count)**；离线整轮体积公式 = `total_x10 × n`，**n=阀体规格**(本机 1ml，常量 `INJ_V_UNIT_ML=1`)。
  - 等价关系：`total_ml = total_x10 × n = 单份×K`（单份必为 n 的整数倍，K=份数）。离线拿不到逐份分布，按阀体额定剂量整轮注。
  - 改动：离线公式由 `total_x10 × inj_v` 改为 `total_x10 × INJ_V_UNIT_ML`；INJ_V_UNIT_ML 注释更新为"n：阀体规格"。
- 验证：build/verify 增量整编 EXIT 0（FLASH 359476B）。
