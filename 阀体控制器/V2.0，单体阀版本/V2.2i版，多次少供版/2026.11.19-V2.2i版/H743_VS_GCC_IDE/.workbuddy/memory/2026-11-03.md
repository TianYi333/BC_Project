## 修复：入站验签排序函数的键数上限缺陷（方案 B 的自我修正）

### 起因
用户追问"数组是不只在内部做排序" → 复核 `json_sort_object_children` 实现时发现**自己引入的缺陷**。

### 缺陷
首版（2026-11-02）用「**定长数组（`JSON_SORT_MAX_ITEMS=32`）收集子节点 + 重建链表**」：
```c
cJSON *items[JSON_SORT_MAX_ITEMS];
for(cJSON *c = obj->child; c != NULL && n < JSON_SORT_MAX_ITEMS; c = c->next)
    items[n++] = c;
...
obj->child = items[0];      // 只重建了前 32 个
```
**键数 > 32 时，第 33 个及之后的节点被从链上孤立**：
1. **签名串丢字段** → 验签必然失败（整帧作废、任务被静默丢弃）；
2. **内存泄漏** —— `cJSON_Delete` 只沿 `next` 链遍历（`cJSON.c:106-118`），
   被孤立的节点永不释放；cJSON 走 `pvPortMalloc` → 泄漏耗尽 FreeRTOS 堆。
- 实际报文最内层对象约 10~16 键，**当时不会触发**；但属于埋雷，且"防御性上限"本应是"安全降级"而非"破坏数据"。

### 修复：改用**稳定 selection sort**（两条独立链）
`rest`（未排序，原链）/ `out`（已排序，结果链），每轮从 `rest` 找最小节点、摘下挂到 `out` 尾部。
- **零额外缓冲区** → 无键数上限；**两条链各自独立遍历** → 结构上不可能自环；**稳定**（相同 key 取最先出现者）。
- 同时删除失去用途的 `JSON_SORT_MAX_ITEMS` 宏。

### 踩坑记录（重要：**"遍历中修改链表"是死循环高发区**）
本次为找正确算法试了 3 个版本，**前两个都死循环**（Python 复刻时被 SIGTERM 打断才暴露）：
1. **就地摘链插入排序**（摘下节点、在已排序段中找位置插回）：
   搜索插入位置时会**扫回刚插入的节点自身** → `ins` 前进到 `cur.next` → **成环死循环**。
   加 `sorted_end` 边界仍无法根治（边界随插入而变）。
2. **冒泡式相邻交换**：交换 `c` 与 `nxt` 后 `c` 仍在 `nxt` 之前，两节点**来回交换无限循环**。
3. ✅ **最终方案：摘链 + 两条独立链 selection sort** —— 关键在于"结果链"与"未排序链"**互不遍历**。
- **教训**：在**单向/双向链表**上做重排时，若排序过程需要**回溯已处理节点**，几乎必然成环。
  安全做法是"维护两条不相交的链"或"先收集到独立容器再重建"。
- **教训2**：定长数组做"收集-重建"时，**超限必须是"放弃排序、原样返回"而非"截断"** —— 后者会静默丢数据。
  若无法确定上限，宁可不用数组（改用链表原地算法）。

### 验证
- 编译 **EXIT=0**；FLASH 360972 → **360764 B（-208 B）**（去掉栈数组）；**RAM_D1 330240 B 不变**。

  真实网关帧签名仍 == `4020F204`；**5700 组随机排列压力测试零错误**。

- **排序合规性：全部通过** —— 9 个分支签名串键序均为严格字典序。
  `task_order` 用新增的 `json_sort_keys()` 递归排序；其余 8 个为手工拼串（键固定、无数组）。
- **字段完整性：全部通过** —— 各分支字段集合与报文完全一致，无遗漏。
  ⚠️ 但这是**脆弱点**：网关若新增字段，设备拼串不会自动带上 → 验签必失败（已实测确认）。

  与 `通讯实例.txt` 记录值**逐位吻合**（证明两侧算法字节级一致）。
  另注意：`通讯实例.txt` 里 **"Sorted task_order" 行漏写了 `remaining` 字段**（"complete" 行有），
  记录值对应的是**含 remaining** 的串。

### 审计中发现的一处"假阳性"（我的复刻错误，非固件缺陷）
首版审计脚本报 `device_reboot` 键序错（`device_id` 在 `delay` 前）。**实际代码是对的**：
`net_comm_task.c:2416` 的 `cJSON_AddNumberToObject(temp_sign, "delay", ...)` **在** `:2418` 的 `device_id` **之前**，
键序 `delay → device_id → reason → seq → ts → type` 与注释一致；真实帧 `通讯实例.txt:80` 也是这个顺序。
**教训**：用 Python 复刻固件行为时，必须**照抄代码的实际调用顺序**而非照抄注释 ——
注释与代码不一致时（本例中我是被自己的注释误导），复刻会引入假阳性。

### 已知风险点（均非本次改动引入；当前字段集下不触发）
1. **时间窗校验 + seq 防重放两道闸被注释掉**（`:2089-2099` 的 `// goto exit;`）：
   签名对了就放行，不检查过期/重放。合法帧被截获后原样重发仍会执行（除非被 dedup 拦下，
   但去重窗口仅 48 格且环形覆盖）。**放开前须确认网关每次发新 seq + 合法 ts**，否则误杀正常帧。
2. **字符串 HTML 转义不对称**：Go `json.Marshal` 默认转义 `<` `>` `&` → `\u003c` `\u003e` `\u0026`；
   cJSON **不转义** → 字段含这三字符时两边串不同、验签失败。
   当前全部字段为 `[A-Z0-9_]` 纯 ASCII 不触发，但属**依赖数据内容的巧合**，非设计保证。
3. **浮点格式不对称**：cJSON `print_number` 非整数用 `%f`（`1.5` → `1.500000`），Go 用最短表示（`1.5`）→ 失配。
   协议 V2.7 中 `task_info[]` 全为 `int`；设备出站 `valve_temp`/`valve_hum` 亦为 `uint16_t`
   （`net_comm_task.h:159-160`）→ **当前无浮点字段**，不触发。
   （`temperature`/`voltage` 只出现在 `通讯实例.txt` 历史帧里，**协议 V2.7 未定义**，是网关侧字段，设备不上报。）
4. **签名仅取 HMAC-SHA256 前 4 字节（32 bit）** + `strcmp` 比较（非常量时间）：
   前者是协议规定（§2.4.1「取结果前8位」），碰撞概率 1/2^32；后者是理论时序侧信道，收益极低。
