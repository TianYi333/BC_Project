## 离线整轮兜底超注缺陷确认（分析阶段，待用户选方案）

用户提问：批1、批2 已在线执行，断连后批3 的 exec_at 到点，是否会又注一次整轮量？
**结论：会，且超注。** 已逐行核对 `net_comm_task.c`：

### 缺陷链路
1. 在线执行批（`:3811-3816`）：`val = s->inj_v`（只注本份 15ml），随后 `s->done=1; s->valid=0` **回收槽位**
   → 调度表不再保留"本轮已注了多少"的任何痕迹。
2. 断连后批3 exec_at 到点 → 调度器走 else 离线分支（`:3820`）。
3. `already` 守卫（`:3828-3835`）判据 = `valid && done && 同task_id`。
   但全工程 `done=1` 只有两处写入（`:3815` 在线、`:3859` 离线），**两处都同时把 `valid` 置 0**
   → 不存在 `valid==1 && done==1` 的表项 → `already` 恒为 0 → **守卫完全失效**。
4. 于是 `total_val = s->total_x10`（`:3838`）= 整轮 45ml 整量注入 → 与已注 30ml 重复。
   结果 15+15+45 = **75ml，应为 45ml，超注 30ml**。

### 变体（与"网关发几批执行几批"无关）
- 断连时批3 帧**已收到** → 批3 到点触发 → 超注 = 45 - 30 = 30ml。
- 断连时批3 帧**未收到**（表内只剩批2）→ 批2 到点触发 → 超注 = 45 - 15 = 15ml。
- 一轮全部批都在断连前收到且未执行 → 首个到点的批触发整轮 45ml → **正确，无超注**。

### 叠加效应
- 第二段周期注油：`last_fire_unix` = 首批发 exec_at（`:2441`），`adj_period_sec`=3672 → T1+3672 再注 45ml（新一轮语义，量本身正确，但与第一段在同一周期窗口叠加）。
- 离线注油不回报（TCP 断开，`g_tcp_connected` 守卫）→ 网关只看到批1/批2 的 execute_result（各 15ml），账面 30ml，设备实注 75ml，**账实不符**。

### 根因一句话
离线整轮兜底直接用"整轮量 total_x10"，固件**没有"本轮已注量"记账**；唯一防护（`already` 守卫）因判据多写 `valid &&` 而恒假，且槽位复用（`sched_add_split_task` 对 `valid==0` 槽 `memset` 复用，`:2018`）会抹掉前批 `done` 标记 → 守卫即使修判据也不彻底。

## 调度器改为按 exec_at 排序触发（2026-10-30，加固）

**背景**：原实现按数组下标顺序触发（"第一个到点且槽3 空闲"即执行）。但 `sched_add_split_task` 填**第一个 `valid==0` 的空槽**，而执行完的槽立即 `valid=0` 回收 → 新批会复用已释放的空槽 → **入表顺序 ≠ `exec_at` 顺序时可能乱序**。当前网关批间隔 1224s ≫ 单批耗时 ~6s，实际不会触发，属防御性加固。

**实现**（`net_comm_task.c` `task_scheduler_task`）：拆成"先选后触发"两步。
```c
int pick = -1; uint32_t pick_at = 0;
for(uint8_t i = 0; i < SCHED_MAX; i++) {
    SplitTaskSched_t *s = &g_sched_list[i];
    if(s->valid == 0 || s->done == 1) continue;
    if(s->exec_at > 0 && now < s->exec_at) continue;   // 未到点
    uint32_t key = (s->exec_at == 0) ? 0U : s->exec_at; // exec_at==0 视为立即执行、键=0
    if(pick < 0 || key < pick_at) { pick = (int)i; pick_at = key; }  // 严格小于 → 同值保稳定
}
if(pick >= 0 && task_object_list[3].task_status == 0) { /* 触发 g_sched_list[pick] */ }
```
**排序规则**：`exec_at` 升序；`exec_at==0`（立即执行）键=0 排最前；`exec_at` 相同按下标小者优先（稳定）。
**槽3 忙**：本拍整拍不触发（不再逐格 continue），表项原样保留、等下一拍重试 —— 语义与改前一致。

**推演验证**（Python 复刻同一算法，5 场景全过）：
1. 乱序下发（batch3@3000/batch1@1000/batch2@2000）→ 执行顺序 batch1→batch2→batch3 ✅
2. `exec_at==0` 优先于已过期的 `exec_at=100` ✅
3. 同 `exec_at` 取下标最小者（稳定）✅
4. 槽3 忙 → 不触发、`valid`/`done` 不变 ✅
5. **槽位复用打乱入表顺序**（old1@1000 回收后 new@5000 复用槽0）→ old2@2000 仍先于 new@5000 执行 ✅（改前会乱序）

**收益**：FLASH 359316 → 359396 B（+80 B，两趟扫描 + 少量局部变量）；RAM_D1 不变（无新增全局）。

**文档同步**：契约 §4.2-8（新增"按 exec_at 排序触发"说明）、§6 第 6 条（追加加固说明）。

**注意（工具链坑）**：本次 Edit 工具对该文件的 UTF-8 中文匹配连续失败（`String to replace not found`），改用 **Python 按行号锚点替换**才成功（脚本 `.workbuddy/tmp_patch_sched.py`，用完已删）。后续改本文件中文注释块时优先考虑 Python 脚本方案。

## 离线周期配置单槽覆盖缺陷确认（8 注油点场景，2026-10-30）

**用户提出**：离线注油只能记录一个注油点（id），设备有 8 个注油点，网关断网前若把 8 个点的注油间隔都发过，其他 7 个点没有实现相应功能。

**结论：确认存在，且比"只记录一个点"更严重 —— 逐点覆盖、先到的配置被彻底删除。**

### 根因（精确定位）
- `net_comm_task.c:49`：`OfflineRoundSched_t g_offline_round_sched = {0};` —— **单实例全局**。
- `net_comm_task.c:2429-2439` 捕获逻辑：`new_round = (valid==0) || (task_id 不同)`，判为新轮次即**整份覆盖**（inj_id / total_x10 / adj_period_sec / task_id / last_fire_unix 全冲）。
- `net_comm_task.c:2440-2451` else 分支（同 task_id）**也覆盖 `inj_id`**。
- ⇒ 网关"一帧 8 个 task_info"（`TASK_DATA_MAX=8` 允许）或"连发 8 帧"，8 个点各有各 task_id → 逐个判新轮次 → 逐个覆盖 → **离线后只剩最后一个点有自注油能力**，其余 7 点离线期一次都不注油（total_x10 / adj_period_sec / 轮起点全丢）。
- 修复范围很窄：`g_sched_list[]` 每项自带 inj_id，**8 个点可共存、不受影响**；坏的只有 `g_offline_round_sched` 这条"离线周期自主整轮注油"路径。

### 附带发现（另一套机制，需与用户区分）
- **type=2（周期）路径离线也不自注油**：`injector_task_maker`（running_logic.c:231）本地定时器只置 `injectRequest=99` 并入 `xTimerReqQueue` → `timer_req_send_task`（net_comm_task.c:3363-3369）离线时 `TCP offline, drop timer notify` **直接丢弃**；本地不产生注油动作，全靠网关收 `task_request` 后回下发 `task_order`。
- ⇒ 若用户所说"8 个点的间隔都发过"指 **type=2 的 inj_ts（整周期）** → 离线时 8 个点全都不注油（另一问题）；
  若指 **type=3 的 adj_period_sec（整轮间隔）** → 即上述单槽覆盖问题。两者机制不同、修复方式不同。

### 推荐方案 A（待用户确认，未动代码）
单槽 → 按 inj_id 分 8 槽（索引 inj_id-1），每槽独立存 `{valid, inj_id, total_x10, adj_period_sec, task_id, last_fire_unix}`。
- 捕获：`p->inj_id` 直接定位自己槽；轮界判定改为**该槽自己的 task_id** 是否变化 → 同时支持"一个 task_id 跨多点"与"每点独立 task_id"两种网关风格，互不覆盖。
- 离线触发：每拍扫 8 槽挑**到期最早**者触发（槽3 单注油口天然串行）；只推进该槽自己的 `last_fire_unix = now`（保持"宁少不补、防爆发"）。
- RAM：8 × 64 B = 512 B，净增 **448 B**（H743 RAM_D1 现用 329792 B，空间充裕）。
- 契约语义不变：total_x10 整轮量 / adj_period_sec 整轮间隔 / last_fire_unix 取本轮首批发时间。

## 方案 A：type=1/2/4 补落去重键（2026-10-30，用户选定"A"）

### 背景（用户提问引出的核查）
用户质疑："type=1/2/4 是直接执行的，不需要入队，且没有 sub_index 还需要加 dedup_mark 吗？"
核查结论（两条都需澄清）：
- **"直接执行、不入队"不准确**：type=1/2/4 走 `xQueueSend(xTcpTaskQueue, ...)`（`net_comm_task.c:2533`），
  队列在 `freertos.c:258` 创建（`TCP_TASK_QUEUE_LEN=16`）。它**不入的是 `g_sched_list` 调度表**
  （那是 type=3 按 `exec_at` 延时执行用的），但**确实入 FreeRTOS 队列**。
  "入队"（执行路径）与"去重"（防重复执行护栏）是正交的两件事。
- **"没有 sub_index"不是不落键的理由**：type=1/2/4 的键退化为单 `task_id`，而这**正是它们应有的粒度**
  （一轮只有一个实体任务，不存在"第 2..K 批"要区分）。type=3 需要复合键是因为一轮内多批共享同一 task_id，
  两者需求方向相反。
- **真实缺陷**：`dedup_is_duplicate` 检查在 `task_type` 分支**之前**对所有类型生效，
  但 `dedup_mark` **全工程仅 type=3 分支一处**（`:2492`）→ type=1/2/4 的去重护栏**形同虚设**，
  同一 `task_id` 重传会被重复执行 → **重复注油**。原 `:2459` 注释声称"type1/2/4 保持原时机（入队前落键）"，
  与实现不符（描述的是从未实现的意图）。

### 改动（`UserCode/Drivers/ETH/net_comm_task.c`，2 处）
1. **type=1/2/4 分支**：`xQueueSend` 改为检查返回值，**成功后才** `dedup_mark(p->task_id, p->sub_index)`；
   失败（队列满）则**不落键** → 网关重传可重新入队（不因一次拥塞永久丢任务）。
   同时补 LOG（入队成功 / 队列满）。
2. **修正 `:2459` 注释**：统一表述为"去重键一律在【本任务成功被受理之后】才落"（type=3=入表成功、type=1/2/4=入队成功）。

### 关键实现约束（务必保留）
- **落键必须用 `p->sub_index`，不可硬编码 0**：检查点用的是 `p->sub_index`。
  硬编码 0 时，若网关在 type=1 帧误带非 0 `sub_index`，会"查 `(task_id,5)`、写 `(task_id,0)`"
  → 去重失效 + 污染 type=1/2/4 键空间。type=1/2/4 的 `sub_index` 恒为 0，故 `p->sub_index` 天然等于单 task_id 键。
- **落键必须在受理成功之后**：否则表满/队列满时任务被丢却被环记住 → 网关重传被拦 → 永久丢失。
- **键空间隔离**：type=1/2/4 落 `(task_id,0)`、type=3 落 `(task_id,1..K)` → 同一 task_id 下两型互不误杀。

- Python 复刻算法推演 **9 组场景全过**：type=1/2/4 重传被拦 / 不同 task_id 互不影响 /
  队列满不落键且环未被污染 / type=1 与 type=3 同 task_id 键隔离 / **type=1 误带 sub_index=5 时去重仍生效且未污染 (Y,0) 键空间** /
