## 分次调度表容量核查：发现 3 个待修缺陷（只读分析，未改代码）
背景：用户问"g_sched_list 为什么是 24、表内任务是否顺序执行"，并补充"网关每批推一帧、task_info 只有 1 个元素"。
- **SCHED_MAX=24 的真实语义**：不是"同时挂起 24 份"，而是**设备一生只能接受 24 帧 type3 task_order**。
  原因：`sched_add_split_task()`（`net_comm_task.c:2012-2036`）找空位靠 `valid==0`，而调度器只置 `done=1`
  （`:3797` 在线 / `:3839` 离线），**全工程无任何一处把 `g_sched_list[i].valid` 置回 0**（grep `valid = 0` 命中的全是
  `g_slot3_ctx.valid`）。故表项只增不减 → 第 25 帧起 `sched_add_split_task` 返回 -1，`:2433` 只打一行
  LOG `sched_list full, drop split task`，**不回报 execute_result、不回报失败** → 网关 150s 看门狗超时判失败。
  按 K=3 份/轮 ≈ 8 轮（周期任务每天 1 轮 → 8 天）后设备永久拒收 type3。
- **连带缺陷（更隐蔽）**：`net_comm_task.c:2426` 的 `dedup_mark()` 在 `:2431` `sched_add_split_task()` **之前**执行
  → 表满被丢弃的那份，去重键已写入 → 网关重传同一帧会被 `dedup_is_duplicate` 跳过 → 该批**永久丢失**，无法自愈。
- **离线降级过量注油风险**：离线分支 `:3808-3814` 的 "already" 判定与 `:3835-3840` 的 "同 task_id 全标 done"
  **都只按 task_id 匹配**。按契约 §6-2（`generateTaskID` 按子任务生成、同纳秒可能碰撞）推断 **task_id 是"每份一个"而非"每轮一个"**
  → 同轮 K 份的 task_id 各不相同 → 离线降级只标 done 自己那一份，**其余 K-1 份到期时各自再注入一次 total_x10
  → 整轮被注 K 次**（严重过量注油）。仅当网关把整轮 K 批塞进同一帧（K 个 task_info 元素）时才不会同时挂起。
- **离线分支缺忙判断**：在线分支 `:3776` 有 `if(task_object_list[3].task_status != 0) continue;`，
  离线分支**没有** → 离线降级可能在槽3 正跑时改写 `task_object_list[3].val/inject_id`，与在执行任务串台。
- 另注：`adj_period_sec` / `inj_ts` 两字段固件已解析入表但**未参与任何调度判断**（批间隔实际由网关的 exec_at 表达）。
- 待用户选方案（尚未动手）：A 回收 done 表项 / B 环形覆盖最旧 done 格 / C 改按 task_id 整轮入表。
