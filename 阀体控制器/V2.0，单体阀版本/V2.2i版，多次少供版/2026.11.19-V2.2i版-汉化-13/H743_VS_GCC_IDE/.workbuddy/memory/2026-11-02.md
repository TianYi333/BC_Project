## 方案 B：入站验签按 key 字典序规范化（2026-11-02，用户选定"B"）

### 背景（用户提问引出的核查）
用户问"task_info 数组内部顺序影响验签吗"，进一步要求"查看项目原本的签名校验，重点携带数组的，
签名校验需按照字典序排序的" → 核查发现**当前 `task_order` 入站验签与协议 §2.4.1 不一致**：
- 协议 V2.7 §2.4.1 明文：「提取消息中所有字段（排除sign）→ **按key字母顺序排序** → 构建JSON字符串 → HMAC-SHA256」。
- 固件实现（`net_comm_task.c:2167` 原）：`cJSON_Duplicate(task_info_arr, 1)` **原样保留报文里的键序**
  （`cJSON_Duplicate` 保留 `string`(key) 与解析顺序），→ 设备算出的签名串**依赖网关报文中键的书写顺序**，
  而非协议规定的字典序。**外层 5 键是手工字典序**（device_id→seq→task_info→ts→type，`:2170-2174`），
  但**内层 `task_info` 数组元素的键未排序**。

### 证据链（4 条，均已核验）
1. 协议 §2.4.1 明文要求字典序。
2. **仓库真实通讯记录 `d:/Desktop/R/工程/阀体控制器/通讯实例.txt`**：网关实际下发的 task_order 内层键序为
   `inj_id→inj_v→period_seq→remaining→sub_index→sub_total→sub_volume→task_id→task_type` = **严格字典序**；
   同文件记录的真实网关签名 `sign=4020F204`。
3. 项目自身出站报文（`state_response` / `task_request` / `execute_result`）一直是**全层级字典序**
   → 网关既须能验证这些含数组报文，其签名器必然同样支持嵌套排序。
4. 参考上位机 `mock_device.go` 的 `generateSign` 用 `sort.Strings` 排顶层键；
   `task_info` 为 `[]map[string]interface{}`，**Go 的 `json.Marshal` 自动按字典序输出每个 map 的键**。

### 改动（`UserCode/Drivers/ETH/net_comm_task.c` + `.h`，纯新增，未改任何既有行）
- **新增** `json_key_cmp()` / `json_sort_object_children()` / `json_sort_keys()`（置于 `tcp_parse_cmd` 之前）：
  - cJSON 官方**无排序接口** → 自行实现。cJSON 对象子节点是 `child`/`next`/`prev` **双向链表**，
    重排后必须同步维护 `prev`（否则 `cJSON_Delete` 遍历会漏释放）。
  - 对象键按 **`strcmp` 字节序**（区分大小写）**稳定插入排序** —— 与网关 Go 的 `sort.Strings`/`json.Marshal` 一致。
    ⚠️ 不可用 cJSON 内部的 `cJSON_strcasecmp`（那是大小写不敏感的，仅用于 `cJSON_GetObjectItem` 查表）。
  - **数组元素顺序不动**（元素先后有语义），仅递归元素内部的对象。
  - `node->type & 0xFF` 屏蔽 `cJSON_IsReference`/`cJSON_StringIsConst` 标志位。
- **新增** 宏 `JSON_SORT_MAX_ITEMS 32`（`net_comm_task.h:189`）：单对象最大键数上限，
  仅用于**栈上**临时数组（不占静态 RAM）；实际最内层对象约 10~16 键。
- **调用点**：`task_order` 分支 `cJSON_Duplicate` 之后、`cJSON_PrintUnformatted` 之前 → `json_sort_keys(arr_copy);`
- **影响面**：仅 `task_order`（**唯一含数组的入站分支**）；其余入站分支（`state_request`/`task_empty`/`stop_task`/
  `heartbeat_ack`/`device_reboot`/`upgrade`）为**手工拼串**、字段固定、无数组，行为完全不变。

### 验证（编译 EXIT=0）
- FLASH 360372 → **360972 B（+600 B）**；**RAM_D1 330240 B 不变**（排序数组在栈上）。
- Python 复刻「网关算法（Go sort.Strings + json.Marshal）」与「固件算法（cJSON + 字典序规范化）」交叉比对，**8 场景全过**：
  1. 真实帧：固件串 == 网关串（逐字节）
  2. **端到端密码学验证：固件算法算出的签名 == `通讯实例.txt` 记录的真实网关签名 `4020F204`**（含 remaining 那个变体）
     —— 同时证明两侧复刻均字节级精确
  3. 乱序帧：固件串 == 网关串（新行为对）；旧行为（不排序）签名不匹配 → **证实原缺陷客观存在**
  4. **回归**：真实帧（内层本已字典序）新旧行为结果完全一致 → 此前是「**碰巧对**」
  5. 数组元素顺序未被重排 / 6. 嵌套对象已递归排序 / 7. 重复 key 保持原相对顺序（cJSON `parse_object` 保留重复键）
  8. 单元素 task_info 排序幂等

  记录值 `4020F204` 对应的是**含 `remaining`** 的串 —— 故该文档的 Sorted 行是**手写示例、与实际签名串不一致**。
