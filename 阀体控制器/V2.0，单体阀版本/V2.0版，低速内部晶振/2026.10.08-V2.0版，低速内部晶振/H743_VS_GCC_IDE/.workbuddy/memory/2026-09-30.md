# 2026-09-30 工作日志

## RTC 不走时（LSE）启动流程诊断（仅分析，未改代码）

用户现象：RTC 使用外部低速晶振（LSE）时不走时，怀疑启动顺序。

### 代码真实现状
- `Core/Src/main.c:176` `SystemClock_Config` 的 `RCC_OscInitStruct.OscillatorType = RCC_OSCILLATORTYPE_LSI|RCC_OSCILLATORTYPE_HSE;`
  —— **根本没启用 LSE**（无 `RCC_OSCILLATORTYPE_LSE`，无 `LSEState = RCC_LSE_ON`）。
- `Core/Src/rtc.c:111` `HAL_RTC_MspInit` 中 `RTCClockSelection = RCC_RTCCLKSOURCE_LSI;`
  —— 当前 RTC 实际跑在 **LSI（内部 32kHz）**，不是 LSE。
- `.ioc` 中 `RCC.RTCFreq_Value=32000`（717行）对应 LSI，确认 CubeMX 配置就是 LSI。
- 全工程无 `HAL_PWR_EnableBkUpAccess` 调用（HAL 内部 896 行 SET_BIT(PWR->CR1,DBP) 自行处理，DBP 非问题根）。

### 与启动顺序的关系（核心结论）
- **是的，与顺序有关**，关键约束：**必须先启动 LSE（LSEON=1），再由 MSP 把 RTC 时钟源选为 LSE（RTCSEL=LSE）**。
- `HAL_RCCEx_PeriphCLKConfig`（rcc_ex.c:925-938）在 `RTCClockSelection==LSE` 时会 **等待 LSE ready（超时 RCC_LSE_TIMEOUT_VALUE）**；若 LSE 没启动，等待超时返回 `HAL_TIMEOUT` → `HAL_RTC_MspInit` 的 `!= HAL_OK` 分支触发 `Error_Handler()`（表现为 RTC 起不来/不走时甚至卡死）。
- 当前 main 调用顺序本身正确：`SystemClock_Config`(107行) 先于 `MX_RTC_Init`(122行)；问题是 `SystemClock_Config` 里**压根没启动 LSE**，违反了"LSE 先启动"这一条。
- 该函数在切换 RTCSEL 前若发现值变化，会 `__HAL_RCC_BACKUPRESET_FORCE/RELEASE`（918-919行）强制备份域复位——若重复初始化会清掉日历，正常启动只调一次无碍。

### 修复方向（待用户确认再动手）
1. `.ioc` 中 LSE 设为 "Crystal/Ceramic Resonator"，并将 RTC 时钟源选 LSE，重新生成（推荐，避免手动不一致）。
   或手动两处同步：
   - `SystemClock_Config` 的 `OscillatorType |= RCC_OSCILLATORTYPE_LSE`，加 `RCC_OscInitStruct.LSEState = RCC_LSE_ON;`（必要时配 LSEDriver 匹配负载电容）。
   - `HAL_RTC_MspInit` 将 `RCC_RTCCLKSOURCE_LSI` 改为 `RCC_RTCCLKSOURCE_LSE`。
2. 确保 LSE 启动在 MSP 之前（main 现有顺序已满足）。

## "选外部(LSE)就卡死" 根因坐实 + LSE 驱动等级问题（仅分析，未改代码）

用户确认：现在工程用 LSI，是因为**选 LSE 时程序会卡死**。

### 卡死链路（已逐行确认）
1. `.ioc` 选 LSE → 生成代码把 `RCC_OSCILLATORTYPE_LSE` 加进 `OscillatorType` 并设 `LSEState=RCC_LSE_ON`。
2. `HAL_RCC_OscConfig`（`stm32h7xx_hal_rcc.c:703-738`）：置 `PWR->CR1 DBP` → 置 `RCC->BDCR LSEON` →
   `while (LSERDY == 0) { if 超时 > RCC_LSE_TIMEOUT_VALUE return HAL_TIMEOUT; }`
3. `RCC_LSE_TIMEOUT_VALUE` = `LSE_STARTUP_TIMEOUT` = **5000 ms**（`Core/Inc/stm32h7xx_hal_conf.h:142`）。
4. 晶振起不来 → 5 秒后返回 `HAL_TIMEOUT` → `SystemClock_Config`(main.c:189-191) 判 `!=HAL_OK` → `Error_Handler()`
   （main.c:347-355）= `__disable_irq()` + `while(1)` → **固件在 scheduler 之前永久冻死**（无网络/串口/LED）。
   注：`RCC_DBP_TIMEOUT_VALUE=100U`（hal_rcc.h:8018）。

### LSE 驱动等级（Drive Capability）关键事实
- `__HAL_RCC_LSE_CONFIG(RCC_LSE_ON)` **只写 `RCC_BDCR_LSEON`，完全不碰 `LSEDRV`**（hal_rcc.h:7435+）。
  即 CubeMX 生成的 `HAL_RCC_OscConfig` **从不设置 LSE 驱动等级**。
- `RCC->BDCR` 复位值 = 0 → **`LSEDRV = 00 = Low`（默认最低驱动）**。故本工程 LSE 永远跑在 Low 档；
  若晶振需要更大驱动，必然起振失败 → 回到上面的卡死路径。
- 要改必须单独调 `__HAL_RCC_LSEDRIVE_CONFIG()`（= `MODIFY_REG(RCC->BDCR, RCC_BDCR_LSEDRV, ...)`），
  且**必须在 DBP=1 之后**（否则写 BDCR 无效）。
- **H7 驱动等级 erratum**：`hal_rcc.h:7743-7758` 被 `#if defined(RCC_VER_X)` 包住（`stm32h743xx.h:14409` 有定义），
  特殊分支是 `if (HAL_GetREVID() <= REV_ID_Y && (等级==MEDIUMLOW || 等级==MEDIUMHIGH))` → 取反写。
  即 **MEDIUMLOW/MEDIUMHIGH 在 rev ≤ Y 上映射异常**；**`RCC_LSEDRIVE_HIGH` 在两个分支里都是按字面写，任何 revision 都可靠**。
  → 想用最大驱动救弱晶振，**直接选 High**。
- 本板 CubeMX 报 **Product revision = rev.V**；HAL 定义 `REV_ID_Y=0x1003`、`REV_ID_V=0x2003`（hal.h:61/70），
  `0x2003 > 0x1003` → 不落入特殊分支，各档按字面生效。
- `RCC_LSEDRIVE_LOW/MEDIUMLOW/MEDIUMHIGH/HIGH` 定义见 `hal_rcc.h:714-717`。

### CubeMX 界面位置
- **"LSE Drive Capability" 只在 Low Speed Clock (LSE) 的 Mode 设为 "Crystal/Ceramic Resonator" 后才会出现**；
  当前 LSE 未启用（Mode=Disable），所以该参数被隐藏 —— 用户截图中的 RCC Parameters 列表里确实没有。
- 该 Mode 下拉框位于 RCC 面板**上方**（截图中 "Power Parameters" 之上被裁掉的部分）。
- 备选方案：不动 CubeMX，直接在 `SystemClock_Config` 的 `HAL_RCC_OscConfig` 之前手动
  `__HAL_RCC_PWR_CLK_ENABLE(); PWR->CR1 |= PWR_CR1_DBP; while(!(PWR->CR1&PWR_CR1_DBP)){}; __HAL_RCC_LSEDRIVE_CONFIG(RCC_LSEDRIVE_HIGH);`
  （可避开 CubeMX 重新生成对生成段的覆盖风险）。

### 待办
- 待用户确认：① 板子 PC14/PC15 是否有 32.768kHz 晶振（"没有"指选项还是指晶振，尚未澄清）；
  ② 是否要实施 Option C —— LSE 失败时**回退 LSI、不进 `Error_Handler` 死循环**，防量产变砖。

## 补充：CubeMX 里**确实没有** LSE Drive 选项（已证实，非用户漏看）

用户反馈：已把 `Low Speed Clock (LSE)` Mode 设为 `Crystal/Ceramic Resonator`，RCC 面板仍**没有** "LSE Drive Capability"。

### 决定性证据：H7 的 HAL 结构体里根本没有这个字段
- `RCC_OscInitTypeDef`（`hal_rcc.h:84-117`）成员仅：
  `OscillatorType / HSEState / LSEState / HSIState / HSICalibrationValue / LSIState / HSI48State / CSIState / CSICalibrationValue / PLL`
  —— **没有 `LSEDrive` 成员**。
- 对比：STM32L4 等系列的 `RCC_OscInitTypeDef` **有** `LSEDrive`，所以那边 CubeMX 有该选项；**H7 没有，故 CubeMX 无字段可填、UI 也就没有此项**。
- 结论：**H743 上 LSE 驱动等级只能手写代码设**，`RCC->BDCR.LSEDRV` 否则恒为复位值 `00 = Low`。

### ⚠️ 卡死其实有**两处** 5 秒 LSERDY 等待（不止一处）
1. `HAL_RCC_OscConfig`（`stm32h7xx_hal_rcc.c:703-738`）→ 失败返 `HAL_TIMEOUT` → `SystemClock_Config`(main.c:189) → `Error_Handler()`。
2. `HAL_RCCEx_PeriphCLKConfig`（`stm32h7xx_hal_rcc_ex.c:925-939`）在 `RTCClockSelection == RCC_RTCCLKSOURCE_LSE` 时**同样等 LSERDY、同样 `RCC_LSE_TIMEOUT_VALUE`(5s)** → 失败返 `HAL_TIMEOUT` → `HAL_RTC_MspInit`(rtc.c:112) → `Error_Handler()`。
   → LSE 起不来会**连卡两个机会**，防 brick 要同时处理这两处。

### 🔑 备份域复位规则（决定"动态切 RTC 源"不可行）
`hal_rcc_ex.c:912-922`：
```c
/* Reset the Backup domain only if the RTC Clock source selection is modified */
if ((RCC->BDCR & RCC_BDCR_RTCSEL) != (PeriphClkInit->RTCClockSelection & RCC_BDCR_RTCSEL)) {
    tmpreg = (RCC->BDCR & ~(RCC_BDCR_RTCSEL));
    __HAL_RCC_BACKUPRESET_FORCE(); __HAL_RCC_BACKUPRESET_RELEASE();
    RCC->BDCR = tmpreg;   // 保留 LSEON/LSEDRV 等，仅换 RTCSEL
}
```
- **仅当 RTCSEL 变化时才强制复位备份域**（会清 RTC 日历 → `RTC_ISR_INITS` 失效 → rtc.c 会重设时间）。
- 故**绝不要做"运行时 LSI↔LSE 动态切换"**：那样每次开机都不停在换源 → 每次复位备份域 → 日历被清。
- **RTC 时钟源必须在 `.ioc` 里定死**（本例定死 LSE）。
- 换源时 `tmpreg` 保留了 LSEON，所以源切换后 LSE 会重启（第 924 行注释即此意）。

### 其他确认到的环境事实
- `HAL_MspInit`（`stm32h7xx_hal_msp.c:63-79`）**只使能 SYSCFG**（70 行），**未使能 PWR 时钟**。
  故在 `HAL_Init()` 之后、`SystemClock_Config()` 之前要写 `PWR->CR1`，**必须先自己 `__HAL_RCC_PWR_CLK_ENABLE()`**。
- `main.c` 可用且**抗 CubeMX 重新生成**的插入点：`/* USER CODE BEGIN Init */`（102-104 行），
  正好在 `SystemClock_Config()`（107 行）之前、`HAL_Init()`（100 行）之后。
- CubeMX 本次已把 LSE Mode 改为 Crystal/Ceramic Resonator（尚未 Generate Code）。

### 方案（待用户选）
1. `main.c` USER CODE BEGIN Init 加"驱动=High"（抗重生成）——前提：板子**有**晶振。
2. 方案1 + 防 brick（需碰生成代码或 HAL，重新生成后要重贴）。
3. 维持 LSI ——若板子**无**晶振。
