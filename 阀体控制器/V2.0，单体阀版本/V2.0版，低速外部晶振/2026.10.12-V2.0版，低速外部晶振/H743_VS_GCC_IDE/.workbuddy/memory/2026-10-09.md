# 2026-10-09 工作日志

## RTC 掉电不保持（用户反复追问，本轮逐行钉死）

### 结论
RTC 掉电后时间不保留、上电回到默认 —— **根因在硬件 VBAT 未供上备份域，与程序无关**。

### 软件侧铁证（逐行）
- `Core/Src/rtc.c:65-69`：`MX_RTC_Init` 在 `INITS!=0` 时直接 return，不重写日历。
- `UserCode/Drivers/Clock/rtc_cluck.c`：所有 `SetTime/SetDate`（`UnixMs_To_RTC` L29 / `Unix_To_Time` L119）仅用户主动设时间时调用，启动流程无无条件写时间。
- 全工程唯一备份域复位路径：`HAL_RCCEx_PeriphCLKConfig` 内"RTCSEL 改变才清"（hal_rcc_ex.c:913），LSI→LSE 切换为一次性触发。

### CubeMX 生成代码的关键坑（INITS 陷阱）
- `HAL_RTC_Init`（hal_rtc.c:319）在 `INITS==0` 时进初始化模式并退出，硬件**置 INITS=1**。
- 因此 `rtc.c:65` 的 `if(INITS!=0) return` 永远成立 → **rtc.c:74-91 的 2025-01-01 默认时间段永不执行**。
- 实际每次上电日历被清成**硬件复位值 2000-01-01 00:00:00**（非 2025）。
- 反证：用户若看到 2000，即说明 INITS 每次都是 0 = 备份域每次断电都复位。

### 硬件根因（VBAT）
H7 的 RTC 日历+备份寄存器+LSE 全在备份域，仅由 VBAT 引脚供电。常见"加电池仍丢"：
① VBAT 被板子短接到 VDD（最常见）；② 电池没接 MCU 的 VBAT 脚；③ 电池电压<1.8V；④ 虚焊/未布线。
当前工程 RTC 源已切 LSE（10-08），LSE 也在备份域靠 VBAT 维持。

### 验证方法（未改代码）
- 方法1：设时间后按 NRST（不拔主电）看是否保留 → 保留则纯硬件 VBAT 问题。
- 方法2：看上电显示 2000 还是 2025（2000 印证 INITS 坑）。
- 方法3：断电10s 量 MCU VBAT 引脚对 GND，≈3V 正常，≈0V 实锤未供上。

### 可选改进（待用户确认，非根因）
把 `rtc.c:65` 的 INITS 判断改为备份寄存器判断（`HAL_RTCEx_BKUPRead(DR1)==0x32F2`），仅让"无电池时"显示合理默认，不解决保留问题（保留只能靠 VBAT）。用户尚未确认是否改。

## 用户实测反馈（10-09 下午，推翻"纯 VBAT"简单结论）
- 上电看到时间 = **2025**（非 2000）→ 铁证：每次启动都走了 `rtc.c:74-91` 默认分支，即 `MX_RTC_Init` 的 `INITS` 判断每次都失败（INITS 每次为 0）。
- 按 NRST 复位键 → 时间**不保留**。
- **修正上午判断**：之前说"INITS 坑导致 2025 永不执行"是错的——实测 2025 在执行。说明 INITS 每次都被清零。

### INITS 置位机制（已查 RTC_ExitInitMode @ hal_rtc.c:1980）
- `RTC_ExitInitMode` 仅清 `RTC_ISR_INIT` 位；**`INITS` 由硬件在"退出初始化模式"时自动置 1**（参考手册：INIT 从 1 变 0 时硬件置 INITS）。
- 故：`HAL_RTC_Init` 在 INITS==0 时进初始化模式并成功退出 → INITS 应被硬件置 1 → `MX_RTC_Init` line65 读到 1 → return，**不执行 2025 默认**。
- 实测每次走 2025 分支 → 说明 INITS 在 `MX_RTC_Init` 读之前已被清零 → **每次启动都发生了 BDRST（备份域复位）**。

### BDRST 触发条件（hal_rcc_ex.c:913）
- `__HAL_RCC_BACKUPRESET_FORCE/RELEASE` 仅在 `(RCC->BDCR & RTCSEL) != (请求 & RTCSEL)` 时触发。
- 若 BDCR.RTCSEL 每次都是默认(00)（备份域每次复位）→ 与请求 LSE(10) 不符 → **每次启动都 BDRST** → 每次清 INITS+日历 → 每次走 2025 默认。
- 若备份域正常保留（VBAT 正常或 NRST 时 VDD 在供）→ BDCR.RTCSEL 已是 LSE → 不 BDRST → 时间保留。

### NRST 反常（用户二次澄清：RST 引脚拉低 = 真·系统复位，VDD 不断）
- **更正上一条**：用户确认是 RST 引脚拉低（真 NRST），非 POR。故"按钮=POR"假设**错误**。
- **矛盾**：STM32H7 手册规定系统复位（NRST）不复位备份域；NRST 时 VDD 不断，备份域由 VDD 供，RTCSEL/INITS/日历应保留。但实测按 RST 后时间仍丢 → **反常**。
- **症状反推**：看到 2025 默认 → `MX_RTC_Init` line65 `if(INITS) return` 为假 → INITS 在 line65 前已被清 0 → BDRST 发生于 `HAL_RTC_Init`(line54) 内的 `HAL_RCCEx_PeriphCLKConfig`。
- BDRST 门控（hal_rcc_ex.c:913）`(RCC->BDCR.RTCSEL != 请求)` 为真才触发 → 说明**该 NRST 启动后 `RCC->BDCR.RTCSEL` 读到的是 0（默认），即 BDCR 没被保留成 LSE**。
- **两种可能**：
  ① **隐藏 VDD 跌落**：按 RST 瞬间板子有 brownout/POR（虽用户认为 VDD 不断，需示波器量 3.3V 轨确认是否真平整）。
  ② **软件 BDRST 每次触发**：`RCC->BDCR` 读到 0 的原因——可能是某条件下读返回默认，导致门控每次为真。需加诊断 LOG 确认。
- **决定性问题**：按 RST 时 MCU 的 3.3V 主电源轨是否真的保持平整（示波器量）；或加临时 LOG 在 `MX_RTC_Init` 入口打印 `RCC->BDCR`（RTCSEL/LSEON/RTCEN 位）与 `ISR.INITS` 原始值（改前需用户确认）。

### 下一步/待用户确认（硬件定位）
1. 电池**接在哪**：MCU 的 VBAT 专用脚？还是板上一处实际短接到 VDD 的焊盘/座？
2. 按按钮时量 MCU **VDD（3.3V 轨）**是否跌落至 0（确认按钮=POR）。
3. 断电 10s 量 MCU **VBAT 脚**对 GND 电压（≈3V 正常，≈0/<1.8V 实锤未供上）。
4. 若板子把 VBAT **硬短接到 VDD**：则电池必须改为"撑住 VDD"——电池+肖特基二极管接 3.3V 轨，主电掉时由电池保 VDD（备份域随之保电）。否则电池接到 VBAT 无效。
5. 因已切 LSE：32.768kHz 晶振也在备份域靠 VBAT 维持，VBAT 缺失则 LSE 停振，RTC 既丢日历也不走时。

### 软件修复方案（待用户确认，非万能）
1. `MX_RTC_Init` 判断改"INITS 或 BKUP_DR1 magic 任一为真则跳过 SetTime" + 首次设默认时写 `HAL_RTCEx_BKUPWrite(DR1,0x32F2)`。局限：BDRST 清整个备份域，BKUP 同被清，对"每次 BDRST"场景无效。
2. 避免 BDRST：在 `HAL_RTC_MspInit` 调 `HAL_RCCEx_PeriphCLKConfig` 前，先判 `RCC->BDCR & RTCSEL == LSE`？若是则跳过 RTC 时钟源配置（直接 `__HAL_RCC_RTC_ENABLE`）。仅对"NRST 也丢且 BDCR 不知为何默认"有效；对"断电丢（VBAT 没供）"无效。
3. **根治**：VBAT 正确供电（电池接 MCU VBAT 引脚且不被短接到 VDD）。软件改判断救不了断电丢。
