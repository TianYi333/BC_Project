## 根因定性：Q 电机"零点基准"易失，运行序列不自校准 → 重启才恢复
- 现象闭环：`test_running_callback`（运行序列）失败 `sen p1 g2 r2`（等 SEN_1 实际在 SEN_2 位）；
  `menu_item_unit_test` 单步却 `p1↔g1 / p2↔g2` 都能对上；**重启后运行序列恢复正常**。
- 代码实锤（关键）：
  - `injector_task()`（上电启动）在 `running_logic.c:75/80` 调 `zdt_run_motor_zero()`（命令 0x9A，电机自动归零/回零）→ **唯一**建立"校准零点"的地方，仅上电执行一次。
  - `zdt_set_motor_reset_zero()`（命令 0x93/0x88/0x01，"把当前位置设为零点"）在 `oled_page.c:391` 的 Q 电机初始化页按 ENCODER_PUSH 时调用 → 会**改写**零点基准（相对当前物理位置）。
  - `inject_running()`（运行序列）**开头不重新归零**，只发 `zdt_run_motor_loc_abs_t` 绝对角度命令（基于当前零点 + motor_loc_list[].deg）。
  - `start_running()`（上电 SYS_MODE_STARTING）也不调 0x9A，只 move 到 motor_loc_list[0] 并确认传感器。
- 结论：零点基准是"易失状态"。一旦被 `zdt_set_motor_reset_zero`（unit test 归零页）改写、或运行中位置误差累积，运行序列的绝对 deg 命令就落到错误物理点（deg180 本该是 SEN_1 位却落到 SEN_2 位），导致 `p1 g2`。
  **重启会重新执行上电 `zdt_run_motor_zero`（0x9A）重建校准零点 → 运行序列恢复**。这正是一直"重启就好"的根本原因。
- 为何 unit_test 单步能"对上"而运行序列"对不上"：unit test 的 Q 初始化页在用户操作时重新 `zdt_set_motor_reset_zero` 自校准了零点（故单步时 deg 与传感器对齐）；运行序列无此自校准，直接继承被改写的零点 → 失败。两条路径零点基准不一致。
  ⚠️ **【2026-11-04 已被用户纠正并作废】** 用户指出：`menu_item_unit_test()` **并不调用** `zdt_set_motor_reset_zero()`——该命令只在 "Q Model Init" 菜单页 `q_model_init_callback()`（oled_page.c:391）里调用。
  ⇒ **"unit test 自校准零点、运行序列不自校准"这一解释作废**；两条路径都用同一个电机零点基准。
- 修复方向（尚未改代码，待用户确认）：在 `inject_running` 开头（或 `start_running` 内）**重新执行 `zdt_run_motor_zero` 并复位 `q_model.point`/`dir` 到 motor_loc_list[0] 基线**，使运行序列不依赖残留零点/位置状态；同时评估 unit test 的 `zdt_set_motor_reset_zero` 是否应仅用于首次标定、避免污染运行零点。
- 旁证：绝对角度命令不依赖起始 `point`/`dir`（最终落点 = 表 deg + 当前零点），故问题纯粹在"零点基准"，与位置表/传感器逻辑无关——与"删 build 重编/改 PIPULLDOWN/改注释"都无关，之前几条猜测线均已排除。

## 推导："运行序列第一个开放位 = id2(deg180, pipe1)" 的完整代码依据
- 初始状态 `init_main_sys_state()`（var_init.c:90-92）：`q_model.point = motor_loc_list[0]`（id0/deg0/pipe2），`q_model.dir = 1`。
- 上电 `start_running()`（running_logic.c:261-385）结束时 Q 停在哪，取决于上电瞬间传感器读数三分支：
  - `Read_MET_Sensor()==0` → 先走 list[0] → `waiting_met_sen(pipe=2)` → 再走 list[1]（**id1/deg90/pipe0**，预备点）
  - `Read_MET_Sensor()==2`（==list[0].pipe）→ 直接走 list[1]（同上）
  - `Read_MET_Sensor()==1` → 走 list[3]（id3/deg270/pipe0）
  - ⇒ 3 个分支中 **2 个落在 id1**，1 个落在 id3。
- `inject_running()` 开头 `q_motor_run_close()`：point.pipe==0 → 走 else 分支直接 `return 1`，**Q 不动**。
- 循环内第一次 `q_motor_run_open()`：因 point.pipe==0 走 else 分支（running_logic.c:883）→ `open_idx = point.id + dir`。
  - 起点 id1 ⇒ open_idx = 1+1 = **2** → `motor_loc_list[2]` = **id2 / deg180 / pipe1** ✅（最常见情形）
  - 起点 id3 ⇒ open_idx = 3+1 = 4 → list[4] = id4/deg360/pipe2
- `q_motor_run_point()` 成功后执行 `q_model.point = point`（running_logic.c:750），所以紧随其后的 `waiting_met_sen(point.pipe)` 等的就是该位 pipe。
- 后续开放位序列（pipe!=0 分支 `open_idx = id + dir*2`，running_logic.c:855）：
  **id2 → id4 → id6 → id8 →（id8 处 dir=-1 反转）id6 → id4 → id2 → id4 …**，pipe 交替 1,2,1,2…
  中间位（奇数 id，pipe=0）为关闭位，循环内不经过；`q_motor_run_close()` 才会去。
- 表中 6 个开放位：id0(deg0,pipe2，仅上电定位用)、id2(deg180,pipe1)、id4(deg360,pipe2)、id6(deg540,pipe1)、id8(deg720,pipe2)、id10(deg900,pipe1，**不可达**，dir 在 id8 即反转)。
- **可自检的推论**：失败后 Q 停在 deg180（point=id2/pipe1）；若不重启直接再跑一次注油，`q_motor_run_close()` 会走到 id3(deg270)，下一个开放位变成 **id4/deg360/p=2** → 错误码应从 p1 变为 p2。若仍显示 p1，说明每次都是重新上电后的首次运行（起点 id1）。

  ⇒ 故障根因锁定在**电机侧的多圈计数/零点状态**：断电后电机丢状态导致绝对角度（0xFD 多圈）命令基准改变；
    而软件重启保留了电机状态 → 一切正常。`zdt_run_motor_zero`(0x9A) 是**单圈归零/触发回零**，并不能恢复多圈计数基准。
- 对应代码：`zdt_run_motor_loc_abs_t()`（running_logic.c:746 使用）发的是 **0xFD 多圈位置模式**（buffer[0]=0xFD, buffer[1]=0x00, buffer[2]=0x02），
  位置值 = `(loc*rate*10)/256`、`(loc*rate*10)%256`（loc=deg，rate=1）→ 走的是**多圈绝对位置**，依赖电机端保留的多圈计数；
  而 `zdt_run_motor_loc_abs()`（0xFB 单圈）并未被 Q 电机使用。**P 电机也用 `_t`(0xFD)**（running_logic.c:711）。

## 关键重构：差异不在"两条路径"，而在"两种断电方式"（2026-11-04 上午 2nd）
- 用户新事实：①**交换两个传感器物理位置后仍对不上**；②**多次断电重启无效**；③**最后一次软件重启（reboot_system→NVIC_SystemReset）后突然正常**。
- ⚠️ 重要修正：`menu_item_unit_test()` **不调** `zdt_set_motor_reset_zero()`（该命令只在 `q_model_init_callback`=Q Model Init 菜单页 oled_page.c:391 调用）。
  ⇒ **"unit test 自校准零点、运行序列不自校准"解释作废**；两条路径用的是同一个电机零点基准。
  ⇒ 进一步：**unit test 的"能对上"与 run sequence 的"对不上"很可能是两次不同供电状态下的观测**（unit test 可能在软件重启后的"正常态"测的，
  run sequence 失败是在断电后的"异常态"测的）→ 二者并非同一状态下的对比，该对比可能不成立。
- **决定性推理**：断电重启 vs 软件重启，**MCU 侧 RAM 与 Flash 状态完全相同**（两者都清 RAM、Flash 都保留）；
  唯一差别是**电机驱动器(ZDT Emm42)是否掉电**。故状态差异只可能存在于**电机内部**（单圈零点 / 多圈计数 / 上电初始位置）。
  ⇒ 根因锁定：**电机的角度参考（0x93 设置的单圈零点、0xFD 依赖的多圈计数）在断电后未被可靠重建**；
  `zdt_run_motor_zero`(0x9A) 每次上电都执行，但两种重启结果不同 ⇒ **0x9A 并不能恢复那个关键状态**（仓库无法确认 0x9A 精确语义，实验不依赖它）。
- **决定性实验（不改代码、约 1 分钟）**：
  1) 当前（软件重启后的正常态）跑 unit test → 确认映射全 OK；
  2) **断电重启** → 立刻跑 unit test，看状态栏 id/p/g 是否变成 **NG / g2**；
     · 若 unit test 也变成 NG ⇒ 现象完全由"供电状态"决定，两条路径等价，根因=电机侧参考丢失；
     · 若 unit test 仍全 OK ⇒ 才轮到查运行序列自身的走位历史。
  3) 结论指向后，修复方向 = **每次上电做"传感器自校准"**：找到 SEN_2 触发位（= 表中 deg0 位置，pipe 图案周期 360°，360° 误差无害）→ 调
     `zdt_set_motor_reset_zero`(0x93) 把电机零点锚定到该物理位 → 断电后也能自恢复。
- 顺带发现的两个**真实代码缺陷**（待用户确认后修）：

## 已实施修复：两个真实代码缺陷（方案 A，用户确认后落地）

  - 依据：`waiting_met_sen` 返回 1成功/2非法/3两秒队列超时/4系统总超时/5未知；`> 0` 会把 3/4/5 全当成功 → 上电"阀芯传感器到位确认"实为空检查，

- **缺陷②**（归零失败不阻断启动）：新增全局标志 `g_q_zero_ready` / `g_p_zero_ready`（running_logic.c 定义，running_logic.h 声明 extern）。

## 根因定性（2026-11-04 下午）：零点基准被"手动置零"标歪 180°（p1 g2 的真正机制）
- 用户纠正：操作的是 **q_model_init_callback（Q Model Init）**，不是 P Model Init（我"方向搞错"的结论作废）。
- 用户现象链：一直失败 → 用 Q Model Init 手动置零 → **仍然失败** → 再**重启** → **正常**。
- 两种置零命令的握手差异（代码实锤，`motor_zdt.c`）：
  - `zdt_run_motor_zero` = **`0x9A`**：两段式握手——先收 `buffer[1]==0x02`（开始），再收 `buffer[1]==0x9F`（到达/完成，超时 5s）→ **电机执行了归零动作**。
  - `zdt_set_motor_reset_zero` = **`0x93/0x88/0x01`**：单段握手——只收 `buffer[1]==0x02`（超时 1.5s）→ **电机原地不动**，仅把"当前位置"标记为 0。
  - ⇒ 两者建立**两套不同基准**：0x9A 落在驱动器**规范基准点**（可复现）；0x93 落在**用户按下那一刻的物理位置**。
  - ⇒ **0x9A 能覆盖/撤销 0x93 的错误标记，0x93 无法修正 0x93 自己标歪的基准** → 解释"手动置零没用、重启才行"。
- **"p1 g2" = 恰好 180° 半周期错位**（位置表 pipe 图案周期 360°：`init_Q_motor_loc_list()` var_init.c:143-181，pipe2 在 deg0/360/720，pipe1 在 deg180/540/900）。
  - 错位 180° ⇒ 表里期望 pipe1 的位置落到物理 pipe2 位 ⇒ 读数恰为 `p1 g2`（期望 SEN_1、实测 SEN_2）。
  - 360° 整倍数错位则**无害**（pipe 图案周期 360°，表能自洽映射）。
- ⇒ **手动置零正确操作**：必须把阀芯停在 **SEN_2（pipe2）触发位**再按 PUSH；若停在 SEN_1 位按 PUSH，必然引入 180° 错位 → 永久 p1 g2。
  - 旁证：重启后正常 ⇒ `0x9A` 归零落点必然是 **pipe2 位**。
- 附带缺陷：`q_model_init_callback` 手动置零成功后**未复位** `main_sys_status.q_model.point` / `dir` 到基线（`motor_loc_list[0]` / dir=1）。
- 待实施修复（已向用户提方案，待确认）：`q_model_init_callback` 执行 0x93 **之前**校验 `Read_MET_Sensor()==2`（SEN_2），否则拒绝并提示；成功后复位 point/dir。
