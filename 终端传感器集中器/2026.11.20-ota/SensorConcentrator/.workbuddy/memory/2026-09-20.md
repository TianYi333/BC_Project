## 核查：把 SH_DEBUG_UART_ID 改成 0 后 CH1(UART7) 能否恢复（结论：功能能，但不能只改宏）
- 读码确认：**所有**调试口特判都在 `#if SH_DEBUG_UART_ID` 内 → 宏=0 时整段不编译，CH1 与其余 7 路同构：
  `SensorHub_Init`（sensor_hub.c:420-423 不再 continue → 置 DE=0 + `sh_start_rx`）、`HAL_UART_ErrorCallback`（323-326 不再忽略）、`SensorHub_BootProbeModes`（589-594 不再 skip）、`SensorHub_Query`/`WriteReg`（770/804 不再返回 -2）、`LOG_SH` 帧打印。硬件侧无遗留：`MX_UART7_Init` 115200 8N1、NVIC `UART7_IRQn` 已使能、`UART7_IRQHandler→HAL_UART_IRQHandler(&huart7)`、MSP 里 PF6 上拉(usart.c:491-492) 全部无条件。
- ⚠️ **3 处编译期遗留会导致链接失败**（实测：用 build/Debug/compile_commands.json 真实参数单编，`-DSH_DEBUG_UART_ID=0` 时 `debug_uart.o` 不再导出 `DebugUart_*` / `_write_r` / `__io_putchar`，而这 3 个 TU 仍对其有未定义引用 U）：
  1. `Core/Src/main.c:122` `DebugUart_Init();`（USER CODE BEGIN 2，无保护）
  2. `Core/Src/stm32f7xx_it.c` `Fault_Dump()` → `DebugUart_Panic` / `DebugUart_PanicHex`（异常 dump，无保护）
  3. `UserCode/Drivers/flash/fal_flash_stm32f7_port.c:225 / 316 / 369` 同上（无保护）
- ⚠️ 另一副作用：`debug_uart.c` 是 `_write_r()`（newlib-nano 下 printf/所有 LOG_* 的真正出口，见跨项目踩坑）**唯一强定义**。宏=0 → 全部日志（含 FAL/OTA/网络/HardFault dump）消失，且 printf 会退回 newlib 默认 `_write_r()`→`syscalls.c` 的 weak `_write()`→未定义的弱 `__io_putchar`（既有坑：完全无输出/可能跳空指针）。
- 待用户选方案：**A**（推荐）`debug_uart.c` 加 `#else` 空桩（Init/Flush/DumpHex/Panic/PanicHex 全空）+ 把 `_write_r()` 移出 `#if` 作丢弃型空实现 → 调用方零改动；**B** 把 3 个文件的调用点各自用 `#if SH_DEBUG_UART_ID` 包起来（改动多，日后开关需同步）。
- **用户决定（2026-09-20）：暂不改，只留结论**。即当前 `SH_DEBUG_UART_ID` 仍为 1（CH1=UART7 被调试口占用），代码未做任何改动；后续真要放掉 CH1 时按上面 A/B 之一配套改，否则链接会失败且日志全丢。
  - 追加事实：`LOG_SH` / `LOG_Debug` / `LOG_logic`（`UserCode/Logic/project_config.h:30/38/46`）**均无条件展开为 printf**，不随 `SH_DEBUG_UART_ID` 变化 → 关调试口后这些调用仍存在，只是没有出口，故方案A 的 `#else` 分支里**必须**保留一个丢弃型 `_write_r()` 强定义。
  - 用户又问"后续要关调试口、恢复 CH1 采集该怎么操作"→ 已给出 5 步清单：①`debug_uart.c` 补 `#else` 空桩(5 个 DebugUart_* + `_write_r`，需 `#include <sys/types.h>`/`<sys/reent.h>`) ②`sensor_hub.h:78` 宏翻 0 ③重新构建 ④烧录 App ⑤上电核对（`S1 boot mode=` 出现、无 `boot probe skip (debug port)`、心跳 `sensor_online[0]`、单路 sensor_read）；回退只需把宏改回 1（两条分支互不干扰）。

## 新增逻辑：alarm_type=2（通讯丢失）时清零该路暂存数据
- 需求（用户）：通道 `alarm_type=2` 时，"将通道暂存的数据变为 0"。
- 落点（单一、覆盖所有路径）：`sensor_hub.c::sensor_alarm_eval()`（sensor_hub.c:79 起）。该函数在 `sensor_cache_update` / `SensorHub_GetCached` / `SensorHub_GetOnlineMask` / `SensorHub_EvalAlarms` 四个入口都会被调用，故清零逻辑一处即覆盖周期检测、查询、心跳在线判断。
- 范围（用户选定"测值+标志"）：`alarm==2` 时清 `e->data.temperature=0` / `e->data.voltage_flag=0` / `e->data.temp_flag=0`，并复位 `e->vflag_watch=0` / `e->vflag_rise_tick=0`。**刻意保留** `sensor_id`(上报必需) / `mode`(后续 30s 判据还要用它) / `alarm_type`(本次触发条件) / `last_data_tick`+`boot_fail`+`has_data`(维持"已丢失"状态直到新帧)。不清 `has_data` → 网关 query 仍得 `ok=1` 但 temperature=0，配合 alarm_type=2 表达"已丢失且数据清零"。
- 安全性核验：`sensor_cache_update()` 收到新有效帧后会先 `e->data=*sd`（真值）再调 eval，此时 last_data_tick=now、boot_fail=0、has_data=1 → 不会被判 2，真值不被误清；恢复通道走正常路径即可取回真实数据。
- 构建：`cmake --build build/Debug` EXIT=0，`[2/2] Linking ... Building BIN`，无 error；FLASH 210892B（较此前 205236B 略增，属正常）。
