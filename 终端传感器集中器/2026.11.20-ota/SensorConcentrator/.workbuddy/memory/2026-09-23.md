# 2026-09-23 工作日志

## 修复 mode 写后读回 FAIL(-3) + 调试口串口脏数据

### 现象
- `[NET:370] mode_set S3 write ok, readback FAIL(-3), fallback to requested`
- 调试口(CH1/UART7)串口出现大量二进制乱码（"靠靠靠靠"）。

### 根因与修复
1. **读回 -3（确定性 bug）**：`sh_read_resp_match()` 在 FC03 读应答匹配里多了一段错误判断
   `buf[2]==(r->reg>>8) && buf[3]==(r->reg&0xFF)`，但 FC03 应答帧 `buf[2]` 是字节计数(=0x02)而非寄存器高字节，
   导致匹配器**永远不命中** → 读信号量永不释放 → 必 -3。已删除该判断，仅保留 `sh_fc03_resp_match`（校验 addr/func/字节数/CRC）。
2. **写后需延时（用户指出）**：`SensorHub_WriteReg` 只等 FC06 写回显，回显一到即发 FC03 读，从机改 mode 处理中易丢弃读请求。
   新增 `SH_MODE_READBACK_DELAY_MS=30`，在 `SensorHub_ReadModeBack()` 发读前 `vTaskDelay(30ms)`。
3. **串口乱码**：固件唯一往 huart7 发数据的 `debug_uart.c` 只发文本/十六进制，从不发二进制 → 乱码非 printf 产生，
   是 RS485 总线上的原始字节（空闲总线噪声 / 或 8 路共用总线时的其它传感器帧）。
   将调试口改为 **DE 常置发送态**（TX-only 控制台，初始化即 DE=1，发送后不再拉低），消除空闲噪声。

### 改动文件
- `UserCode/Drivers/RS485/sensor_hub.h`：新增 `SH_MODE_READBACK_DELAY_MS=30`。
- `UserCode/Drivers/RS485/sensor_hub.c`：`sh_read_resp_match` 删错误判断；`SensorHub_ReadModeBack` 加写后延时。
- `UserCode/Drivers/RS485/debug_uart.c`：调试口 DE 常置发送态（init + debug_uart_send + Panic/PanicHex 去掉拉低）。

### 验证 / 注意
- `cmake --build build/Debug` → 149/149，bin 211628B，0 error，无相关告警；`SensorHub_ReadModeBack/ReadReg/sh_read_resp_match/g_rd_sync` 均编入 ELF。
- **安全性**：`debug_uart.c` 整套 DE 逻辑在 `#if SH_DEBUG_UART_ID` 内；`DEBUG_UART_ENABLE=0` 时该代码不编译，CH1 的 DE 完全由 `sensor_hub.c` 按传感器路控制 → **不影响关闭调试后的正常采集通讯**。
- 若乱码属"8 路共用一条 RS485 总线"，则固件无法消除（调试口会看到所有传感器二进制帧），需调试口改接独立干净链路。

## 09-23 后续：脏数据根因纠正 + 读回加重试

### 用户纠正（关键）
- CH1 调试口是**独占、不接传感器**的 RS485 线；且 DE 常置发送态**之前**就有大量脏数据。
- ⇒ 脏数据**既非传感器对打、也非 485 收发切换**（当前 debug_uart.c 的 DE 是常置、根本不切换，乱码反而更多在旧版也存在）。
- 真因是这条独占线本身的**硬件问题**：无终端/偏置电阻 → 悬浮振铃，或 USB-RS485 转接板噪声。固件改 DE 救不了。

### 方案调整
- **(A) 不做"回退 DE"**：原拟把 DE 改回"发完拉低回接收态"（DE=0 空闲），但独占线上 DE=0 会让空闲线悬浮、噪声回来；DE 常置发送态(=1)才是更优，保持现状（已在 09-23 早些时候落地）。
- **(B) 读回加重试（已落地）**：
  - `sensor_hub.h`：`SH_MODE_READBACK_DELAY_MS` 30→**150**；新增 `SH_MODE_READBACK_RETRY=3`、`SH_MODE_READBACK_GAP_MS=50`。
  - `sensor_hub.c`：`SensorHub_ReadReg` 整体包进重试循环（发 FC03→等应答；超时 -3 / CRC 错 -4 时隔 50ms 重发，最多 3 次；发送失败 -1 直接退出不重试）。
  - 最坏阻塞：ReadModeBack 150ms 预延时 + 3×500ms ≈ 1.65s（mode_set 偶发命令可接受）。

### 验证
- `cmake --build build/Debug` → 0 error，bin 211940B；`SensorHub_ReadReg/ReadModeBack` 符号在，无 sensor_hub.c 告警。
- 脏数据残留为硬件问题，建议：CH1 连接器端加 120Ω 终端 + 偏置电阻，或换质量更好的 USB-RS485 转接板/查 USB 接地环路。

## 09-23 纠正：脏数据真因 = Flash 升级/启动坏状态（非电气噪声、非 485 切换）

### 用户最终定位（权威结论）
- **整片擦除 Flash + 重新下载后，调试口脏数据完全消失** → 证明脏数据（"靠靠"/"?"/"厘 Q?"）**不是**电气噪声、也不是 485 收发切换。
- 真因：**之前一次升级/启动失败，导致 Flash 处于坏状态**（App 镜像损坏或启动配置错乱），MCU 跑的不是正常代码 → 在调试 UART 吐乱码。
- 连带说明：之前看到的 OTA meta 脏值 `0xDCF563DF` 也是同一坏 Flash 状态的产物，整片擦除后一并消失。

### ⚠️ 反思（避免再误诊）
- 之前把脏数据归因为"CH1 独占线电气噪声 / 需终端偏置电阻"是**错误方向**。当看到"整片擦除后正常"时，应优先怀疑 Flash/固件状态而非硬件。
- 排查串口乱码时，若乱码夹在 printf 正常文本**之间**（如 `厘 Q?183]`），且 DE 已确认常置高、UART7 无硬件 DE，应怀疑是 MCU 在跑异常代码（镜像损坏/跑飞），而不是总线噪声。

### 后续可加固（用户未要求，待定）
- Bootloader 跳转 App 前**校验 App 镜像有效性**（合法栈顶指针落在 RAM 区 + 可选 CRC/签名），损坏则不下跳、留在安全态并报错，避免"跑飞吐乱码"这种难诊断状态。

## 09-23 追问：ota_meta 为何"每次上电都读错、只能整片擦除才好"

### 结论（排查两端代码后）
- **meta 脏值是"症状"不是"病因"**；FAL 分区/地址/sanitize 逻辑经核对均正确（ota_meta@0x08090000 S16 SNB=20，读写同一物理地址，sanitize 写回合法 NONE 且上报成功）。
- 真因 = **一次失败的 OTA 升级把 Bank2 App 镜像写坏/写残**：坏 App 跑飞 → 既吐脏串口数据（用户之前看到的"靠靠/?"），又会把垃圾写进 ota_meta；于是每启动重读脏 meta、重入坏状态，直到整片擦除+干净重下。
- 当前版（用户重下的这版）两端自愈**已逐行坐实正确且健壮**（修正上一版"旧 Bootloader 复写"假设——用户澄清重下时就是同时烧当前版 Boot+App）：
  - SNB 机制：App `ram_flash_erase_sector` 与 Boot `write_meta` 均**绕过 HAL**、直接写 `FLASH->CR.SNB=20`（Bank2 S16 寄存器值，不含 HAL 的 +4 陷阱），正确命中 S16；不会擦错扇区/错地址。
  - 擦/写均检查 `FLASH_ERR_FLAGS`（WRPERR/PGPERR 等），写保护会返回 -1（非假成功），sanitize 会打 FAIL 而非假成功。
  - Boot `main_boot.c:404` 无 magic→双 Bank 下 `write_meta(clean NONE)`；App `ota_app_confirm` 脏→`ota_meta_sanitize()` 写 NONE。
  - ⇒ **当前代码不会循环脏**；今后即便 meta 意外变脏，上电即自愈。
- 用户澄清：重下时就是同时烧录当前版 Bootloader + App → **排除"旧 Bootloader 复写脏 meta"假设**。
- **最终根因**：重下之前那块板的脏状态是**旧固件（无自愈）时期**一次失败/异常 OTA 产生的——旧固件不修正脏 meta，坏 App 还反复把垃圾写回 S16 → 每启动都脏的死循环，只有整片擦除打破。重下当前版后已正常，且当前版自愈已根除复发。

### 处置建议
- 当前版已自愈，无需改代码。防复发验证：当前版板子若从脏状态首次启动，Boot 日志应出现 `[BOOT] sanitize dirty meta -> NONE`（自愈生效实证）；之后不再出现。
- 唯一仍可能"每启动脏、仅整擦才好"的硬场景：**S16 被选项字节设为写保护(WRP)** → 自愈 erase 返回 -1、NONE 写不进；此时需整片擦除+重设选项字节（正常烧录不动 WRP，一般不会触发）。
- 防砖加固（待用户定）：OTA FAILED / firmware_a CRC 未过**不覆盖现有好 App**；或烧前先校验 firmware_a 完整性，避免把残缺镜像烧进 App 区。

## 09-23 追加排查：用户假设"掉电数据侵占覆盖 ota_meta"——结论：排除

### 假设
- 用户：「ota_meta 每次上电都脏、整片擦除才好，会不会是掉电时别处(A 区/KV)的数据写到 ota_meta 地址、把其侵占覆盖了？」

### 代码实测（排除）
- FAL 分区连续不重叠（fal_cfg.h:69-71）：`firmware_a[0,384K]` / `ef_kvdb1[384K,64K]` / `ota_meta[448K,64K]`，边界无缝、无重叠；fal_partition.c:142 `check_and_update_part_cache` 还会校验 offset<dev->len。
- firmware_a 接收有严格越界保护（ota.c:67-91）：`g_ota_off+len > g_ota_exp_len` 或 `> OTA_FW_PART_SIZE(384K)` 直接 return -1；且 upgrade_start 已校验 new_len<=384K。故固件数据不可能越过 0x08080000 侵占 KV/meta。
- Flash 物理特性：编程按地址原子（64-bit 双字），掉电最多损坏正在写的那个双字/扇区，**不会把数据"搬移/侵占"到相邻地址**；相邻地址的既有数据不会被覆盖。
- OTA 掉电安全：do_update 先校验 firmware_a CRC 再 burn_app（main_boot.c:318），校验不过设 FAILED 不烧 → 不会把残缺镜像覆盖好 App（无备份但 CRC 守卫）。

### 唯一布局脆弱点（理论风险，当前配置安全）
- ef_kvdb1 与 ota_meta **物理相邻**（0x08090000 边界）。当前 KVDB 配 4×16KB=64KB 正好不越界；若日后改 KVDB 配置增大扇区数/扇区尺寸则会覆盖 meta。注意：FAL 仅在**设备级**(dev.len=512K)做边界检查、不在**分区级**，故 KVDB 越界 FAL 不拦。

### 结论
- "掉电数据侵占覆盖 ota_meta" 在当前设计与配置下**不会发生**；本次脏值是旧固件无自愈 + 一次失败 OTA 写坏 App/meta 的死循环（坏 App 主动反复写脏 meta，现象像侵占但本质是被坏代码覆盖，非掉电/布局错）。
- 可选加固（待用户定）：在 FAL/KVDB 初始化时加一道"ef_kvdb1.end == ota_meta.start"断言或预留 1 个保护扇区，杜绝未来 KVDB 配置越界误伤 meta。
