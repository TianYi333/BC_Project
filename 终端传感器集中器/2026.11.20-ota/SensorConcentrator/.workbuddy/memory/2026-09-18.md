## 签名源串与 JSON_Sign_Tool.html 对齐（规范化 helper）
- 根因：HTML 工具对该 JSON 递归按 key 的 ASCII 字典序排序后再做 HMAC；而 C 端 cJSON 按字段添加顺序序列化，不会自动排序。`sensor_data_all` 数组元素手写顺序错（关键：下划线 `_`(0x5F) 小于字母，故 `temp_flag` 必须排在 `temperature` 之前），导致签名不一致。实测：C 端旧逻辑 sign=43BF6F63 vs 工具 71D56A4A。
- 修复：新增 `cjson_sort_recursive()` + `cjson_sort_object()`（递归排序 object 内 key、数组元素顺序不变，仅重排 sibling 链表、不增删节点），在 6 个"以 `cJSON_PrintUnformatted(root)` 为 HMAC 源串"的发送函数（sensor_data / sensor_data_all / mode_set_resp / device_reboot_ack / upgrade_start_ack / reboot_result）的源串打印前调用。
- 未动 `device_online` / `discover_response` / `register` 等 A 类函数——它们原本就用"手写字典序 sign_buf"算 HMAC，发出的 JSON 即便乱序，网关/工具排序后验签仍等价，**已与工具一致且绝不能改**（否则网关验不过）。
- 验证：Python 离线模拟（对添加顺序 JSON 递归 sort_keys 后 HMAC）= 71D56A4A，与 HTML 工具完全一致；旧未排序=43BF6F63 不一致。`cmake --build build/Debug` EXIT=0，仅既有 g_sensor_ack_status 未用告警。
- 提示：网关验签端必须同样"递归字典序排序后 HMAC"；排查时用 HTML 工具把集中器实际发出的 JSON（串口/日志里的 `Send ...`）原样贴入，工具算出的 sign 应等于报文自带 sign。

## 通讯丢失口径修正（方案A）+ 故障消除确认
- 现象：全量 `sensor_data_all` 里未接传感器的通道 `mode` 全为 0(问答模式)，上电 30s+ 仍 `alarm_type=0`。根因：`sensor_alarm_eval` 的通讯丢失(2)原条件 `e->has_data && e->data.mode==1 && 30s无帧` 有双重闸门——(1)要求 `mode==1`(主动上报)，而 8 路全为 0；(2)要求 `has_data==1`(曾收到数据)，未接通道从未收到故 has_data=0。两者皆不通 → 不报。
- 用户确认方案A：**任何通道 30s 无数据即判通讯丢失**，去掉 `mode==1` 与 `has_data` 双重限制。新条件：`(e->has_data && now-last_data_tick>=30000) || (!e->has_data && now>=30000)`（now=HAL_GetTick()）。即"曾通讯后失联"或"上电30s从未收到帧"都判 alarm=2。`last_data_tick` 启动=0，故 now>=30000 天然实现"上电30s窗口"，无启动误报。
- 故障消除（用户追加要求）：alarm_type=1 后若后续某帧 `voltage_flag==0`，`sensor_cache_update` 的 `else if(sd->voltage_flag==0) e->vflag_watch=0` 立即清监视窗，`sensor_alarm_eval` 见 vflag_watch=0 跳过故障分支→alarm 归 0 写回。该行为**原已具备**，无需改代码；在 sensor_read 读取与 SensorHub_EvalAlarms 周期评估中均为实时重算、状态一致。
- 构建：`cmake --build build/Debug`(ninja) EXIT=0，`[149/149] Linking ... SensorConcentrator.bin` 无 error/FAILED。

## 🔴 OTA 根因坐实：FLASH_CR.SNB "扇区号+4" 约定是错的（Bank2 擦除全部打偏）
- 现象（用户 2026-09-18）：① 每次重启 App 都打印脏 meta（`magic=0xFEFFFBDF / 0xDEFFFBDF state≈0xDFFFBFEF`，即"几乎全 1、零星几个 0"）→ `[OTA:380] -> sanitize NONE`；② **只有整片全擦后才能升级**，之后既不能升级、meta 也一直是脏的。
- 权威依据：ST 官方培训文档《STM32F7 Memory_Flash》给出 **1MB 双 Bank 扇区表**：Bank1=0x08000000 起 S0~S3(16K)、S4(64K)、S5~S7(128K)；**Bank2=0x08080000 起 S12~S15(16K)、S16(64K)、S17~S19(128K)**。即 **Bank2 扇区号就是 12~19，SNB 直接填扇区号**。本工程 HAL 也印证：`stm32f7xx_hal_flash_ex.c:699 FLASH_Erase_Sector()` = `FLASH_CR_SER | (Sector << FLASH_CR_SNB_Pos)`，**没有任何 +4**；`FLASH_CR_SNB` 为 5bit(bits7:3, 0xF8)。
- 工程里却按 "Bank2 SNB = 扇区号 + 4"：`fal_flash_stm32f7_port.c` 的 `tbl[11]` 填 16~19/20/21~23（并注释"是 HAL 的 +4 规则"）、Boot `main_boot.c` `bf_erase_sector(20)`（meta）、`app_snb[3]={21,22,23}`（App 区）、`ota_common.h`/`fal_cfg.h` 注释均如此。**根因 = 这个臆造的 +4。**
- 后果（完全解释两个现象）：
  1. **meta 擦除(SNB20)/App 区擦除(SNB21~23) 打到不存在的扇区 → 擦除是空操作**；而驱动 `ram_flash_erase_sector` 只看 BSY+错误标志、**不校验 EOP、也不回读**，空操作被当成功(返回0) → meta 扇区**永远没被擦**。首次写入（芯片全擦后为空）能落，之后再写就是"往非空扇区编程" → F7 只允许 1→0，编程失败/PGPERR → 位上留下**零星 0、其余全 1 的残留**（= 看到的脏 magic，每次尝试结果略不同）→ 永远存不下 PENDING → 升级失败。**"只有全擦后能升级"正是因为那时候目标区本来就是空的。**
  2. **ef_kvdb1 的擦除(SNB16~19) 实际打在 S16(0x08090000=ota_meta) + S17/S18/S19(0x080A0000~0x080FFFFF = App 自身！)**。`FlashDB format_sector()`(fdb_kvdb.c:776) **无条件先擦**，KVDB 首次 format/以后 GC 都会触发 → 目前靠"KVDB 数据区在整片擦后本来就是空的、且负载极小还没到 GC"侥幸没炸，**但这是潜伏的一擦就砖**（擦到 0x080A0000 时 CPU 正从该区取指）。也解释了"meta 曾被莫名其妙擦过一次"。
- 附带确认缺陷：`fal_partition_erase()` 返回的是驱动返回值(成功=0)，而 `ota.c` 两处判错写成 `er != OTA_META_SIZE` → **每次成功擦除都会误报** `ota: meta erase fail ret=0` / `ota: sanitize FAIL erase=0 write=32`，把真正的失败线索掩盖了。`fal_partition_write()` 返回写入字节数(驱动已修)，故 `wr != sizeof(meta)` 判断是对的。
- 待用户确认后修：① `fal_flash_stm32f7_port.c` tbl 的 Bank2 SNB 改 12/13/14/15/16/17/18/19（Bank1 5/6/7 不动）；② Boot `main_boot.c`：meta 擦除 20→16、`app_snb` {21,22,23}→{17,18,19}、文案同步；③ `ota.c` 两处 `er != OTA_META_SIZE` → `er < 0`；④ 清掉所有 "+4" 注释；  ⑤（建议）擦除后回读校验 0xFF、编程后回读比对，让"静默空操作"再也不能冒充成功。

### 🔴 心跳改动引入的回归：sensor_read 签名源串 snprintf 被误删（同日已修）
- 现象：加完心跳后**全量/单路 sensor_read 全部不回复**（连 "sign check failed" 都不打）。
- 根因：给 `tcp_parse_cmd` 加 `heartbeat_ack` 分支时，落盘的 new_string **把 sensor_read 分支里的 `snprintf(tcp_sign_buf_2048, ... "sensor_read")` 整段丢了**，只剩 `sign_src = tcp_sign_buf_2048;`。而函数入口第 1713 行有 `memset(tcp_sign_buf_2048,0,...)` → `sign_src` 指向空串 → 第 1884 行 `if(sign_src==NULL || strlen(sign_src)==0) goto exit;` **在验签前就 exit**，故两种查询一律无响应。
- 修复：还原 4 行 snprintf（`{"device_id":"%s","sensor_id":%d,"seq":%lu,"ts":%s,"type":"sensor_read"}`），并加"切勿再删"警示注释。已 Read 核验落盘（1852~1863 行）。
- 次生影响（同因）：`hb_lost_cnt` 唯一清零点在验签通过之后（1906 行），sensor_read 到不了那里 → 网关若只靠 sensor_read 轮询、不回 ack，设备会在 120s 后打 `Heartbeat timeout 3 times, restart TCP network!` 主动断链。修复后恢复正常。
- 教训（本工程反复踩）：**改 `tcp_parse_cmd` 的 if/else-if 分支链时，编辑必须只针对目标分支，落盘后逐分支核验"每个 `sign_src = tcp_sign_buf_2048;` 前面都有配套的 snprintf"**（现共 5 处：upgrade_start/sensor_data_ack/mode_set_req/sensor_read/heartbeat_ack）。
- 构建：`cmake --build build/Debug` EXIT=0，`[149/149] Linking ... SensorConcentrator.bin`，无 error（仅既有 cJSON 三方告警 + `g_sensor_ack_status` 未用）。
