## 排查：调试口（RS485 重定向 printf）完全无输出

**现象**：按昨日方案把第 8 路 RS485 改作调试口、实现 `__io_putchar()` 强定义后，
串口助手上收不到任何字符。

**根因（重要，易复踩）**：
本工程链接参数是 `--specs=nano.specs`（见 `cmake/gcc-arm-none-eabi.cmake`），
配合 `-ffunction-sections` + `-Wl,--gc-sections`。在这种配置下：

- `printf()` 的真正出口是 **newlib 的 `_write_r()`**，
  **不是** `Core/Src/syscalls.c` 里那个 `__attribute__((weak))` 的 `_write()`；
- `_write()` 没有任何强引用，被 `--gc-sections` 整段回收；
- 于是 `_write()` 调用的 `__io_putchar()` 也一并被回收 → 我们写的重定向代码
  编译进 obj 却在最终 elf 里消失，串口自然毫无输出。

即：STM32 CubeMX 工程里常见的「实现 `__io_putchar()` 就能 printf」经验，
在 newlib-nano + gc-sections 下**不成立**。

**诊断方法（可复用）**：
1. `nm elf | grep 符号` —— 目标符号在 obj 里有 `T`，但 elf 里查不到 = 被回收；
2. 查 `build/Debug/SensorConcentrator.map`，看符号是否落在
   `Discarded input sections` 段（该段地址列全为 `0x00000000`）；
3. `objdump -d --start-address=... --stop-address=...` 反汇编出口函数，
   确认是否真的 `bl` 到了自己实现的发送函数。

**修复**：
- `debug_uart.c` 新增 `_write_r()` **强定义**（覆盖库中版本），内部循环调用
  `debug_putc()`；`__io_putchar()` 保留并加 `__attribute__((used))` 作为兼容路径。
- `DebugUart_Init()` 末尾加一行上电自检打印 `[DBG] RS485 #N debug port ready, 115200 8N1`，
  上电即可判断链路是否打通（不必依赖收到传感器数据）。
- 验证：`nm` 显示 `_write_r` / `DebugUart_Flush` 均为 `T` 且地址落在本模块
  （0x0801ffb8 / 0x0801fef8）；`objdump` 确认 `_write_r` 内 `bl <debug_putc>`。
  FLASH 203108B/19.37%，RAM 460904B/87.91%。

**遗留提醒**：
- 若上电仍看不到 `[DBG]` 行，优先排查：串口助手是否接在第 8 路（默认 `SH_DEBUG_UART_ID=8`，
  对应 UART8 / PE2 方向脚）、波特率 115200 8N1、RS485 收发器 A/B 与 USB-485 转换器的极性。
- `SensorHub_Task` 栈实测为 **2048 字**（`freertos.c:238`），不是此前记录的 1024 字。

## 二次排查：修好 _write_r 后仍然无输出

补上 `_write_r()` 后用户反馈依旧无打印，继续深挖，先排除两项：
- **方向脚**：`gpio.c` 里 8 路 `*_RTS_Pin` 均为 `GPIO_MODE_OUTPUT_PP`（普通推挽，非 AF 复用），
  `HAL_GPIO_WritePin` 能正常拉高/拉低 DE ✓
- **硬件流控**：`usart.c` 里 8 路 `HwFlowCtl` 全部 `UART_HWCONTROL_NONE` ✓（不会卡等 CTS）

**新根因（高度可疑）**：`configTOTAL_HEAP_SIZE = 30720`（仅 30KB，见 `Core/Inc/FreeRTOSConfig.h:67`），
而各任务栈需求合计已超 50KB：
defaultTask 4K + Task_InitTask 8K + Udp 8K + Tcp_client 8K + tcp_sender 8K + Reboot 2K + TimeSync 4K + SensorHub 8K。
`SensorHub_Task` 排在倒数第二个创建，**很可能因堆不足而创建失败**；
而 `DebugUart_Init()` 原本只在 `SensorHub_Init()`（即该任务内）被调用 → 任务没起来就永远不会被初始化 → 零输出。

**修复**：把 `DebugUart_Init()` 提前到 `main()` 的 `USER CODE BEGIN 2`（`MX_RTC_Init()` 之后、
`MX_FREERTOS_Init()` 之前），不依赖任何任务创建成功，上电最早即可打印。
同时新增诊断输出（一次上电即可判断堆是否耗尽）：
- `[DBG] heap total: N bytes`（调度器启动前）
- `[DBG] heap left after tasks: N bytes`
- `[DBG] task_create: sensorhub=OK/FAIL tcp_client=... udp=...`（在 `Task_InitTask` 末尾）

**验证**：`objdump -d` 确认 main 中 `bl <DebugUart_Init>` 位于 `bl <MX_FREERTOS_Init>` 之前 ✓
（`SensorHub_Init` 内仍保留一次调用，靠 `s_inited` 防重入）。
`nm` 确认 `_write_r`(08020028) / `DebugUart_Flush`(0801ff68) / `DebugUart_Init`(0801fe84) 均已保留。

**下一步建议（待用户确认）**：若打印出 `sensorhub=FAIL`，需增大 `configTOTAL_HEAP_SIZE`
（剩余 RAM 约 63KB，堆可上调至 45~50KB），或削减其他任务栈。

## 结果：调试口已打通 ✅

用户确认串口助手已有打印输出。确认生效的修复为「`_write_r()` 强定义 + `DebugUart_Init()`

- `_write_r()` 解决 **符号被 `--gc-sections` 回收**（printf 根本没出口）；

## HardFault 真因：autoip_start 在非 tcpip 线程上下文被调用（上下文错误）

**现象**：tcpip_thread 内 `autoip_tmr→autoip_arp_probe→etharp_request→etharp_raw`
触发 `CFSR=0x01000000`（UFSR.STKOF 栈溢出）升级为 HardFault。无限扩 TCPIP_THREAD_STACKSIZE
（曾扩到 8192=32KB）仍崩；**注释掉 `autoip_start(&gnetif)` 后不再进错误中断**（用户实测）。

**真因**：`autoip_start/stop` 以及 `netif_set_ipaddr/netmask/gw/up/down/addr` 在
`LWIP_TCPIP_CORE_LOCKING=1` 下首行都带 `LWIP_ASSERT_CORE_LOCKED()`，必须由
**tcpip_thread** 执行（或持 core lock）。但它们被放在普通任务 `StartDefaultTask`
调用的 `net_config_init()` 里直接调用 → 与 tcpip_thread 的定时器并发读写 netif 共享状态
（autoip 结构体/linkoutput 等）→ 数据竞争破坏指针 → 在 tcpip_thread 表现为 STKOF。
（注意：`net_comm_task.c:1070` 处另一处 `autoip_stop` 已正确用 `LOCK_TCPIP_CORE` 包住，无需改。）

**正确修法**（官方 netifapi，注释明写 "To be called from non-TCPIP threads"）：
- `net_comm_task.h` 增加 `#include "lwip/netifapi.h"`
- `net_config_init()` 内：
  - if 分支：`netif_set_ipaddr/netmask/gw` 三句 → `netifapi_netif_set_addr(&gnetif,&ip,&mask,&gw)`；
    `autoip_stop` → `netifapi_autoip_stop(&gnetif)`；`netif_set_down/up` → `netifapi_netif_set_down/up(&gnetif)`。
  - else 分支：`autoip_start(&gnetif)` → `netifapi_autoip_start(&gnetif)`。
- `netifapi.c` 已在 `cmake/stm32cubemx/CMakeLists.txt:142` 编译，接口可用。
- **不需要继续扩栈**：栈溢出是竞争破坏的「症状」不是原因，修好上下文后栈可保持合理值。

**待用户回填**：`[DBG] heap left after tasks` 与 `[DBG] task_create: sensorhub=OK/FAIL` 的实际值，
用以判定是否需要上调 `configTOTAL_HEAP_SIZE`，以及 `[Sx RX]` 传感器帧是否正常出现。

## 三次排查：反复打印 = IWDG 复位循环；关狗后卡在 FAL 初始化之后

**现象**：上电反复打印 `[DBG] RS485 #8...` / `[DBG] heap total` / FAL 分区表这一整块；
用户手动关掉看门狗后不再复位，但打印停在 `Flash Abstraction Layer (V0.5.99) initialize success.` 之后。

**已排除**：
- `fal_flash_init()`(`fal_flash.c:32`) 与 `fal_partition_init()`(`fal_partition.c:165`) 都有 `init_ok`
  守卫 → FAL 日志每次上电只打印一次，排除"FAL 被重复调用"。
- `HardFault_Handler`(`stm32f7xx_it.c:106`) 是 `while(1)`，不会复位 → 排除硬件故障复位。

**根因（高置信）**：IWDG 超时远小于内部 Flash 擦除时间。
- `iwdg.c`：Prescaler=4、Reload=4095、LSI=32kHz → 超时 = 4096×4/32000 ≈ **512 ms**。
- FlashDB 首次初始化会格式化 KVDB：分区 `ef_kvdb1` 512KB = **2 个 256KB 扇区**（`fdb.c:72-97`，
  sec_size 取 FAL `blk_size`=256KB，max_size/sec_size=2 刚好卡在最小允许值）。
- STM32F7 单 Bank 模式下**擦除/编程 Flash 期间 CPU 取指被阻塞**（总线 stall），
  256KB 扇区擦除典型 1~4s ≫ 512ms → IWDGTask 无法喂狗 → IWDG 复位 → 上电重来 = 反复打印。
- 关狗后不再是复位，而是真的停在擦除 stall 里（看起来像死机）。

**链路**：`init_sys_db()`(`syncif.c:47`) → `fdb_kvdb_init()` → `fdb.c:64 fal_init()` →
打印 FAL 分区表 → 之后 FlashDB 格式化擦除 256KB 扇区 → CPU stall。
下一步本应打印 `FlashDB V1.x is initialize success.`（`fdb.c:108`），据此可判断是否只是慢。

**待确认 / 备选修复**：
1. 先等 30~60s 看是否出现 `FlashDB V... is initialize success.` —— 若出现则只是慢，不是死机。
2. 加大 IWDG 超时：Prescaler 4→64（8.2s）或 →256（32.8s）。
3. 改双 Bank（nDBANK=0），代码跑 Bank1、擦 Bank2，根治 CPU stall（需改选项字节 + 布局）。
4. KVDB 只有 2 个扇区是 FlashDB 下限，每次 GC 都要擦 256KB，内部 Flash 做 KVDB 结构性偏慢。

**隐患（需单独修）**：`main.c:117` 的 `MX_IWDG_Init()` 被注释，但 `IWDGTask`(`freertos.c:213`)
仍调 `HAL_IWDG_Refresh(&hiwdg)`，`hiwdg.Instance` 为 NULL → 向地址 0x00000000 写 0xAAAA。

## 四次排查：关狗后真卡在 Flash 编程（HardFault）

**现象**：用户截图显示程序停在 `HAL_FLASH_Program` 的 `FLASH_WaitForLastOperation`
（寄存器 `r1 = 0x08080004`，即 S6 扇区 + 4），调用栈为 `HardFault_Handler ← HAL_FLASH_Program`。
说明不是简单的擦除慢，而是 **Flash 编程期间触发了 HardFault**。

**根因**：
- STM32F7 **单 Bank 模式**下，对 Flash 进行擦除/编程时，CPU 不能从同一 Flash Bank 取指；
- 如果此时有中断发生，而 ISR 代码存放在 Flash 中，ISR 入口取指会触发 BusFault/HardFault；
- 此前 `fal_flash_stm32f7_port.c` 的 `write()`/`erase()` 没有关中断，Flash 操作期间任何中断
  （例如 UART IDLE、DMA TC、ETH、SysTick）都可能导致 HardFault。

**修复**：在 `fal_flash_stm32f7_port.c` 的 `write()` 和 `erase()` 中：
1. Flash 操作前 `primask = __get_PRIMASK(); __disable_irq();`
2. Flash 操作后 `__set_PRIMASK(primask);` 恢复原中断状态
3. 用 PRIMASK 而不是裸 `__enable_irq()`，避免在调用者原本就关中断的情况下错误打开。

**验证**：`cmake --preset Debug` + `ninja` 编译通过（156/156，FLASH 202932B/19.35%）。

**副作用/注意**：
- 擦除 256KB 扇区期间中断被屏蔽约 1~4s，UART/ETH/lwIP 等中断均无法响应，
  网络/串口会出现短暂“无响应”；首次格式化/少量 KV 写入可接受，高频写入不建议。
- 若后续看门狗恢复，必须确保 IWDG 超时 > 单次最大 Flash 操作时间（建议 ≥ 8s）。
- 根治方案仍是双 Bank（nDBANK=0）或外部 Flash。

## 五次排查：关中断后仍写失败 + 偶发 HardFault

**现象**：
- 有时直接进 HardFault（调用栈仍为 `HAL_FLASH_Program`）；
- 有时能跑起来，但稳定出现 3 次 `[E/FAL] Partition write error! Flash device(stm32_onchip) write error!`，
  之后才打印 `ETH database initialization successful`。

**根因**：FAL 设备的 `write_gran` 配置错误。
- `fal_def.h:126-128` 明确注释：`write minimum granularity, unit: bit.
  1(nor flash)/ 8(stm32f2/f4)/ 32(stm32f1)/ 64(stm32l4)`；
- STM32F7 内部 Flash 与 STM32L4 同为 **64 位（8 字节）双字编程**，应设 `write_gran = 64`；
- 此前误设为 `8`（= 1 字节），FlashDB 据此按任意字节地址调用 `write()`，
  导致 `HAL_FLASH_Program(FLASH_TYPEPROGRAM_DOUBLEWORD, 0x08080004, ...)` 收到非 8 字节对齐地址，
  触发 PGAERR → 写失败日志；偶发 HardFault 则是错误路径 + 中断临界区交互的副作用。

**修复**：
1. `stm32_onchip.write_gran` 从 `8` 改为 `64`；
2. `write()` 重写为基于 read-modify-write 的 8 字节双字循环：
   - 把任意 `addr/size` 对齐到 8 字节边界 `align_addr = addr & ~0x07`；
   - 读出原 64 位内容，用 `memcpy` 覆盖新字节，再整双字写回；
   - 保留 PRIMASK 中断保护。

**验证**：编译通过（156/156，FLASH 202964B/19.36%）。

**结论/教训**：配置 FAL 内部 Flash 端口时，`write_gran` 必须以 **位** 为单位匹配 MCU 的
真实 Flash 编程粒度；F7 是 64 bit，不是 F4 的 8 bit。这个错误是本次反复 HardFault/写失败的
直接根源。

## 六次排查：偶发 HardFault 的 lr/pc 为乱码 → 内存损坏

**现象**：最新截图中 HardFault 时 `lr = 0x38e85203`、`pc = 0x38e85202`，这不是有效代码地址
（F767 RAM 只到 0x2008_0000 左右），说明返回地址被破坏，属于栈溢出/堆越界写症状。
每次调用栈都停在 `HAL_FLASH_Program`，是因为 Flash 操作关中断时间长，把原本潜伏的
内存损坏问题“挤”出来了。

**修复/加固**：
1. `FreeRTOSConfig.h`：`configTOTAL_HEAP_SIZE` 从 30720 增大到 **51200**；
2. `freertos.c`：
   - `defaultTask` 栈从 1024 字增大到 **4096 字**；
   - `Task_InitTask` 栈从 2046 字增大到 **4096 字**；
   - `init_net_db()`（FlashDB/KVDB 初始化）从 `StartDefaultTask` 移到 `Task_InitTask`，
     避免在只有 4KB 栈的 defaultTask 中做重型初始化；
   - 注释 `IWDGTask` 的创建：因为 `main.c` 中 `MX_IWDG_Init()` 被注释，`hiwdg.Instance=NULL`，
     `IWDGTask` 每 200ms 向地址 0x00000000 写 0xAAAA，本身就是潜在 HardFault/总线错误源。
3. `debug_uart.c/.h`：新增 `DebugUart_Panic()`，不依赖 printf/堆/互斥量，直接轮询发串口；
4. `stm32f7xx_it.c`：`HardFault_Handler` / `MemManage_Handler` / `BusFault_Handler` 入口调用

**验证**：编译通过（156/156，FLASH 203020B/19.36%，RAM 481368B/91.81%）。

**注意**：RAM 使用率上升到 91.81%，已比较紧张。若后续再加功能，需考虑减任务栈或恢复
外部 Flash 以释放内部 Flash/内存压力。

## 修复：Auto generate DEVICE_ID 后进入 HardFault_Handler

**现象**：上电打印 `[NET:99] Auto generate DEVICE_ID: 511300280043` 后立即进入
`HardFault_Handler(void)`。

**两个根因（均已修复）**：

1. **kvdb 未初始化即被读取（主因）**：`net_config_init()` 在 `StartDefaultTask` 里于

**构建**：`cmake --preset Debug` + ninja（build/Debug）编译通过，

## 修复：FAL 写内部 Flash 持续报 "Partition write error" + Task_InitTask 不运行

**现象**：HardFault 修复后，上电能打完 DEVICE_ID，随后反复打印
`[E/FAL] (fal_partition_write:469) Partition write error!`，且 `Task_InitTask` 不运行
（KVDB 始终初始化失败 → init_net_db 失败）。

**根因（关键，STM32F767 易踩）**：
STM32F767 **出厂默认是双 Bank**（nDBANK=0）。双 Bank 下：
- Bank1 = 0x08000000，Bank2 = 0x08080000；
- 0x08080000 实际是 **Bank2 / Sector12**，物理扇区大小 16K×4 + 64K + 128K×3，**不均等**；
- 而本工程 KVDB 分区设计按**单 Bank** 假设：0x08080000 = Bank1 / S6+S7，各 256KB，统一擦除粒度 256KB。

旧 `fal_flash_stm32f7_port.c` 把扇区表写死成单 Bank（S6/S7=256KB，
`erase()` 里 `Banks=FLASH_BANK_1`），导致在默认双 Bank 硬件上**擦错了物理扇区**，
0x08080000 实际从未被擦除，于是每次 `HAL_FLASH_Program` 都因目标非空而失败 →
"Partition write error"，KVDB 永远初始化不出来，连锁导致 Task_InitTask 的 init_net_db 失败。

**修复**：`fal_flash_stm32f7_port.c` 的 `init()` 检测 Bank 模式：
- 若为双 Bank，则**一次性把 nDBANK 选项位写 1 切到单 Bank**（`HAL_FLASHEx_OBGetConfig`
  + 仅置位 `OB_NDBANK_SINGLE_BANK` 的 `OPTIONBYTE_USER` 编程，再 `HAL_FLASH_OB_Launch()`
  复位生效）。该操作只改 USER 选项位（nDBANK 等），**不动 RDP/BOR，不会锁死芯片**；
- 复位后 init() 走单 Bank 分支（S6/S7=256KB），与上层 KVDB 设计完全一致。

**验证**：`cmake --preset Debug` + ninja 编译通过（FLASH 19.74% / RAM 91.84%）。
首次烧录会多一次"切单 Bank + 复位"，之后即稳定。

**经验**：STM32F7 用内部 Flash 做 FAL/FlashDB 时，务必先确认 Bank 模式；F7 默认双 Bank，
其扇区布局与单 Bank 完全不同，分区/扇区表必须匹配实际 Bank 模式，否则擦写全失败。

## 修复：单 Bank 同 Bank 写 Flash 崩溃 / 反复 "Partition write error"

**现象**：烧录后打印 DEVICE_ID 即反复 `[E/FAL] Partition write error!`，偶发 HardFault
停在 `HAL_FLASH_Program` 内部。日志 `blk_size: 0x00040000`(256KB) 说明芯片处于**单 Bank**。

**根因（F767 内部 Flash 关键约束）**：STM32F767 内部 Flash 编程/擦除期间，**CPU 不能从
同一 Bank 取指令**。本工程代码在 Bank1、KVDB 也在 Bank1（0x08080000 = S6/S7），单 Bank 下
二者同 Bank → 写 KVDB 时 CPU 取指失败 → HardFault / 写错误。这就是之前反复失败的真凶
（早先判定的"双 Bank 扇区表错"是误判，单 Bank 切换反而把问题暴露得更直接）。

**修复（方案 A：强制双 Bank + 只使用 Bank2 均匀扇区）**：
- `fal_flash_stm32f7_port.c`：`init()` 检测若当前是单 Bank(nDBANK=1)，先 `OB_NDBANK_DUAL_BANK`
  清 nDBANK 位切回双 Bank（`HAL_FLASH_OB_Launch()` 触发复位，只动 USER 选项位，不动 RDP/BOR）；
  复位后走双 Bank 分支。KVDB 设备起点改为 `0x080A0000`（Bank2 S17），只用 S17+S18 两个
  **均匀 128KB** 扇区（共 256KB，满足 FlashDB 至少 2 扇区磨损均衡），`blk_size=128KB`。
  代码留 Bank1，写 Bank2 时 Bank1 仍可取指，安全。
- `fal_cfg.h`：`ef_kvdb1` 分区长度 512KB → 256KB（与设备长度对齐）。
- `STM32F767xx_FLASH.ld`：FLASH 长度 1024K → **512K**，强制代码只进 Bank1，避免溢出到
  Bank2 与 KVDB 同 Bank 再次踩坑（固件超 512K 会直接链接报错而非产生不可启动固件）。

**验证**：`cmake --preset Debug` + ninja 编译通过，FLASH 39.52% / RAM 97.70%
（用户已将 `configTOTAL_HEAP_SIZE` 提到 81920 字节缓解任务创建不足）。

**烧录注意**：当前芯片已是单 Bank，需**先全片擦除**再下载新固件（擦除后下载器无 Bank 模式
冲突）；新固件首启检测到单 Bank → 自切双 Bank → 复位 → 之后 KVDB 正常读写，且后续下载无需再擦除。

**经验**：STM32F7 用内部 Flash 存数据，**务必让代码与 Flash 数据位于不同 Bank**（双 Bank 模式）；
单 Bank 模式绝不可让代码与待写 Flash 同 Bank。这是比"扇区表/对齐"更底层、更致命的约束。

## 修复：方向 A —— Flash 擦/写底层改为 RAM 内执行（彻底消除同 Bank 写崩溃）

**现象**：之前在 `init()` 里自动改写 Option Byte 切 Bank，调试器挂接时 `HAL_FLASH_OB_Lock` 附近 HardFault；脱离调试器时切 Bank 其实成功（芯片现已双 Bank），但 KVDB 写仍偶发 `Partition write error`（FlashDB 探测未格式化分区时的可恢复报错，最终 `ETH database initialization successful`）。

**根因**：STM32F7 内部 Flash 编程/擦除期间整块 Flash 阵列停摆，CPU 不能从被操作的 Flash 取指。原 `write()/erase()` 调用 HAL 库函数（在 Flash 中），写 KVDB（Bank2/单Bank）时下一句取指在 Flash → 崩溃/写失败。

**最终方案（方向 A：RAM 驻留 flash 驱动）**：
- `fal_flash_stm32f7_port.c` **删除全部 Option Byte 切 Bank 逻辑**（危险源码，HardFault 元凶）。
- 新增 RAM 段函数 `__attribute__((section(".RamFunc")))`：
  `ram_flash_wait / _clear_flags / _unlock / _lock / _program_dword / _erase_sector`，
  全部**寄存器直写**（不调用 HAL，不调用 libc/memcpy），用 `FLASH->KEYR` 解锁、
  `FLASH_CR_PG + 双字写`、`FLASH_CR_SER + SNB 擦`。`write()/erase()` 也标 `.RamFunc`，
  内部手动拼 64 位数据（无 memcpy），全程关 PRIMASK 保护。
- KVDB 固定 **双 Bank** 布局：`0x080A0000`(Bank2 S17) + `0x080C0000`(S18)，2×128KB=256KB，
  代码留 Bank1。检测若为单 Bank → `DebugUart_Panic` 报错 + `while(1)`（不崩溃，提示用
  CubeProgrammer 设 nDBANK=0）。
- 链接：`.RamFunc` 已并入 `.data`（startup `LoopCopyDataInit` 从 `_sidata`→`_sdata` 拷贝，
  VMA=RAM `0x20000398`，覆盖在 `_sdata.._edata` 内，实测正确）。`main.c` 在
  `MX_FREERTOS_Init()` 前加 `SCB_InvalidateICache()` 保险。
- `fal_cfg.h` 分区 `ef_kvdb1`：offset 0, len 256KB；`STM32F767xx_FLASH.ld` FLASH 限 512K。

**验证**：`cmake --preset Debug` + ninja 编译通过（FLASH 39.19% / RAM 97.95%），map 确认
`.RamFunc` 落在 RAM 且被 startup 拷贝。烧录后 KVDB 应在 RAM 函数下稳定读写，无 Partition write error。

## 修复：MemManage_Handler 停在 erase() 入口（RAM 函数被 MPU 判不可执行）

**现象**：方向 A 改完（Flash 擦/写底层放 RAM）后，烧录运行从 HardFault 变成
`MemManage_Handler`，调用栈停在 `erase()`（`fal_flash_stm32f7_port.c:247`）入口。

**根因**：`Core/Src/main.c` 的 `MPU_Config()` 配了 MPU region 0：
`BaseAddress=0x20000000, Size=128KB, DisableExec=MPU_INSTRUCTION_ACCESS_DISABLE`。
`.RamFunc` 段落在 `0x20000398`，正好落在这 128KB SRAM 区域内。MPU 把该区标为
"不可执行"，跳转到 RAM 函数执行即触发 MemManage。这就是 HardFault→MemManage 的真相：
RAM 函数本身没问题，是 MPU 拦了执行。

**修复**：`MPU_Config()` 里 region 0 的 `DisableExec` 改为 `MPU_INSTRUCTION_ACCESS_ENABLE`
（STM32 跑 RAM 函数的标准做法），允许 SRAM 区域执行代码。

**验证**：`cmake --preset Debug` + ninja 编译通过（FLASH 39.19% / RAM 97.95%）。
烧录后 KVDB 擦/写应在 RAM 函数中正常执行，不再 MemManage / Partition write error。

**经验**：STM32F7 用 RAM 函数（.RamFunc）时，必须确认 MPU 没有把该函数所在 SRAM 区
标成 XN（Execute Never），否则 MemManage。CubeMX 默认 MPU region 0 常把 SRAM 128KB
设成 DisableExec，需手动放开。

## 修复：MemManage 修好后仍报 Partition erase error（FAL 擦除虚报失败）

**现象**：MPU 放开后不再 MemManage，但上电仍反复 `[E/FAL] Partition erase error!`，最后
`ETH database initialization successful`（擦除失败 3 次后竟成功）。

**根因**：`ram_flash_erase_sector / ram_flash_program_dword` 的**成功判定依赖 EOP 标志**
(`if (FLASH->SR & FLASH_SR_EOP)`)。在 STM32F7 上擦除/编程后 EOP 不一定可靠置位，导致
函数**虚报 -1**（擦除其实成功了，但 EOP 没读到）→ FAL 认为擦除失败反复重试，最终 FlashDB
靠重试/后续写入"成功"收场。

**修复**：
- 成功判定放宽为"**无错误标志即成功**"：返回时 BSY 必然已清（ram_flash_wait 保证），
  故 `FLASH->SR & FLASH_ERR_FLAGS == 0` 即视为操作完成，不再依赖 EOP。
- 同步加 `__DSB()`（与 HAL 的 FLASH_Erase_Sector 对齐，确保 STRT 写被观察到）。
- 新增诊断：捕获失败时的 `FLASH->SR` 到 `g_flash_last_sr`，外层 erase/write 失败时
  经 `DebugUart_PanicHex` 打印 `[FLASH] erase fail SR=...` / `[FLASH] prog fail SR=...`，
  可定位真实错误位（WRPERR/PGAERR/PGPERR/ERSERR）。

**验证**：`cmake --preset Debug` + ninja 编译通过（FLASH 39.22% / RAM 97.97%）。
烧录后 `Partition erase error` 应消失（除非真有 WRP 等硬件错误，届时 SR 值会指明）。

**经验**：STM32F7 内部 Flash 驱动不要靠 EOP 判成功，靠"BSY 清 + 无错误标志"更稳。

## 修复：MemManage (IACCVIOL) 重现 —— MPU DisableExec 被还原 + 区域仅 128KB

**现象**：烧录当前源码后启动即 `!!! MemManage !!!`，CFSR=0x1(IACCVIOL)，PC/EXC_LR=0x2007FFB0(MMFARVALID=0，
栈帧为乱值，真正的违例点在 .RamFunc)。日志 `heap total: 81920` 对应当前源码(configTOTAL_HEAP_SIZE=81920)，
说明板上是**当前源码**的新构建。

**根因**：之前那次"MPU DisableExec 改 ENABLE"的改动**没保留**——`Core/Src/main.c` `MPU_Config()` 第223行
仍是 `MPU_INSTRUCTION_ACCESS_DISABLE`，且 region 0 只覆盖 **128KB**(0x20000000~0x2001FFFF)。
Flash 擦/写底层(.RamFunc)在 `0x20000398`(落在 region 0 内)，被标成 XN→一执行就 IACCVIOL。
(此前"Partition erase error"那次是 MPU 还是 ENABLE 的旧构建；文件被还原后重编重烧，MemManage 回来。)

**修复**：`MPU_Config()` region 0 改为：
- `Size = MPU_REGION_SIZE_512KB`(覆盖整片 SRAM)
- `DisableExec = MPU_INSTRUCTION_ACCESS_ENABLE`(允许 SRAM 执行代码)
保持 non-cacheable + shareable(DMA 安全)。注释说明 .RamFunc 必须可执行。

**验证**：`cmake --preset Debug`+ninja 编译通过；RAM 41.20%(216KB/512KB)、FLASH 39.25%；
`nm` 确认 ram_flash_* 链接地址 0x20000398/0x20000424/0x200004b8 均在 512KB 可执行区内。

**附带发现**：当前源码 `FreeRTOSConfig.h` 的 `configTOTAL_HEAP_SIZE` 也还原回了 81920(原值)，
但 `lwipopts.h:PBUF_POOL_SIZE=32`、`ethernetif.c:ETH_RX_BUFFER_CNT=32` 仍在 → RAM 仅 41%，够用，堆无需再改。
**教训**：本项目 main.c / FreeRTOSConfig.h 等会自动被还原(CubeMX 重生成或 git checkout)，
改完务必重新编译并核对 elf，不能假设上次的补丁还在。


## 修复：safe_tcp_close() 在 UNLOCK_TCPIP_CORE() 处卡死（取锁成功判失败→锁泄漏死锁）

现象：Tcp_client_task 调用 safe_tcp_close() 后停在内层 UNLOCK_TCPIP_CORE();（调试图 PC 指在该行）。

根因：net_comm_task.c:1178 取锁判断写反：
  err_t mutex_ret = xSemaphoreTakeRecursive(tcp_send_mutex, osWaitForever);
  if(mutex_ret != osOK) { UNLOCK_TCPIP_CORE(); return; }
xSemaphoreTakeRecursive 成功返回 pdPASS=1，而 CMSIS osOK=0 → 1 != 0 恒真，
每次成功取锁都被判成失败走错误分支。后果：
1. tcp_send_mutex 已被当前任务取走却从不 xSemaphoreGiveRecursive → 永久泄漏；
2. tcp_close()/tcp_abort() 在 do{...}while(0) 中早退未执行 → TCP PCB 不关闭。
真正卡死点：tcp_send_mutex 泄漏后，后续 xSemaphoreTakeRecursive(..., osWaitForever) 永久阻塞。
调试图停在 UNLOCK_TCPIP_CORE 只是案发最后一句假象——osMutexRelease 内部 xSemaphoreGive 阻塞时间恒 0 永不阻塞。

修复：改 if(xSemaphoreTakeRecursive(tcp_send_mutex, osWaitForever) != pdPASS)（与 1397 行一致）。
验证：cmake+ninja 编译通过（RAM 41.20% / FLASH 39.22%）。
经验：FreeRTOS 原生 API(xSemaphoreTake*)返回 pdPASS/pdTRUE(1)，绝不能与 CMSIS 的 osOK(0) 比较；比较锁结果统一用 == pdPASS / != pdPASS。


## HardFault 根因转向：tcpip_thread 任务栈溢出/破坏（非启动栈）

现象：启动栈从 4KB→16KB→32KB 都仍 HardFault，PC=0x2007FFB0 指向栈区，调用链底部出现两次
pxPortInitialiseStack(port.c:208)——这是 FreeRTOS 初始化任务栈的函数，运行时绝不该出现在调用链。

根因：调用栈底部出现 pxPortInitialiseStack 说明 tcpip_thread 的任务栈（PSP）已被破坏/溢出，
调试器读到了栈底填充的 magic 值/初始上下文。问题不是 MSP 启动栈容量，而是 tcpip_thread 任务栈不足
或被其他代码越界写。

改动：
- LWIP/Target/lwipopts.h: TCPIP_THREAD_STACKSIZE 4096→8192 (word)，tcpip_thread 实际栈从 16KB→32KB
- Core/Src/freertos.c: vApplicationStackOverflowHook 改为强定义，打印 `[RTOS] Stack overflow in task: xxx`
  并死循环，便于串口定位哪个任务栈溢出。
- STM32F767xx_FLASH.ld: _Min_Stack_Size 保持 0x8000 (32KB)，给 MSP 留足余量。

验证：cmake+ninja 编译通过；RAM 50.60% / FLASH 39.25%。

下一步：烧录新固件测试。若仍 HardFault 且 hook 没打印，说明不是 FreeRTOS 检测到的任务栈溢出，
而是其他任务/中断越界写破坏了 tcpip_thread 的栈，需要进一步用 watchpoint 或内存检查定位。

## HardFault 真因定位 + 根治：autoip_start 在错线程上下文调用（编译期又被 LWIP_NETIF_API 关闭放大）

现象：注释掉 `autoip_start(&gnetif)` 后不再进 HardFault（用户实测），确认触发点就是 autoip 路径，
而非栈大小问题。此前无限扩 TCPIP_THREAD_STACKSIZE 到 32KB 仍崩，因栈溢出只是"症状"。

真因：本工程 `LWIP_TCPIP_CORE_LOCKING=1`。此模式下 `autoip_start/stop` 及 `netif_set_*`
首行均带 `LWIP_ASSERT_CORE_LOCKED()`，必须由 **tcpip_thread** 执行（或持 core lock）。
但这些调用原本放在普通任务 `StartDefaultTask` 调用的 `net_config_init()` 里直接调用
→ 与 tcpip_thread 的 `autoip_tmr` 定时器并发读写 netif 共享状态（autoip 结构体/linkoutput 等）
→ 数据竞争破坏指针/栈 → 在 tcpip_thread 的 `autoip_arp_probe→etharp_raw` 表现为 STKOF(HardFault)。

两处叠加隐患：
1. 调用上下文错误（上述）；
2. `LWIP_NETIF_API` 在工程里**未定义**（默认 0），导致 `lwip/netifapi.h` 整份声明被
   `#if LWIP_NETIF_API` 条件编译屏蔽 —— 即便 include 了 netifapi.h，编译器仍报
   "implicit declaration of netifapi_*"，安全接口名存实亡。

修复（用户确认"修改"后已落地，编译通过）：
- `LWIP/Target/lwipopts.h`（USER CODE BEGIN 0，CubeMX 不覆盖）：新增 `#define LWIP_NETIF_API 1`
  （紧挨 `LWIP_TCPIP_CORE_LOCKING 1`）。
- `UserCode/Drivers/ETH/net_comm_task.h`：新增 `#include "lwip/netifapi.h"`。
- `UserCode/Drivers/ETH/net_comm_task.c` `net_config_init()`：
  - if 分支（原 LOCK_TCPIP_CORE 包裹的 netif_set_*）：
    `netif_set_ipaddr/netmask/gw` → `netifapi_netif_set_addr(&gnetif,&ip,&mask,&gw)`；
    `autoip_stop` → `netifapi_autoip_stop(&gnetif)`；`netif_set_down/up` → `netifapi_netif_set_down/up(&gnetif)`。
  - else 分支：`autoip_start(&gnetif)`（原 LOCK_TCPIP_CORE 包裹）→ `netifapi_autoip_start(&gnetif)`。
  - **关键**：改用 netifapi 后必须**删除原 LOCK_TCPIP_CORE/UNLOCK 包裹**，否则会持锁等待 tcpip_thread
    取同一把锁 → 死锁（netifapi 内部已在 tcpip_thread 上下文正确加锁）。
  - `netifapi.c` 已在 `cmake/stm32cubemx/CMakeLists.txt:142` 编译列表中，接口可直接用。
- **未动**：`net_comm_task.c:1070` 处另一处 `autoip_stop` 仍用 LOCK_TCPIP_CORE 包裹（运行时机晚、
  lock 已创建，属已验证的安全路径），按"先确认再改"约定保持不变。

验证：cmake+ninja 编译通过（RAM 45.13% / FLASH 39.33%，仅一个无关的 RWX LOAD 段警告）。

结论/经验：
1. `LWIP_TCPIP_CORE_LOCKING=1` 下，**任何 netif_set_*/autoip_*/dhcp_* 都必须走 tcpip_thread**；
   非 tcpip 线程调用请统一用 `netifapi_*`（头文件注释 "To be called from non-TCPIP threads"）。
2. **启用 netifapi 前必须开 `LWIP_NETIF_API`**，否则接口被条件编译屏蔽，报 implicit declaration。
   这是比"加 include"更隐蔽的一层——include 有了但宏没开，声明照样不展开。
3. 栈溢出（STKOF）在 tcpip_thread 路径上出现时，先怀疑"错线程调用 netif API 导致并发破坏"，
   而非盲目扩栈；盲目扩栈治标不治本。
4. 首次烧录新固件请重点验证：AutoIP 能拿到 169.254.x.x 且不再进 HardFault。

## 七次排查：AutoIP 启动后仍 HardFault —— 这次是真·UNALIGNED（etharp_raw 非对齐 u32 写）

现象：改用 netifapi 后（上下文问题已修），AutoIP 启动周期性发 ARP 仍进 HardFault。
故障分析仪：FORCED + UNALIGNED；`addr2line 0x08014C48` → `etharp.c:1137`
`IPADDR_WORDALIGNED_COPY_FROM_IP4_ADDR_T(&hdr->sipaddr, ipsrc_addr)`。
反汇编证实编译器把 4 字节 memcpy 优化成 `str r2,[r3,#0]`（u32 直接写）。

根因：
- `struct etharp_hdr` 中 `sipaddr/dipaddr` 协议偏移 14/24 字节；`pbuf_alloc(PBUF_LINK)` 的
  payload 被对齐到 4 字节（LWIP_MEM_ALIGN_SIZE 向上取整）→ `&hdr->sipaddr` 实际落在
  **2 字节对齐、非 4 字节**地址。
- 一旦 `SCB->CCR.UNALIGN_TRP=1`，etharp_raw 里的 u32 写即触发 UsageFault，升级 HardFault。
- 仅 AutoIP 启动后走 etharp_raw 填 ARP 包才触发 → 故"屏蔽 autoip_start 不崩"在前几轮成立。

修复（方案 A，用户确认，已落地 lwipopts.h USER CODE BEGIN 0）：
- 重定义两个宏，强制 u16_t 分两次复制（含 PP_HTONS 字节序转换），
  不再依赖编译器对 memcpy 的生成方式：
  ```c
  #define IPADDR_WORDALIGNED_COPY_FROM_IP4_ADDR_T(dest, src) do { \
      u32_t _tmp = ((const ip4_addr_t *)(src))->addr; \
      ((struct ip4_addr_wordaligned *)(dest))->addrw[0] = PP_HTONS((u16_t)(_tmp)); \
      ((struct ip4_addr_wordaligned *)(dest))->addrw[1] = PP_HTONS((u16_t)(_tmp >> 16)); \
  } while(0)
  // TO 宏反向，dest=ip4_addr_t*，src=struct ip4_addr_wordaligned*
  ```
- 注：`net_comm_task.c:1070` 处另一处 `autoip_stop` 仍 LOCK_TCPIP_CORE 包裹，未动（安全路径）。

验证：cmake+ninja 编译通过（RAM 45.13% / FLASH 39.41%，仅无关 RWX LOAD 段警告）；
objdump 确认 etharp_raw 中 sipaddr/dipaddr 已变为 `strh`（半字存储），不再有 `str r2,[r3]` 非对齐 u32 写。

经验：lwIP 在 Cortex-M7 + 强优化下，`IPADDR_WORDALIGNED_COPY_*` 默认 SMEMCPY 实现可能被
优化为 u32 访问，对 etharp_hdr 这种"字段天然 2 字节对齐"的协议结构会踩 UNALIGNED 陷阱；
若开启 UNALIGN_TRP，应在 lwipopts.h 显式重定义这两个宏为 u16_t 复制。

## ✅ 验证通过：方案 A 烧录后不再进 HardFault（用户确认）

用户烧录含"方案 A（重定义 IPADDR_WORDALIGNED_COPY_FROM/TO_IP4_ADDR_T 为 u16_t 复制）"
的固件后，实测 **AutoIP 启动正常、不再进 HardFault**（用户原话"不再进 HardFault"）。

至此 AutoIP 相关连环故障全部闭合：
1. `autoip_start` 错线程上下文 → 改用 `netifapi_*`（开 `LWIP_NETIF_API`）；
2. etharp_raw 非对齐 u32 写 → 方案 A 重定义宏为 u16_t 复制（objdump 已确认 `strh`）。
两条路径叠加才彻底消除 AutoIP 路径上的 HardFault。
