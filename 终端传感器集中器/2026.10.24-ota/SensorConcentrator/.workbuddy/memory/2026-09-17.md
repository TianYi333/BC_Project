## [OTA] meta state=0x04000002 异常诊断
- 现象：App 启动打印 `[OTA:336] meta magic=0x4C55424F state=67108866 (0x04000002)`。
- 拆解：低字节 `0x02`=DONE（正确），高字节 `0x04` 是垃圾位 → 当前 32B 读取把高字节当成 state 一部分。
- 排查：App/Boot 的 `ota_meta_t` 字节级一致（32B，magic@0/state@4）；git 单提交 `340e789`(09-14) 引入后从未改；枚举 0~4；H7 派生源 `/d/Desktop/boot` 也是同款 32B 结构。**无任何代码路径写 0x04000002。**
- FAL 校验：`stm32_onchip` 设备基址=0x08020000，ota_meta 分区 offset=448*1024 → 物理 0x08090000，**与 Boot `OTA_META_OFFSET` 完全一致** → 不是读错扇区。
- 结论：S16(ota_meta) 扇区里是**旧版固件遗留的 meta**（旧结构把 flags/version 字打进 state 高字节，或 state 是更小类型）；很可能是烧录新 boot+App 时未擦 S16，旧实验 meta 残留。
- 影响：无害启动（boot `default` 分支→跳 App；App `ota_app_confirm` 见 `state!=DONE` 跳过）；但垃圾值持续、且会掩盖真正 pending 的 OTA。
- 修复方向（待用户确认）：(A) 代码自愈——`ota_app_confirm` 遇 `magic` 正确但 `state∉{0..4}` 则擦 meta→NONE；(B) 一次性 CubeProgrammer/调试擦 S16(0x08090000)。

## [OTA] meta magic 变垃圾 + "不能正常更新" 根因坐实
- 现象升级：用户复现 `meta magic=0x4CD563DF state=1179099883(0x4647AE2B)`——magic 也变垃圾，S16 整体是随机/旧固件残留（不再是上轮的"合法 magic+脏 state"）。
- 复查排除：KVDB 受分区 `len` 限制绝不溢出进 S16；App/Boot 的 meta 写入均写合法 magic 且关中断+.RamFunc 同 Bank 安全；FAL `ota_meta` 物理=0x08090000 与 Boot `OTA_META_OFFSET` 一致 → 垃圾非当前代码输出。
- **用户验证（本轮回）**：CubeProgrammer 擦除整个 Flash 后 OTA 正常升级 → 根因就是 S16(及可能的 firmware_a/KVDB) 旧残留挡住 OTA 握手（boot 读不到合法 PENDING）。一次性整片擦除清掉残留即恢复。
- 结论：属一次性遗留状态，非代码 bug；当前 OTA 代码每次成功都写合法 meta，正常流程不复发。
- 可选加固（**已实现 2026-09-17**，用户说"实现"）：用户确认后落地 A+B。
  - A 自愈：App `UserCode/Drivers/ota/ota.c` 新增 `ota_meta_sanitize()`（擦 S16+写 NONE）；`ota_app_confirm()` 遇 `magic!=OTA_META_MAGIC || state>OTA_STATE_FAILED` 调它。`SensorConcentrator_boot/Core/Src/main_boot.c` 在"无 magic 分支(双 Bank 下)"与"switch default 分支"均置 NONE 并 `write_meta()`。
  - B 判错日志：`ota_on_complete()` 现检查 `fal_partition_erase/write` 返回值并 `LOG_OTA` 报错。
  - 验证：App `cmake --build build/Debug`(ninja) 通过，FLASH 205236B；Boot 另配 Ninja 到 `build_ninja` 构建通过(8040B) 后删该临时目录，原 `build/` 不变。

## [RS485] sensorhub_parse_frame 温度解析字节序 bug（已修复）
- 现象：实际帧 `01 04 08 00 00 00 00 00 00 CE 41 B0 5D`，用户反馈 `sd` 全 0（temp/vflag/tflag=0，mode=0）。
- CRC 核验：脚本算 `modbus_crc16(前11字节)=0x5DB0 == recv(B0 5D)` → **CRC 通过**，解析确实走到温度逻辑（vflag/tflag 为 0 是真实无突变；mode=0 是配置默认）。
- 根因：`sensor_hub.c:306` 把温度拼成 `raw=(reg2<<16)|reg3`=0x0000CE41（字节序反），本应是 4 字节小端 `0x41CE0000=25.75℃`。实际传感器把 float32 按**小端(DCBA / byte+word swapped)** 存于 reg[2]~reg[3]，frame 字节=reg2_lo,reg2_hi,reg3_lo,reg3_hi 即 float 小端映像（00 00 CE 41）。
- 修复（用户确认"要"后改）：删 `temp_hi`，温度改按 `buf[3+SH_REG_TEMPERATURE*2]` 起 4 字节小端直拼 uint32 再转 float；并同步修正 `sensor_hub.h` 寄存器布局注释（原"reg[2]=高16/reg[3]=低16" 是 ABCD 约定，与设备不符）。
- 验证：App `cmake --build build/Debug`(ninja) 通过 EXIT=0，FLASH 205252B；`g_sensor_ack_status` 未使用告警为既有，无关。
- ⚠️ 提示：Modbus 规范只定义 16-bit 寄存器，32-bit float 跨寄存器字节序是厂商自定义（ABCD/DCBA/BADC/CDAB 等变体）；换不同型号传感器需重新确认字节序。

## [RTC] 时钟不走 → 每10s 差10s 诊断（待用户定修复方向）
- 现象：`[NET:2343] Time diff: 10263 ms > threshold, re-sync`，每约10s 重复；协议 ts 字段冻结(此前记的 `Get_Unix_Second()` 恒 1788192001)。
- 链路：`Get_Unix_Second()`(`UserCode/Drivers/Clock/rtc_cluck.c:75`)→`RTC_To_UnixMs()`→`refresh_rtc_time()` 直接读 RTC 硬件寄存器(TR/DR/SSR)。
- `TimeSyncTask`(`net_comm_task.c:2293`)每 10s：`sys_unix_ms=0`→`NTP_Force_Refresh()`(SNTP 回调经 `lwipopts.h::SNTP_SET_SYSTEM_TIME_US` 写 `sys_unix_ms`)→读 `rtc_ms=RTC_To_UnixMs()`→差>2s 则 `UnixMs_To_RTC()` 把 RTC 重设成 NTP 时间。NTP 侧工作正常(能拿到真实时间)。
- 关键判据：若 RTC 计数器在走，`rtc_ms` 应≈`sys_unix_ms`(都基于真实时间)，diff≈0；每周期差整整~10s ⇒ **RTC 计数器这 10s 内根本未递增**，每次都被 NTP 追平、下轮又落后10s。
- 代码正确面：`main.c:170` 已 `RCC_LSE_ON`；`rtc.c:101` 选 `RCC_RTCCLKSOURCE_LSE`；预分频 `AsynchPrediv=127/SynchPrediv=255`→(128×256)=32768 对 LSE 正确；`.ioc` `RCC.RTCClockSelection=RCC_RTCCLKSOURCE_LSE`。
- 根因(硬)：LSE 已使能、预分频正确，RTC 却不计数 ⇒ 实际只剩两类：(1) **LSE 晶振物理未稳定起振/未焊接/负载电容不对**(最常见；HAL 等 LSE_RDY 超时本应 Error_Handler 卡死，但临界起振会"启动能过、RTC 几乎不计数")；(2) RTC 卡在初始化模式(INIT 位未清)暂停计数。
- 设计缺陷：`Get_Unix_Second()` 把系统时间唯一真源建在硬件 RTC 上，RTC 一不稳 ts 全废；`sys_unix_ms` 仅 SNTP 回调写、两次校时之间不累加(冻结)。
- 修复方向(待用户选)：(A) **SNTP 软件时钟为主**——`Get_Unix_Second()` 返回 `sys_unix_ms/1000`，并用硬件 tick(HAL_GetTick 差值)每周期累加，RTC 仅作断电保持/上电首校；最稳，不依赖 LSE 准不准(需网络)。(B) **改 LSI**——`rtc.c`+`.ioc` 把 RTC 源 `RCC_RTCCLKSOURCE_LSE`→`RCC_RTCCLKSOURCE_LSI`(内部RC必起振，精度差但能走)。(C) **先验证 LSE**——读 `RCC->BDCR` 的 `LSERDY` 位/CubeProgrammer 看 LSE 是否真 READY，或连读 `RTC->SSR` 数秒看是否变，确认是 LSE 硬件问题再定。

## [RTC] ms 后三位恒为 0 的根因（子秒丢失）
- 现象：`[NET:2360] NTPTime ...07:18:03.635` vs `[NET:2370] RTCTime ...07:18:03.000` —— RTC 秒与 NTP 秒一致，但 RTC 的毫秒永远是 `.000`。
- 链路(代码级)：协议 `ts`→`Get_Unix_Second()`(`rtc_cluck.c:75`)→`RTC_To_UnixMs():86`→`refresh_rtc_time():18` 读 `RtcSubSec=RTC->SSR & RTC_SSR_SS`；`ms=(255-RtcSubSec)*1000/255`(:107)。即 ms 完全由 RTC 亚秒寄存器 SSR 推出。
- 根因：① STM32 RTC 的 **SSR 是只读**(同步预分频计数器，只在每秒翻转时由硬件自动从 PREDIV_S 重载，正常模式不能写)；`UnixMs_To_RTC():66` 直接写 `hrtc.Instance->SSR=subSec` 是**无效写**，设不进任意毫秒；② 配合 RTC 冻结(LSE 未走，见上节)，SSR 停在重载值 255 → `ms=(255-255)*1000/255=0`；且 `refresh_rtc_time` 在 `HAL_RTC_GetTime/GetDate` 之后又直接读 `RTC->SSR`(未重新 RSF 同步)易读到陈旧值。⇒ RTC 路径**只能给整秒分辨率，亚秒物理上已丢**。
- 关键：那 635ms 的 NTP/RTC 差，正是被丢掉的亚秒；秒"对得上"只因每次 re-sync(`UnixMs_To_RTC`)趁 NTP 刚写到 RTC 时就打日志。
- **真时已在手**：`sys_unix_ms` 由 SNTP 回调 `lwipopts.h:81 SNTP_SET_SYSTEM_TIME_US` 写入(含 us→ms，精度到毫秒，`SNTP_UPDATE_DELAY=15s` 周期刷新+`NTP_Force_Refresh` 即时刷新)，但协议 `ts` 完全没用它，反而去读冻结/只读的 RTC ⇒ ts 既丢亚秒又每10s 漂移。
- 修复=A 的子项：让 `Get_Unix_Second()` 优先返回 `sys_unix_ms/1000`(NTP 软件钟，ms 准、不依赖 LSE)，仅 `sys_unix_ms==0`(未联网)时回退 `RTC_To_UnixMs()`；同时 `RTC_To_UnixMs` 亚秒公式分母应为 `(PREDIV_S+1)=256` 而非 255(小误差，次要)。

## [RTC] 用户贴 [RTC-DIAG] 实测 → 推翻"LSE 没起振/晶振"假设
- 实测(用户板子跑出)：`BDCR=0x00008103 LSEON=1 LSERDY=1 RTCEN=1 RTCSEL=1`；`SSR 107->211->...->246` 与 `SSR 197->188->...->108`(后段单调递减) → **SSR 在变，LSE 真 READY**。
- ⚠️ 修正前文假设：之前(第30行)猜"LSE 晶振未起振/临界起振"是错的——`LSERDY=1` 证明 LSE 已稳定供给 RTC。RTC Mode 配置页(本轮回截图)与 Clock 配置页(LSE=Crystal)也都**不是根因**(只是使能外设/选源，配置正确)。
- RTCSEL 位解：**F7 的 RTCSEL 在 BDCR bit[9:8]**，值 `01=LSE / 10=LSI / 11=HSE`；我 DIAG 里 `(bdcr>>8)&0x3=1` → **RTC 源确为 LSE(正确)**。之前打印的图例"(RTCSEL:1=LSI,2=LSE)"写反了，以本段为准。
- 直接读 `hrtc.Instance->SSR/TR` 的 DIAG 不可靠：batch1 非单调(107->211->124...) 证明未走 shadow 解锁序列读到失谐值；batch2 单调递减更像真 down-counter。故**无法单凭这些日志判定 RTC 的准确 Hz**(采样间隔未知)。
- 但仍坐实：协议 ts 用冻结/只读 RTC 必丢亚秒且每10s 漂移；真时只在 `sys_unix_ms`(SNTP 软件钟)。→ 仍走 **方案 A**(软件钟为主、RTC 仅备份)。下一步用户拍板是否实现 A。

## [RTC] SSR 递减但 TR 很久才变 → 量化坐实"RTC 走时偏慢约160倍"(非冻结)
- 用户新观察(每5s 打印一次)：`SSR 169->161 TR 7->7 MOVING` + "SSR 递减但 TR 很久才减一次"。
- 量化：SSR 全范围=`PREDIV_S+1=256`，对应 1 秒(若 RTC 准)。每 5s 真实时间，**准 RTC 的 SSR 应变化 5×256=1280、绕圈 5 次**(会出现低位跳高位的大跳变)；实测 5s 内仅 169→161 单调减 8、**无绕圈** ⇒ RTC 这 5s 只走了 `8/256≈31ms` 的 RTC 时间。
- 速度比：RTC 速 / 真实速 = `31.25ms / 5000ms ≈ 1/160`，即 **RTC 走时约为真实速度的 1/160(慢约160倍)**。
- 印证 TR 现象：TR(秒)每进 1 需 SSR 绕整圈 256 计数；在 1/160 速下 = `256×(5000/8)≈160000ms=160s` 才进 1 秒 ⇒ 用户"TR 很久才减(进)一次"完全对应(秒寄存器递增，"减"为口误)。
- 自洽：10s 真实时间 RTC 仅走 `10/160≈62.5ms` ⇒ 落后 ≈9938ms≈10s，与 `[NET:2343] Time diff:10xxx ms` 完全吻合。
- **推翻"冻结"假设**：之前以为 RTC 卡死不计数；实际"在走但极慢(1/160)"。LSERDY=1 只证振荡器在工作、不保证频率准/分频对。
- 硬件偏慢可能机理(非方案A必需)：① 代码分频 `(127+1)×(255+1)=32768` 对 LSE 正确，但若 **PRER 实际值≠配置**(备份域保留旧值 / `HAL_RTC_Init` 不重写已初始化的 RTC 的 PRER)⇒ 用错分频；② LSE 实际频率远低于 32768Hz(物理晶振)。验证：CubeProgrammer 读 `RTC->PRER` 实际值，或加正规 `HAL_RTC_GetTime` 测真实 Hz。
- **结论收敛**：无论硬件为何偏慢，方案 A(`Get_Unix_Second()` 以 `sys_unix_ms` 软件钟为主、RTC 仅断电保持/未联网回退)是根治；即便修好硬件 RTC，`ts` 毫秒问题(SSR 只读、`UnixMs_To_RTC` 写 SSR 无效)仍在，方案A一举两得。等用户拍板实现。
