## NetAssist 显示 ALL CLIENTS(2) 的定性（2026-09-16 下午）
- 现象：同一设备 IP 出现 52919/52920 两个 client，数据全来自 52920，seq 从 12 起。
- 定性：**⚠️ 此结论依据不足，已于当日订正** —— 当时据"seq 从小数值开始"判为设备重启，错：register 里有强制重置逻辑，重连同样 seq=1。真实原因见下条：设备侧周期性 TCP 重连。设备侧代码核实无误：仅 tcp_pcb==NULL 才建链（LOCK 内二次防护），safe_tcp_close 规范，不可能同时持有两条连接。
- 处置：NetAssist 对僵尸口发任意数据（对端回 RST 即清除）或手动断开；正式网关应靠自身 keepalive/超时清死连。


## “client 越来越多” —— 周期性重连（2026-09-16 16:00 补记）
- 用户反馈：NetAssist 的 client 数量**持续增加**（不是只多一个）→ 定性为**设备侧周期性 TCP 重连**，每次重连都带 register(seq=1)，旧 client 未回收。
- **⚠️ 纠正前次错误判据**：不可再用"register seq 从 1 开始"当重启证据 —— `tcp_send_register()` 内有 `g_tcp_seq = 1;` 强制重置，重连也会 seq=1（已写入 MEMORY.md ②）。
- **关键代码事实（本次新查，决定性强）**：`pcb->tmr = tcp_ticks` 只出现在 `core/tcp_in.c:765 / 845`（收到入站报文）与 `core/tcp.c:1904`（tcp_alloc 新建时）。**发送数据一概不刷新 pcb->tmr**。
  → 上位机只收不发时，keepalive 判据 `(tcp_ticks - pcb->tmr) > (keep_idle + cnt*intvl)/TCP_SLOW_INTERVAL` 必然到期，`tcp_slowtmr` 走 `tcp_abort` → errf(`tcp_error_callback`) → `tcp_pending_close` → `safe_tcp_close` → 2~5s 节流后重连。
  → 这等于把当年“应用层心跳在上位机静默时把自己踢下线”的老毛病换了个地方复发（当时删了应用层心跳改 lwIP keepalive，但 keepalive 同样依赖入站报文刷新）。
- **❌ 候选 ① 已被证伪（当日自查，重要）**：`tcp_process()` 对每个入站报文都刷新 `pcb->tmr` 且清零 `keep_cnt_sent`，而设备发数据必然换来 Windows 的纯 ACK（10s 一次）→ keepalive 的 idle 永远到不了 10.5s 首次探测阈值。**"上位机静默 → keepalive 自杀式断链"不成立**；据此设想的"发送时补 `pcb->tmr = tcp_ticks`"修改作废、禁止实现。
- **剩余候选**：① PHY link flap（`ETH link DOWN` / `ETH link UP` 成对日志）；② lwIP errf abort（`TCP error (mark async close), err:N`，N=-13 ABRT/-14 RST/-15 CLSD）；③ `tcp_write fail, err:-1`；④ 复位重启（App 启动横幅）。
- **时间反推（两种重构都成立，无法仅凭 NetAssist 日志区分）**：最后一帧 15:56:36.080，新 online 15:56:44.844。
  - 重连说：关闭动作触发于 ≈15:56:39.8（5s 节流+握手），即最后一包后约 3.8s；
  - 重启说：复位就在 15:56:36.1 之后，8.7s 走完 boot+ETH+connect（与注释"上电约 8 秒才 link UP"高度吻合）。
- **最快判别手段**：持续 `ping 192.168.0.120 -t` —— 重启会有 ~8s 连续超时；纯 TCP 重连 ping 基本不断。次选：UDP 50000 监听看 device_online 是否重跑；最准仍是串口 [NET] 日志。
