# 2026-09-09 SensorConcentrator 调试日志

## 09:40 插网线后 HardFault（STKOF）

### 现象
- 不插网线：不进入 HardFault_Handler
- 插入网线连接电脑：立即进入 HardFault_Handler
- Fault_Dump：CFSR=0x01000000（STKOF），调用栈
  `tcpip_thread → tcpip_thread_handle_msg → ethernet_input → etharp_input → autoip_arp_reply`
- 异常 PC=0x20033D64 反查后是 `ethernetif.c:130` 的 `ETH_HandleTypeDef heth` 结构体字段地址，
  说明栈溢出后返回地址/异常帧被踩坏。

### 根因
tcpip_thread 栈太小。
- 当前 `TCPIP_THREAD_STACKSIZE=4096 word`（16KB），位于 `lwipopts.h` 的 CubeMX GUI 参数区。
- 不插网线时 PHY link 未建立，tcpip_thread 空转，栈消耗小；
- 插网线后 link up，ARP 包进入，`etharp_input → autoip_arp_reply → etharp_raw` 调用链较深，
  加上 AUTOIP/SNTP/TFTP/TCP 配置，16KB 被用爆。

### 修复
在 `LWIP/Target/lwipopts.h` 的 `USER CODE BEGIN 1` 保护区覆盖：
```c
#undef TCPIP_THREAD_STACKSIZE
#define TCPIP_THREAD_STACKSIZE  8192   // 32KB
```
- 用 `#undef` 覆盖上方 CubeMX 生成的 4096 定义；
- 编译通过：RAM 45.13% / FLASH 39.44%；
- FreeRTOS 堆 configTOTAL_HEAP_SIZE=100KB 仍足够。

### 待验证
烧录新固件，插网线后观察是否还进 HardFault。

## 更新：插网线 HardFault 真因 = ETH 描述符落在 DTCM（推翻栈溢出假设）

### 用户指正
"不是栈大小的问题，查看 Oil_Pump_Control 任务，则可以正常连接通讯"。
对比 Oil_Pump_Control(H743) lwipopts.h：`TCPIP_THREAD_STACKSIZE` 同为 **4096**，且能正常通讯
→ 栈大小非根因。之前扩到 8192 是无效改动，应回退 4096。

### nm 铁证（SensorConcentrator 当前 ELF）
- `DMARxDscrTab`  = 0x20000920  → **DTCM**（0x20000000–0x2000FFFF，ETH DMA 不可达）
- `DMATxDscrTab`  = 0x200009C0  → **DTCM**
- `ucHeap`(FreeRTOS堆) = 0x2000D8BC → **DTCM**
- `memp_memory_RX_POOL` = 0x200310F0 → SRAM1/2（DMA 可达，RX 缓冲 OK）

### 根因
F7 的 ETH DMA 不能访问 DTCM（0x20000000 起 64KB，只连 CPU）。
链接脚本被改双 Bank/512K 时**删掉了 CubeMX 默认的 `.RxDescripSection`/`.TxDescripSection` 段定义**，
导致 `DMARxDscrTab/DMATxDscrTab`（`section(".RxDescripSection")`）落到 `.bss` 默认区 = DTCM。
- 不插线：DMA 不碰描述符，不崩；
- 插线收包：DMA 读写 DTCM 描述符 → 总线异常/踩踏内存 → HardFault（PC 被踩成 heth 字段、表象 STKOF）。

### 修复方向（待用户确认）
- 方案A(推荐)：链接脚本 `RAM (xrw) : ORIGIN = 0x20010000, LENGTH = 448K`，跳过 DTCM。
  所有 RAM 分配（描述符/FreeRTOS堆/LwIP堆/栈）均在 DMA 可达的 SRAM1+SRAM2。栈回退 4096。
- 方案B：链接脚本显式定义 `.RxDescripSection`/`.TxDescripSection` 到 0x20010000（SRAM1），
  改动最小，但 FreeRTOS 堆仍在 DTCM（若 USART 等 DMA 用其 buffer 仍有隐患）。栈回退 4096。

### 经验（F7 ETH 必记）
CubeMX 默认把 ETH 描述符段放在 0x20000000（DTCM），F7 上必须显式移到 SRAM1/SRAM2，
否则 ETH DMA 收包即崩。改链接脚本（双Bank/内存布局）时切勿删除 ETH 描述符段定义。

## 修复完成（方案A，用户确认）
- 链接脚本 `STM32F767xx_FLASH.ld`：RAM ORIGIN=0x20010000, LENGTH=448K（跳过 DTCM 64KB）。
- `LWIP/Target/lwipopts.h`：撤销 TCPIP_THREAD_STACKSIZE 8192 覆盖，回退 CubeMX 默认 4096。
- 编译通过：RAM 51.57%(448K) / FLASH 39.44%。
- nm 复验：DMARxDscrTab=0x20010920、DMATxDscrTab=0x200109C0、ucHeap=0x2001107C、
  memp_memory_RX_POOL=0x2003C0F0，全部在 SRAM1/SRAM2（ETH DMA 可达），DTCM 已空置。
- MPU region0 仍 Base 0x20000000/512KB（覆盖空 DTCM+SRAM1/2，CPU 可访问，无害，未改）。
- 待烧录验证：插网线不再 HardFault 且能正常通讯（ping / 上位机 UDP 发现）。

## 澄清：`.Rx_PoolSection` 段无需单独处理（方案A已覆盖）
- 用户问 "还有 .Rx_PoolSection 这个段"。
- 当前工程 RX_POOL 由 `ethernetif.c:98` 的 `LWIP_MEMPOOL_DECLARE(RX_POOL, 32, sizeof(RxBuff_t), ...)`
  生成，符号 `memp_memory_RX_POOL_base` 是**普通 BSS**（非 CubeMX 默认 lwip.c 里那种
  `section(".Rx_PoolSection")` 钉死地址），实测落 0x20037950（SRAM1，DMA 可达 ✅）。
- 即方案A（RAM 起点 0x20010000 跳过 DTCM）已让所有 RAM 分配——描述符 / RX_POOL / FreeRTOS 堆 /
  LwIP PBUF_POOL 堆——全部落在 SRAM1/SRAM2，DMA 可达，**无需额外定义 `.Rx_PoolSection`**。
- 防御性段定义（可选，非必须）：若将来想和 CubeMX 默认对齐，可在 `.bss` 后加
  `.RxDescripSection/.TxDescripSection` 等，但**不要** `ABSOLUTE(0x2007C000)` 钉 SRAM2（RX_POOL 0x18000
  会溢出 SRAM2 末尾 0x2007FFFF → 链接错误）；只声明段名、位置交给链接器即可。
- 即使 CubeMX 重生成恢复默认 `.Rx_PoolSection`（ABSOLUTE 到 SRAM2），也仍 DMA 可达，不会回归 DTCM 问题。

## 最终根因定位（推翻前面所有局部假设）

### 现象
- 用户烧录"DTCM 跳过 + INTERFACE 4096 + TCPIP 8192"版本后，插网线仍 HardFault（STKOF），
  调用链变为 `tcpip_thread → tcpip_thread_handle_msg → ethernet_input → ip4_input`。
- 同时 AutoIP 一直协商失败。

### 与 Oil_Pump_Control（H743，能正常通讯）的完整对比结果

| 项 | SensorConcentrator (F767) | Oil_Pump_Control (H743) |
|---|---|---|
| CMSIS-RTOS 版本 | v1（栈参数单位 **word**） | v2（栈参数单位 **字节**） |
| `LWIP_RAM_HEAP_POINTER` | `0x20020000`（CubeMX 默认） | `0x30000800`（但配合 `MEM_LIBC_MALLOC=1` 成死代码） |
| `MEM_LIBC_MALLOC` / `MEMP_MEM_MALLOC` | **未定义** | **1** |
| `MEM_SIZE` | 65535 | 65535（死代码） |
| MPU Region0 | 0x20000000/512KB, **TEX=0,C=0,B=0,S=1** → Strongly-Ordered | 0x24000000/512KB, Normal Cacheable |
| ETH 描述符/RX_POOL 段 | 链接脚本无定义，孤儿段 | `ld:186-206` 显式声明 + ALIGN(32) + 放 RAM_D2 |
| `INTERFACE_THREAD_STACK_SIZE` | 350 word → 后改 4096 word（误按字节理解） | 4096 字节 = 1024 word |
| `TCPIP_THREAD_STACKSIZE` | 4096 word → 后改 8192 word | 4096 字节 = 1024 word |
| `configTOTAL_HEAP_SIZE` | 100 KB | 200 KB |

### 真正的三大根因

1. **LwIP 内部堆与 FreeRTOS ucHeap 硬重叠（最直接导致 STKOF）**
   - `lwipopts.h:129`：`#define LWIP_RAM_HEAP_POINTER 0x20020000`。
   - `mem.c:524`：`ram = (u8_t *)LWIP_MEM_ALIGN(LWIP_RAM_HEAP_POINTER)`。
   - 当前 ELF：`ucHeap` = 0x20020D94，大小 0x19000（100KB），结束 0x20039D94；
     `ram_heap` = 0x20039DDC，大小 0x6013（24KB）。两者起始仅差 0x48，几乎紧贴。
   - 插网线后 `mem_malloc`/`memp_malloc` 开始向 0x20020000 写，直接踩踏从 ucHeap 分配的
     tcpip_thread/ethernetif_input 任务栈 → 哨兵字节被改 → `configCHECK_FOR_STACK_OVERFLOW=2`
     报 STKOF；同时破坏 ARP/IP 包 pbuf，表现为 `ip4_input` 路径崩。
   - Oil_Pump_Control 免疫原因：开了 `MEM_LIBC_MALLOC=1` + `MEMP_MEM_MALLOC=1`，LwIP 堆走
     libc malloc（由链接脚本 `._user_heap_stack` 正规预留），`LWIP_RAM_HEAP_POINTER` 是死代码。

2. **MPU Region0 把整片 RAM 设为 Strongly-Ordered（非对齐访问必 HardFault）**
   - `main.c:219-230`：Base=0x20000000, Size=512KB, TEX=0, C=0, B=0, S=1 → Strongly-Ordered。
   - Strongly-Ordered 内存对非对齐访问一律 UsageFault(UNALIGNED) → HardFault。
   - LwIP 解析以太网帧时，IP 头从 MAC 头后 14 字节开始，`ip4_input` 读取 src/dst IP 地址是
     2 字节对齐的 u32 访问，正好触发。之前对 `etharp_raw` 的补丁只覆盖了 ARP 路径，没覆盖 IP 路径。
   - Oil_Pump_Control 免疫：R0 是 Normal Cacheable，非对齐访问合法；仅 0x30000000 DMA 区是 Device。

3. **ETH 描述符段未在链接脚本声明，且对 F767 DTCM 大小判断错误**
   - F767 DTCM 是 **128 KB**（0x20000000–0x2001FFFF），不是 64 KB。
   - 之前把 `RAM ORIGIN` 改到 0x20010000 仍在 DTCM 内，描述符实际仍落 DTCM；
     加上段未在链接脚本声明，是孤儿段，地址不受控。
   - 必须像 Oil_Pump_Control 那样显式声明 `.RxDescripSection/.TxDescripSection/.Rx_PoolSection`，
     并把 RAM ORIGIN 改到 0x20020000（真正的 SRAM1 起点）。

### 本次修复（4 个文件）

1. **`LWIP/Target/lwipopts.h` USER CODE 1 保护区**
   - `#undef LWIP_RAM_HEAP_POINTER`：取消绝对地址，让 LwIP 内部声明 `ram_heap` 数组进 .bss。
   - `#undef MEM_SIZE` / `#define MEM_SIZE (24*1024)`：从 65535 降到 24KB，减小 .bss 占用。
   - `#undef TCPIP_THREAD_STACKSIZE` / `#define TCPIP_THREAD_STACKSIZE 4096`：
     回滚之前误扩的 8192 word（32KB），恢复 CubeMX 默认 4096 word（16KB）。

2. **`Core/Src/main.c` MPU_Config**
   - Region0：`TypeExtField = MPU_TEX_LEVEL1`（TEX=1），`IsCacheable=NOT_CACHEABLE`，
     `IsBufferable=NOT_BUFFERABLE`，`IsShareable=NOT_SHAREABLE` → **Normal Non-cacheable**。
     既允许非对齐访问，又保持 ETH DMA 一致性（非缓存）。

3. **`STM32F767xx_FLASH.ld` 链接脚本**
   - 新增 `DTCM (xrw) : ORIGIN = 0x20000000, LENGTH = 128K`。
   - `RAM (xrw) : ORIGIN = 0x20020000, LENGTH = 384K`（SRAM1 368K + SRAM2 16K）。
   - SECTIONS 里显式声明：
     - `.RxDescripSection (NOLOAD)`
     - `.TxDescripSection (NOLOAD)`
     - `.Rx_PoolSection (NOLOAD)` 并捕获 `*(memp_memory_RX_POOL*)`

4. **`LWIP/Target/ethernetif.c`**
   - `INTERFACE_THREAD_STACK_SIZE`：`4096` word → **1024** word（= 4KB，与 Oil_Pump_Control 的
     4096 字节等效）。之前按字节误解放大到 4096 word（16KB）导致 FreeRTOS 堆超支。
   - 增加 GNU 下的 `__attribute__((section(".Rx_PoolSection"))) extern u8_t memp_memory_RX_POOL_base[];`
     声明，让 RX_POOL 被链接脚本捕获到 32 字节对齐的专用段。

### 编译验证结果
- `DTCM: 0 B / 128 KB`（已完全空置）。
- `RAM: 261216 B / 384 KB = 66.43%`。
- `FLASH: 206252 B / 512 KB = 39.34%`。
- `.data` @ 0x20020000；`.bss` @ 0x20020000+；ETH 描述符/RX_POOL 全落在 0x20020000+（SRAM1）。
- `ucHeap`（0x20020D94, 100KB）与 `ram_heap`（0x20039DDC, 24KB）不再重叠，间隔 72 B。
- `.Rx_PoolSection` = 0xC420（约 50KB）@ 0x20051640，32 字节对齐。

### 关于 AutoIP 协商失败
- AutoIP 失败是上述内存重叠/MPU 问题的连带现象：
  - `autoip_start` 内部 `mem_calloc` 分配 `struct autoip`，返回的指针落在被 ucHeap 污染的区域；
  - ARP probe/announce 的 pbuf 从被踩的 LwIP 堆 / PBUF_POOL 分配，内容异常；
  - `ip4_input` 解析收到/发出的包时又因 Strongly-Ordered 触发非对齐 HardFault。
- Oil_Pump_Control 能正常 AutoIP 的核心差异：LwIP 走 libc malloc（不重叠），且 MPU 把代码/数据区
  设为 Normal Cacheable（非对齐合法）。
- 本次修复后，SensorConcentrator 的 AutoIP 协商应能正常完成。

烧录最终版本，验证：

2. AutoIP 能拿到 169.254.x.x；
3. 电脑与设备同段后能 ping 通、上位机 UDP 发现能收到广播。

### ⚠️ 更正后的真实根因（第三轮）：ARP 解析失败，非 IP/掩码/冲突
- 用户贴出 PC `ipconfig`：PC IP=169.254.41.12，掩码=255.255.0.0（/16）。
  → 推翻前两轮假设：目标 IP 正确、PC 与设备无 IP 冲突、掩码也正确。
- 现象精确定位：设备广播 `device_online` PC 能收；PC **单播**到 169.254.41.0:50000 设备收不到；
  改 PC 发**广播** 255.255.255.255:50000 设备能收。
- 剩余唯一原因：**单播需要 PC 先用 ARP 解析出设备 MAC，这一步失败**。
  广播帧无条件上网线（L2 接收正常，证明设备 ETH RX/lwIP 正常），单播需 ARP 成功才能发包。
- 关键事实（读 autoip.c:88 `LWIP_AUTOIP_CREATE_SEED_ADDR`）：
  设备 AutoIP 地址 = 169.254.0.0 + (hwaddr[4] | hwaddr[5]<<8)，**由 MAC 末两字节确定性算出**，
  非随机。本机 MAC 末两字节 = 00:29 → host offset 0x2900 → 固定 169.254.41.0（末字节为 0）。
- 待 Wireshark 抓 PC 网卡 `arp` 过滤确认到底是：
  (A) PC 根本没发出 ARP request（疑似 Windows 把末字节 .0 当网络地址拒绝发 / 或 APIPA 路由怪癖）；
  (B) PC 发了 ARP request 但设备没回 ARP reply（设备侧 etharp 应答问题）。
- 注：169.254.41.0 在 /16 下主机位=0x2900≠0，按 RFC 是合法主机地址，不该被当网络地址；
  但 Windows 某些路径对末字节 .0 有 classful 遗留处理，属可疑点。

## UDP"能发不能收"根因定位与修复（插线 HardFault 修好后）

### 现象
- 设备能正常发送 `device_online`（广播 255.255.255.255:50000）→ 上位机能看到；
- 但设备 `udp_recv_callback` 不进、`udp_discovery_task` 收不到上位机回复。

### 根因（非设备代码问题）【⚠️ 已更正，见末尾】
- 设备发送用 `udp_sendto(upcb, p_tx, IP_ADDR_BROADCAST, UDP_LISTEN_PORT)`（广播）；
- 接收用 `udp_bind(pcb, IP_ADDR_ANY, UDP_LISTEN_PORT)` + `SOF_BROADCAST` + `NETIF_FLAG_BROADCAST`（可收广播）；
- **初判误判**：曾误以为"上位机单播到 169.254.41.0 不是设备真实 IP"。
  实际设备真实 IP 就是 169.254.41.0（串口 `Local IP: 169.254.41.0` 与 device_online JSON 的
  `cur_ip:169.254.41.0` 双重证实）。所以单播目标 IP 是对的，**不是写错**。

### ⚠️ 真实根因更正：PC 与设备 IP 冲突（同为 169.254.41.0）
- 排查"电脑未识别设备"时曾建议 PC 设 169.254.x.x，用户很可能把 PC 网卡直接填成
  与设备相同的 169.254.41.0（或 PC 的 APIPA 恰好也选了 .41.0）。
- PC 与设备的 IP 相同 → PC 发单播到 169.254.41.0 时，PC 协议栈判定"这是我自己"→ **本地环回，
  根本不上网线** → 设备收不到；而广播帧无条件上网线，故广播能通、单播不通。
- 这解释了全部现象：device_online 广播能收、单播 config_set 收不到、改广播后 callback 进来。
- **修复（改 PC，不动设备）**：PC 网卡 IP 改为与设备不同的同段地址，如 169.254.41.1 / 255.255.0.0，
  网关 DNS 留空。改后单播 169.254.41.0:50000 经 ARP 正常上网线、设备可收。

### 方案 A 误判回顾（留档）
- 曾误判为 RX buffer 对齐问题，在 `lwipopts.h` 加 `#undef MEM_ALIGNMENT`/`#define MEM_ALIGNMENT 8`；
- 实测 `memp_memory_RX_POOL_base` 仍是 0x2004DAEC（mod8=4），因 mempool 底层 u8_t 数组符号地址不受
  MEM_ALIGNMENT 影响；且当前 RAM 是 Normal Non-cacheable，cache 对齐本就不影响收包；
- 该改动**无害**（与 Oil_Pump_Control 对齐有效），但**非本次根因**，可保留。

### 修复（改上位机，不动设备）
把上位机 `config_set` 发送目标从单播 `169.254.41.0:50000` 改为**广播 `255.255.255.255:50000`**
（或先解析 device_online 报文里的 `cur_ip` 真实字段再单播）。

### 验证结果（用户确认）
- 上位机改为广播 `255.255.255.255:50000` 后，设备 `udp_recv_callback` **正常进入**，UDP 接收成功。
- 证明设备侧 UDP 收发链路完全正常，根因确为上位机单播目标 IP 写错。

### 经验（AutoIP 局域网发现必记）

## 修复：FAL 写内部 Flash 报 PGPERR（Partition write error / pr=0x00000040）

### 现象
- 上电 FAL 初始化完成后，KVDB（ef_kvdb1，Bank2 S17+S18 @0x080A0000/0x080C0000，256KB）首次写入失败：
  `[E/FAL] (fal_partition_write:469) Partition write error! Flash device(stm32_onchip) write error!`
- 伴随 `[FLASH] pr=0x00000040`（旧版打印；现代码打印 `[FLASH] prog fail SR=0x...`）。
- 0x40 = FLASH_SR bit6 = **PGPERR**（Programming Parallelism Error）。

### 根因
- `fal_flash_stm32f7_port.c` 的 `ram_flash_program_dword()` 做双字(64bit)编程时，先写 addr 低 32 位、
  再写 addr+4 高 32 位，与 ST HAL `FLASH_Program_DoubleWord` 几乎一致，**但缺了两次写之间的 `__ISB()`
  和第二次写后的 `__DSB()` 屏障**。Cortex-M7 的 F7 Flash 控制器在没有屏障时可能把两个字写乱序/合并，
  误判为并行度不匹配 → PGPERR。ST HAL 正是靠这两个屏障规避。

### 已排除的干扰项（重要）
- **SNB 编码正确**：0x080A0000 = Bank2 扇区1 = FLASH_SECTOR_13(=13)→HAL 加4→SNB 17；
  0x080C0000 = Bank2 扇区2 = FLASH_SECTOR_14(=14)→SNB 18。驱动直接填 SNB=17/18 恰为正确物理扇区，擦除目标无误。
- **对齐无误**：FDB_WRITE_GRAN=64 → FDB 所有写均按 8 字节对齐/取整，驱动 8 字节对齐检查通过后才进原语，
  PGPERR 确为原语内部时序问题，非对齐被拒（对齐被拒只会返回 -1，不会进原语打 SR）。
- F7 的 FLASH_SR 无 PGSERR/RDERR，仅 OPRR/WRPERR/PGAERR/PGPERR/ERSERR，FLASH_ERR_FLAGS 已覆盖全部。

### 修复（单文件 `UserCode/Drivers/flash/fal_flash_stm32f7_port.c`）
- `ram_flash_program_dword()`：在两路 32 位写之间加 `__ISB()`、第二路写后加 `__DSB()`，
  并在函数开头 `ram_flash_wait()` 之后加一次 `ram_flash_clear_flags()`（每次编程从干净 SR 开始）。
- 其余（SNB、PSIZE=DOUBLE_WORD、PG 置位/清除顺序）与原 HAL 一致，未动。

### 验证通过（用户贴新日志，2026-09-09 12:00）—— 结论被随后推翻
- 上电日志：`fal_flash_init` 成功 → FAL 分区表（ef_kvdb1 @0x080a0000/256KB）正常 →
  `Flash Abstraction Layer initialize success` → `[NET:152] ETH database initialization successful`。
- 当时日志无 `Partition write error` + `pr=0x00000040`，误判 ISB/DSB 屏障生效。

### ⚠️ 结论推翻：PGPERR 再次复现（2026-09-09 13:56），ISB/DSB 屏障非根治
- 用户 13:56 重新烧录后，上电日志**再次出现** `[FLASH] pr=0x00000040` + `Partition write error`，
  证明 12:00 那次"干净"是偶发巧合，ISB/DSB 屏障未能根治 PGPERR。
- **重新定位根因**：PGPERR = Flash 控制器判定"编程数据宽度与 PSIZE 不匹配"。ST HAL 的双字编程序列
  （清PSIZE→设DOUBLE_WORD→置PG→写低32→__ISB→写高32→__DSB）本身正确，但它**跑在 Flash 里**，
  两次 store 间有取指等待；本驱动跑在 **SRAM(RamFunc)**，两次 store 间隔更短，F7 Flash 控制器来不及
  锁存低半字就收到高半字 → 偶发 PGPERR。__ISB 是取指屏障，不保证第一次写已到达 Flash 控制器，故无效。
- **最终修复（单文件 `UserCode/Drivers/flash/fal_flash_stm32f7_port.c`）**：`ram_flash_program_dword()`
  改为**两次独立的 32 位字编程**（每次 `PSIZE=FLASH_PSIZE_WORD` + `PG` + 写 4 字节 + `__DSB()` + 等 `BSY` +
  清 `PG`），消除双字并行度时序依赖，与 ST `FLASH_Program_Word` 完全一致。新增 `ram_flash_program_word()`，
  dword 调用它两次。PSIZE 宏与 CR_PSIZE_MASK 值已核对无误（DOUBLE_WORD=0x300, MASK=0xFFFFFCFF）。

## 修复：lwIP 断言 "sys_timeout: timeout != NULL, pool MEMP_SYS_TIMEOUT is empty"

### 现象
- 上电/连服务器瞬间触发断言（timeouts.c:190），串口打印：

### 根因（确定性，非偶发）
- `memp_malloc(MEMP_SYS_TIMEOUT)` 失败 → 定时器内存池被占满。
- `opt.h:508` 的 `LWIP_NUM_SYS_TIMEOUT_INTERNAL` 计算式 = `LWIP_TCP + IP_REASSEMBLY + LWIP_ARP + 2*LWIP_DHCP + LWIP_AUTOIP + LWIP_IGMP + LWIP_DNS + ...`，

- 本工程 `LWIP_SNTP=1`，`sntp_init()`（在 `net_config_init()` 上电早期被调用）内部通过 `sys_timeout()`

- 上电后同时存活的定时器：ARP(1) + AutoIP(1) + SNTP(1~2) + TCP 连接(1) ≈ 4~5 个；
  而 `MEMP_NUM_SYS_TIMEOUT` 默认 = `LWIP_NUM_SYS_TIMEOUT_INTERNAL`（≈3，TCP+ARP+AutoIP），
  **不含 SNTP** → 第 4 个 `sys_timeout`（TCP 定时器）分配失败 → 断言。
- 排除泄漏：`ethernet_link_thread` 不重复 `autoip_start`；`net_config_init()` 仅 `StartDefaultTask` 调一次；
  configured 分支先 `netifapi_autoip_stop` 再 set_addr，无重复 start。故为池太小，非泄漏。

### 修复（`LWIP/Target/lwipopts.h`，USER CODE BEGIN 0 区，CubeMX 不覆盖）
- 在 `MEMP_NUM_UDP_PCB`/`MEMP_NUM_TCP_PCB` 旁新增：
  ```c

  #define MEMP_NUM_SYS_TIMEOUT    12
  ```
- 选 12：内部≈3 + SNTP 2 + TCP 1 + 余量，足够且廉价（每个 struct sys_timeo ≈24B，12 个≈288B）。
- `init.c` 的 sanity check `MEMP_NUM_SYS_TIMEOUT >= LWIP_NUM_SYS_TIMEOUT_INTERNAL` 满足（12≥3），无编译报错。

### ✅ 真根因已找到并修复（2026-09-09 15:30）——ARP 字节序被宏反转
用户 `arp -a` 结果：**完全没有 192.168.0.120 的动态条目** → 设备**根本没回 ARP**。
但 ARP 请求是 L2 广播，设备能收 UDP 广播就一定能收到它 → 问题在 ARP 协议栈本身。

**根因：本项目为规避 UNALIGNED HardFault，在 `LWIP/Target/lwipopts.h` 重定义了
`IPADDR_WORDALIGNED_COPY_FROM/TO_IP4_ADDR_T`，但多套了一层 `PP_HTONS`，把 ARP 报文里的 IP 字节序反转了。**

- 原生 lwIP（`Middlewares/.../lwip/prot/etharp.h:71/78`）是 **纯 `SMEMCPY(dest,src,4)` 字节拷贝，无字节序转换**。
- 关键点：`ip4_addr_t.addr` 本身**已按网络字节序存储**（小端 CPU 上内存字节即 `C0 A8 00 78`），
  `addrw[0]/addrw[1]` 是 u16_t，小端下天然拼回同样字节序列 → **直接赋值即可，绝不能 PP_HTONS**。
- 实测：192.168.0.120 被写成 **168.192.120.0**（已用 Python 脚本验证：OLD=[168,192,120,0]）。
- 命中点（grep 全库仅 3 处）：
  - `etharp.c:678-679` `etharp_input` 解出 `sipaddr/dipaddr` → **garbled** →
    `etharp.c:686 for_us = ip4_addr_cmp(&dipaddr, netif_ip4_addr(netif))` 恒为假 →
    **设备永不回 ARP**（完美解释 `arp -a` 无条目）。
  - `etharp.c:1137-1138` `etharp_raw` 写**出向** ARP → 对端收到错 IP → 设备自己发的
    ARP request 也无效 → 无法解析 192.168.0.12 → TCP `err:-13`(ERR_ABRT)。
  - `autoip.c:471-472` `autoip_arp_reply`（AutoIP 已停，暂不影响）。
- **为什么所有症状都对上**：广播不需要 ARP → 广播 UDP 一直通；凡是需要 ARP 的单播
  （ping / 单播 UDP / TCP 建链）全挂。且 AutoIP 时期(169.254.41.0)与静态时期(192.168.0.120)
  **同样复现**，因为与 IP 无关。
- **为什么 Oil_Pump_Control(H743) 正常**：它的 lwipopts.h **没有这个宏补丁**（grep 无匹配），
  走原生 SMEMCPY，ARP 正确。

**修复**：去掉两个宏里的 `PP_HTONS`，改为纯半字搬运（与 SMEMCPY 字节等价）：
```c
#define IPADDR_WORDALIGNED_COPY_FROM_IP4_ADDR_T(dest, src) do { \
    u32_t _tmp = ((const ip4_addr_t *)(src))->addr; \
    ((struct ip4_addr_wordaligned *)(dest))->addrw[0] = (u16_t)(_tmp); \
    ((struct ip4_addr_wordaligned *)(dest))->addrw[1] = (u16_t)(_tmp >> 16U); \
} while(0)
#define IPADDR_WORDALIGNED_COPY_TO_IP4_ADDR_T(dest, src) do { \
    u32_t _tmp; \
    _tmp  = ((u32_t)((const struct ip4_addr_wordaligned *)(src))->addrw[1]) << 16U; \
    _tmp |= (u32_t)((const struct ip4_addr_wordaligned *)(src))->addrw[0]; \
    ((ip4_addr_t *)(dest))->addr = _tmp; \
} while(0)
```
**不会复现 UNALIGNED**（已反汇编验证）：`etharp_raw` 里 sipaddr 仍是两条 `strh [r3,#14]` /
`strh [r3,#16]`，dipaddr 是 `strh [r3,#24]`/`[r3,#26]` —— 全部 2 字节对齐半字写，
packed 结构体对齐为 1，GCC 不会合并成 u32 写。

- **重定义 lwIP 内部宏时，语义必须与原生定义逐字节等价**；"顺手加个字节序转换"是致命的。

## 网线断开检测不到 / 重插后不通（2026-09-09 16:10，已修）
### 现象
拔网线后设备无反应、不重连；重插后 UDP/TCP 都不通。

### 根因（三处真实缺陷）
1. **TCP 客户端完全不感知物理链路（主因，"没有触发重连"的直接原因）**
   `Tcp_client_task` 只在 `tcp_pcb == NULL` 时才重连。拔线后 `tcp_pcb` 仍非 NULL 且
   `g_tcp_connected==1`，只能等 lwIP TCP **重传超时**（TCP_MAXRTX=12，指数退避，
   几十秒~几分钟）才触发 `errf -> tcp_pending_close`。
2. **`ethernet_link_thread` 裸调 `netif_set_down/up/link_down/link_up`（真实数据竞争）**
   这些函数内部有 `LWIP_ASSERT_CORE_LOCKED()`（netif.c:990/1028 已确认），而链路线程
   **不是 tcpip_thread** → 与 tcpip_thread 的 ARP/AutoIP 定时器并发读写 netif 共享状态，
   可导致重启后 netif 状态不一致。与本项目此前 `net_config_init` 踩的坑同类。
3. **`heth.Init.MACAddr` 指向 `low_level_init()` 的局部栈数组（悬空指针，隐患）**
   CubeMX 生成 `uint8_t MACAddr[6]` 为局部变量，`heth.Init.MACAddr = &MACAddr[0]`；
   函数返回后指针悬空。首次 `HAL_ETH_Init()` 侥幸有效（栈帧未失效），但若再次调用
   `HAL_ETH_Init()`（链路恢复重初始化等）就会把栈垃圾写进 MACA0 → MAC 过滤器失效
   → 单播收不到（广播仍通）。

### 已排除的猜测
- 链路线程逻辑与 Oil_Pump_Control(H743) **逐行相同**，不是逻辑差异。
- `ETH_UpdateDescriptor` 只在 `BackupAddr0==0` 时才新分配 buffer，Stop/Start 不泄漏 RX_POOL。
- `netif_set_link_up` → `autoip_network_changed` 不会重启 AutoIP（`autoip_stop` 已置
  `state=OFF`，autoip.c:337 条件不满足）。
- `HAL_ETH_Stop_IT` 后 `gState=READY`，`HAL_ETH_Start_IT` 能正常重建描述符并重启 DMA。

### 改动
- `LWIP/Target/ethernetif.c`
  - USER CODE 0 增加 `#include <stdio.h>` + `#include "lwip/netifapi.h"`。
  - USER CODE MACADDRESS：改用 `static uint8_t s_mac_addr[6]` 并显式
    `heth.Init.MACAddr = &s_mac_addr[0];`，消除悬空指针。
  - 链路线程：`netif_set_*` → `netifapi_netif_set_*`（down/up/link_down/link_up 四处），
    并加 `[ETH] link DOWN/UP (phy=..., 100M/FD)` 打印，使链路变化可观测。
- `UserCode/Drivers/ETH/net_comm_task.c` `Tcp_client_task`
  - 新增 `s_last_link_up` 边沿检测：`netif_is_link_up(&gnetif)`（只读 flags，无需 core lock）。
  - 断线沿：清 `hb_lost_cnt`，`tcp_pending_close=1` 立即断链；
  - 上线沿：清计数、复位 `stable_tick/reconnect_tick`、`g_fast_reconnect=1` 跳过 5s 节流。
  - 断线期间 `if(!link_up) { osDelay(200); continue; }`（**必须放在 tcp_pending_close
    处理之后**，否则断线时的异步关闭会被跳过）。

## 移除应用层心跳，改用「链路层 + TCP Keepalive」双层检测（2026-09-09 16:30）

### 背景与重要发现
用户要求：去掉协议层心跳，改用链路层检测。排查时发现一个**此前未被察觉的事实**：
应用层心跳的**发送代码早已被注释**（`net_comm_task.c` 原 1344 行 `//tcp_send_heartbeat`），
实际只剩一个"死计数"定时器：
- 每 `HEARTBEAT_PERIOD_MS`(20s) 递增 `hb_lost_cnt`；
- 累计到 `HB_LOST_MAX`(2) 就 `tcp_pending_close = 1` 强制断链；
- **唯一清零点**是收到通过 HMAC 校验的下行报文（`net_comm_task.c` 原 1909 行 `hb_lost_cnt = 0`）。
→ 后果：设备根本不发心跳，上位机自然不回，只要上位机静默 40s，
  **设备就会把自己踢下线一次**（周期性自伤重连）。这是"连上了又莫名断开"的隐藏元凶之一。

### 改造方案（用户选定：链路层 + lwIP TCP 保活）
职责重新划分：
| 场景 | 检测手段 | 响应时延 |
|---|---|---|
| 物理断线（拔线/对端掉电/PHY down） | `ethernetif.c` 链路线程 PHY 轮询 + `net_comm_task.c` 的 `netif_is_link_up()` 边沿检测 | ~100ms |
| 链路仍 up 但对端死（进程崩/不响应） | lwIP TCP Keepalive（内核自动探测） | 10s 起探，25s 判死 |

### 改动清单
1. `LWIP/Target/lwipopts.h`（`USER CODE BEGIN 0` 区，CubeMX 不覆盖）
   - `LWIP_TCP_KEEPALIVE` **0 → 1**（保活参数 `TCP_KEEPIDLE_DEFAULT=10000` /
     `TCP_KEEPINTVL_DEFAULT=3000` / `TCP_KEEPCNT_DEFAULT=5` 此前就已配好，只是开关关着）。
   - 总超时 = keep_idle + keep_cnt×keep_intvl = 10s + 5×3s = **25s**。
2. `UserCode/Drivers/ETH/net_comm_task.c`
   - 创建 PCB 处（`tcp_new()` 之后、`tcp_connect()` 之前，处于 `LOCK_TCPIP_CORE()` 内）新增：
     `ip_set_option(new_pcb, SOF_KEEPALIVE);` + 显式赋 `keep_idle/keep_intvl/keep_cnt`。
   - 删除整个"已连接定时发心跳"块，改为注释说明两层检测职责。
   - 删除 `hb_lost_cnt` / `last_hb_tick` 变量及其全部引用（safe_tcp_close、链路边沿、
     pending_close、未配置分支、tcp_error_callback、tcp_connected_cb、下行报文处理）。
3. `UserCode/Drivers/ETH/net_comm_task.h`：删除 `HEARTBEAT_PERIOD_MS` / `HB_LOST_MAX`，

### 原理备忘（lwIP 保活机制）
- `tcp_slowtmr()`：仅当 `ip_get_option(pcb, SOF_KEEPALIVE)` 且状态为 ESTABLISHED/CLOSE_WAIT 时生效；
  空闲 > `keep_idle + keep_cnt_sent×keep_intvl` → 发探测段并 `keep_cnt_sent++`；
  空闲 > `keep_idle + keep_cnt×keep_intvl` → **`tcp_abort`** → 触发 `errf`(tcp_error_callback)
  → `tcp_pending_close=1` → 自动重连。
- `pcb->tmr` 在**收到对端任何报文时自动刷新** → 有正常下行数据时不会误触发保活，
  因此不需要应用层再维护"最后收包时间"。
